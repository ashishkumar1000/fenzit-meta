# Employee Profile page redesign — 5 tabs (implement the approved Stitch designs)

## Context

The owner approved 5 Stitch screens (project 1594154886874615054) for the web-console employee profile: header card + tabs **Master Record | Jobs | Attendance | Leave | Payroll**, one active tab per screen, grounded in real BE/DB data (Rajuu EMP-004 as the sample). Today fenzit-web has **no employee detail route** — only the list page (`/admin/company/employees`) with inline quick-edit cells. This story builds the profile page per the designs plus the minimal additive backend it needs. Owner decisions (2026-11-21): **build membership deactivate now**; **build a punch-records endpoint** for the Attendance tab; **keep** the list-page quick-edit cells (name cell links to profile).

Sibling-pattern sources: payroll page (`AdminPayrollPage.tsx` + `payrollLoaders.ts` — `?tab=` links, per-tab loader, `Slice`/`settle`), jobs page plan (`.zcode/plans/plan-jobs-page-redesign-2026-11-20.md`).

**Layer calls** (fix-placement rule): member detail + deactivate = **BE** (new endpoints; status semantics live in DB/BE); jobs-by-employee = **BE** (additive filter param on `GET /jobs/page`); punches = **BE** (read endpoint over existing `attendance_records`); all rendering/tabs/empty-states = **FE**; **no DB migration needed anywhere** (view already exposes `technician_id`; attendance_records exists).

## BE — fenzit-be (`/Users/admin/workspace/fenzit-meta/workspace/core/backend/fenzit-be`, additive only, no migrations)

1. **`GET /members/:userId`** (`src/members/members.controller.ts`, `member.read`) — single `MemberView` (reuse the `listCompanyMembers` read path for one id): name, phone, email, avatar, employeeCode, status, role, joinedOn, canCreateJobs, jobApprovalRequired, skills. **No statutory fields** — those stay exclusively behind `GET /members/:userId/employment` (23-1 privacy invariant). Cross-tenant / removed → 404. Add controller-spec permission-table row.
2. **Membership deactivate/reinstate** — `PATCH /members/:userId/active` body `{ active: boolean }`:
   - New permission `member.deactivate` in `src/common/permissions/permissions.ts`, mapped to owner, **outside `ADMIN_PERMISSIONS`** (same exclusion as `member.employment`).
   - Service: `active:false` only from `status='active'` → `'deactivated'`; `active:true` only from `'deactivated'` → `'active'`; invited/removed → 409. **Last-active-owner guard** (409, mirrors `LAST_ADMIN` in `changeRole`). Auth impact is automatic — `membership-resolver.ts` only counts `status='active'`, so a deactivated member loses access on next request; reinstate restores. Write audit entries (action + employee_code only, no PII).
   - Extend status enum (`'invited'|'active'|'deactivated'|'removed'` in `src/common/members/company-members.ts`); add `deactivated` to `/members/page` status filter DTO + list response already carries status.
3. **`GET /attendance/punches?employeeId&from&to`** (`src/attendance/`, `attendance.read`) — rows from `attendance_records`: workDate, checkinAt, checkinDistanceM, checkoutAt, checkoutDistanceM, officeId; newest first; span cap ≤ 62 days (day-statuses precedent); tenant-scoped, 404 on foreign employeeId. Controller-spec row.
4. **`GET /jobs/page` technician filter** (`src/jobs/dto/jobs-page-query.dto.ts` + `jobs.service.ts getJobsPage`): add `technicianId` (IsUUID, optional); filter on the view's `technician_id`; when present, **scope the stats queries to that technician** so the profile's chips are honest (whole-company stats would lie there). Legacy cursor `/jobs` untouched (mobile).
5. **Deferred-work pickups (members module touch):** `updateEmployment` normalises trimmed `''` → `null` on plain-text fields (UAN/PF empty-string hygiene item); fix the stale `@ApiQuery` jobSetting enum on `/members/page`.
6. Tests: members/jobs/attendance `*.spec.ts` additions (permission tables + service behavior); run members/jobs/attendance jest suites.
