# Customers page redesign — mockup-driven, Employees-page pattern

## Context

The admin customers page (`/admin/company/customers`) is the last bare-bones console page: one card, cursor load-more, no search/filters/sort/pager/code/export. The employees page was redesigned (84142e5) into the full console pattern; the owner gave a mockup for customers in the same language and wants the same exercise here. Two product calls are already made with the owner: **buckets are disjoint** (New leads = 0 jobs / Single job = exactly 1 / Repeat = 2+ jobs — tiles + tab counts sum to total), and the mockup's **Region filter is deferred**. BE changes are authorised and push-to-main for BE is authorised; commits still go through BMAD review first.

## Design decisions (mockup → Fenzit reality)

- **Buckets** (owner-approved): `new` (0 jobs), `single` (1 job), `repeat` (2+ jobs). Stats + tab chips always whole-company (stable while filtered), like members.
- **Sorts**: `created_new` (default, today's order) / `created_old` / `name_az` / `name_za` / `recent_activity` (last job, nulls last).
- **VIP badge**: `jobCount >= 10` renders a small violet chip beside the name (mockup's "≥10 jobs completed").
- **Row anatomy**: avatar initials → name (semibold) + `CST-NNN` caption under it + VIP chip; phone with copy button; address with pin; Jobs count chip (sortable); Last job activity (sortable).
- **Tiles**: Total customers / New leads / Single job / Repeat — mirror tab counts (employees tile pattern, `ConsoleTiles`).
- **Deferred to the ledger** (mockup chrome with no product backing): Region/city filter, grid-list toggle, checkbox bulk select, Bulk Import button (stays on Inspect for staff), Live-Sync badge, notification/help buttons, +18%/Top-11% trend analytics, customer edit/delete UI, jobs-column drill-down.

## BE changes (fenzit-be) — one migration + one endpoint

**Migration** `supabase/migrations/20261117xxxxxx_customers_overview_and_codes.sql` (house style, comments explaining why):
1. `create or replace view public.customers_overview with (security_invoker = true)` — `customers LEFT JOIN jobs` aggregated: `job_count`, `last_job_date (max scheduled_start)`, all customer columns + re-asserted grants (attendance-view precedent 20261001000001). RLS stays with the invoker.
2. Customer codes, cloning the proven employee-code mechanism (20261020000003): `customer_sequences (tenant_id, last_seq)` counter table + `set_customer_code()` BEFORE INSERT trigger on `customers` → `'CST-' || lpad(seq, GREATEST(3, len), '0')`, tenant-unique, write-once; oldest-first backfill, counters continue from max.

**Endpoint** `GET /customers/page` — mirror `/members/page` exactly (in-service sort/slice/stats, that's the house pattern):
- `dto/customers-page-query.dto.ts`: `page`, `pageSize` (≤100), `search`, `filter ∈ {all,new,single,repeat}`, `sort ∈ {created_new,created_old,name_az,name_za,recent_activity}` — unknown → default.
- `customers.service.ts` `getCustomersPage()`: select from `customers_overview` (q ilike on name/phone, bucket via `job_count` predicates, order, slice) + `stats {total, new, single, repeat}` computed in service.
- Add `customerCode` to `CUSTOMER_COLUMNS`, `CustomerListItemDto`, `CustomerDetailResponseDto`, and the create-response DTO (so the dialog can echo "Their customer code is CST-007.").
- Controller: `@Can('customer.read')`, owner scope unchanged. Existing `GET /customers` (cursor) is **untouched** — the mobile app uses it.
