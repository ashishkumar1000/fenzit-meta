## Intent

**Problem:** The technician side of attendance does not exist in the app. `GET /attendance/me/access` and `POST /attendance/me/onboarding` have been live since 15-7, `/users/me` has carried the four AD-17 mirror fields (`attendanceEnabled`, `attendanceAccess`, `attendanceStartDate`, `onboardedAt`) since 15-7, and the 15-9 pre-patch fixed the view's office anchor — yet fenzo-app consumes none of it: no service, no types, no `attendanceAccess` union anywhere, no technician Attendance route (the technician tab bar is Today/History/Profile), and the shared `EnrolmentOverview.attendanceAccess` field is `string`-typed and deliberately unread. A tracked employee today sees nothing at all — FR-3's entry-point states (`none`/`upcoming`/`active`/`history_only`), FR-4's first-entry onboarding (intro + location permission + summary), and AD-17's freshness rule (refetch on foreground and on any attendance notification) are entirely unimplemented.

**Spec-time contract gap (verified 2026-09-28):** the story's summary AC — "a summary (Office, Start/End time, Late cut-off, Weekly offs)" — has **no technician-readable source**. `me/access` returns `officeId`/`officeName` only; every rules/weekly-offs route is owner-only (`/attendance/offices`, `/attendance/weekly-offs` → 403 for technicians). The epic marked 15-10 "Frontend", but the AC is unsatisfiable without a backend addition. **User direction 2026-09-28: "lets spin a separate API for attendance"** — a dedicated summary endpoint ships first from fenzit-be (backend-first rule), rather than fattening `me/access` (AD-17 keeps it light: it is refetched on every foreground and every attendance notification) or opening owner-only surfaces to technicians.

**Approach:** Two changes, in the fixed cross-repo order.

1. **BE pre-story (fenzit-be, ships and deploys FIRST):** `GET /api/v1/attendance/me/summary` `[Bearer JWT, Role: technician]` — the FR-4 summary payload for the `active` and `upcoming` states. The service reads the employee's `attendance_access_state` VIEW ROW (the same one `me/access` returns) and takes `officeId` **and the anchor date** from that row — one anchor implementation, zero drift with the tab's state (review finding #8; hand-rolling the anchor in new SQL would recreate the 15-9 defect class) — then joins only the office's rule row effective on the anchor date (FR-5's from-tomorrow rule respected) and the weekly-off selection for that anchor date (employee override if one covers it, else tenant defaults; same day-number encoding as the owner weekly-offs payload). Returns `{ officeId, officeName, startTime, endTime, lateCutOffMinutes, weeklyOffDays }`; times stay `HH:mm` strings on the wire (the house API convention — 12-hour display is FE formatting, see Boundaries). A `history_only` or `none` employee has NO covering/next assignment (disable clips both ranges), so the summary is not defined for them: those states never call this endpoint (review finding #1 — for `history_only` the view row's office is null in 100% of cases, not just post-archive; the screen is banner-only, no summary section). `me/access` is untouched; no new tables, no migrations, no RPCs (AD-3 direction). AD-22 tension, recorded: `attendance_day_context` does not exist until 16-1, so this endpoint joins the shipped tables directly — display-only, and 16-1 may re-home it on the day-context helper with no FE contract change.
2. **FE story (fenzo-app, baseline `89a8812`):** a technician `me/` attendance surface — an access store (AD-21 `useSyncExternalStore`, no new state library) seeded from the `/users/me` mirror, given an initial `me/access` fetch at registration (the AppState listener alone fires only on *change*, so an already-foreground boot would otherwise never resolve), and refreshed via `me/access` on foreground (30 s min-gap), any `attendance.*` notification, and attendance-screen focus (same min-gap); a conditional **fourth tab "Attendance"** in `TechnicianTabs` (hidden for `none` and while unknown — FR-3/UX: no attendance UI anywhere for `none`, bell stays, FR-27); the FR-4 full-screen intro for `active`/`upcoming` employees (mockup `key-onboarding-states`: headline, privacy line, **Allow location access** primary CTA reusing the shared `requestLocationPermission` helper, **Not now — I'll browse without it** secondary); and the state screens — `active` → summary (check-in control ABSENT in this story: Epic 16 owns it), `upcoming` → "Attendance starts on {date}" + summary + early-onboarding CTA + no check-in control (absent, not disabled), `history_only` → ended banner only (records/calendar surfaces are Epics 18/19; no summary section — the endpoint is not defined for this state). The notification registry gains the `attendance` action: shipped events (`attendance.holiday_added`/`attendance.holiday_removed`) render composed technician cards deep-linking to the Attendance tab, and ANY `attendance.*` realtime event triggers an access refresh through a new inverted registration seam in `useRealtimeNotifications.ts` (review finding #3 — the bridge's technician branch must change; the seam keeps `notifications` from importing `attendance`, per the spine's module boundary). Owners are untouched end to end.

## Scope decisions (proposed 2026-09-28 — pending user sign-off; frozen after approval)

- **Spec first, then implement** — this file, reviewed by the user, precedes any code (15-5/15-7/15-8/15-9 precedent).
- **A dedicated attendance summary API ships first (user-directed 2026-09-28, backend-first)** — `GET /attendance/me/summary` as specified above; `me/access` unchanged and light; owner endpoints stay owner-only. The endpoint serves `active`/`upcoming` only and reads its anchor from the `attendance_access_state` view row, so the summary can never disagree with the tab's state about WHICH office applies; `history_only` never calls it.
- **Tab visibility is store-driven, never per-screen** — one `attendanceAccessStore` (module-level, `useSyncExternalStore`) is the single source of `attendanceAccess` for the tab bar AND the screens. States: `unknown` (boot) → tab hidden; `none` → tab hidden; `upcoming`/`active`/`history_only` → tab shown. Seeded from the `/users/me` profile fetch seam (the mirror's four fields — first load, AD-17), given an initial `me/access` fetch at store registration (boot is already foreground — the AppState change listener alone would never fire), thereafter refreshed ONLY by `me/access`: foreground transitions with a 30 s min-gap (survives rapid app switches), any `attendance.*` notification via the seam, and focus of any attendance screen with the same 30 s min-gap. No flicker rule: a refetch failure or an unchanged state leaves the tab exactly as it was — the tab never toggles off while a refetch is in flight.
- **Onboarding completes server-side, once (FR-4/AD-17)** — the intro is shown on entering the Attendance tab when `attendanceAccess ∈ {active, upcoming} && onboardedAt === null` (review finding #5: a `history_only` employee's tracking has ended — asking them for location permission on a surface that can never check in contradicts the epic's "Tracked employee's first entry"; they see the ended screen directly, and if re-enabled later the intro shows then). Primary CTA requests location permission (shared `geolocation.ts` helper) and then POSTs `me/onboarding` — the POST fires after the permission result regardless of granted/denied, because completing onboarding and granting location are separate facts (first-write-wins; replay returns the original `onboardedAt`). **"Not now" dismisses WITHOUT recording** — the intro reappears on the next entry. Recorded as a deliberate PRD interpretation so triage never re-litigates it (review finding #11): FR-4's "shows once" is read as onboarding *completing* once; the *ask* may repeat until completion, which is exactly the mockup's Not-now path. A thrown permission-request error shows the intro's inline error and records nothing; Retry re-requests. The Android OS rationale on the permission dialog is the shared job helper's existing message ("…verify step completion") — accepted as-is for this story because AD-20 forbids changing the job helper (message rewording is a deferred candidate). Permission denied (including "never ask again") never dead-ends: the summary renders in full either way (FR-4 consequence); the "Turn on location to check in" button state and the Settings deep-link are Epic 16's CheckInOutButton concern (deferred). Upcoming employees can complete onboarding early (AC: "can complete onboarding early").
- **`active` ships as summary-only in this story** — the check-in/out control, its location capture and its permission-denied button state are 16-3/16-4. The screen renders the full summary with NO check-in control (absent, not disabled), and the header always reads "Attendance", never bare "Today" (UX naming-collision rule). Recorded in deferred-work.
- **`history_only` ships as an ended banner ONLY** — "Attendance tracking has ended" plus honest office-less copy; NO summary rows (review finding #1: disable clips both ranges, so the view carries no office for this state — the mockup's records rows are Epic 18/19 surfaces and are not stubbed here). Two UX deviations recorded explicitly (review finding #13): the copy is date-less because the payload carries no disable date (adding one is a BE contract change — deferred candidate), and EXPERIENCE.md's "summary also reachable later via a 'My Office' row under Today" is not built (TodayScreen is untouchable per the Never list; reachability is satisfied for now by the tab's own always-present state screens, and the My-Office row lands with 16-4's Today screen).
- **`none` is absence, everywhere (FR-3)** — tab hidden, no route content, no attendance UI anywhere; the notifications bell stays (FR-27). If access flips to `none` while the tab is focused (owner disables the employee), the tab disappears AND the app navigates back to `Today` in the same update (review finding #9: unmounting the focused tab screen must not strand the user on a blank content area). Notification deep links are tap-guarded: an attendance card's tap checks the store and navigates only for `upcoming`/`active`/`history_only`; for `none`/`unknown` the card renders but the tap is a no-op (review finding #4 — an upcoming employee can receive holiday cards and then drop to `none`).
- **Notification registry gains one action kind: `attendance`** — shipped events render as composed technician cards (review finding #6: the payloads are self-contained display DATA, not display text — `attendance.holiday_added` carries only `{holidayName, holidayDate}`, so the FE composes copy like "Holiday added: {name} — {date long-form}"; the registry's humanized fallback stays for truly unknown types) deep-linking to the Attendance tab; any `attendance.*` realtime event ALSO triggers `refreshAccess()` through an inverted registration seam: `features/attendance` registers a refetch callback at mount and `useRealtimeNotifications.ts` invokes registered callbacks for event types prefixed `attendance.` (string-matched in the notifications layer, like the existing hardcoded report events, so no cross-module import — review finding #3; `useRealtimeNotifications.ts` is a touched file and the bridge's technician branch changes by a few lines). The realtime bridge's architecture is otherwise untouched. Owner-side attendance cards are not registered (no owner attendance events shipped yet — generic fallback covers them).
- **Raw-truth rule (carried, non-negotiable)** — the FE derives entry-point state ONLY from `me/access` + the `/users/me` mirror; it never derives anything from the tenant module flag, never computes state from dates itself beyond display formatting, and trusts the server's TODAY-anchored office fields (15-9 view fix).
- **Times: wire stays `HH:mm`, display is 12-hour FE-side** (review finding #2) — NFR-5's "the app displays the dates and times the server sends (12-hour format)" is satisfied by FE formatting, consistent with every existing surface (offices cards, rules chips): the BE keeps its `toHhmm` wire convention (a second wire format for times would fork the API contract), and fenzo-app renders `10:00 AM – 6:00 PM` from `HH:mm` plus composes the cut-off copy (e.g. "Late after 10:15 AM" from `startTime + lateCutOffMinutes`). No verbatim rendering of time fields anywhere.
- **No wizard/owner-side changes** — `AttendanceHome`, the wizard, the roster, MoreScreen and the owner nav tree are untouched; 15-10 is technician-only plus the shared registry seam.

## Boundaries & Constraints

**Always:**
- Baselines: fenzo-app `89a8812`; fenzit-be `7db6e03`. BE first (ship + deploy before FE device verification of the summary), per the cross-repo ordering rule — this is an additive endpoint, so no parallel-old-shape dance is needed.
- BE: route + controller + service + DTO in the existing `src/attendance/` module following the `me-attendance.controller.ts` pattern (JWT identity only, tenant from token, fail-loud 500 on view/read failures, 403 non-technician); response DTO validated; api-contracts.md §"Attendance me" extended; unit tests per house rules; the testing ladder: implement → local server probe → push (Render auto-deploy) → production probe.
- FE: all API access through `services/resources/` — new `attendanceMe.ts` (`getAccess`, `recordOnboarding`, `getSummary`) which also **owns and exports the `AttendanceAccessState` union** (`'none' | 'upcoming' | 'active' | 'history_only'` — review finding #10: the type must live in services so neither `users.ts` nor the store imports from `features/`, and so `enrolments.ts`'s loose `string` field stays 15-9's untouched contract); `users.ts` gains the four mirror fields on the profile type importing that union; the access store lives in `features/attendance/me/` and imports the type from services. Screens never touch `apiClient` directly. Documented failures branched explicitly (401/403/5xx); `me/access` 403 for a non-technician is unreachable by construction (owner tree never calls it) and surfaces as a first-load error state, not a redirect.
- Times: `HH:mm` on the wire everywhere; 12-hour rendering FE-side via one small shared formatter (tested), and the late cut-off composed as copy ("Late after {time}") — never verbatim `HH:mm` in user-visible text (review finding #2).
- Screens follow the house tri-state contract (first-load spinner; stale banner over live content on refetch failure; `InlineError` + Retry on first-load failure). Summary fetch failure degrades the STATE frame, never the access state: the screen still shows which state it is in (started-on / ended / active) with the summary section in its own error state.
- Dates via the shared IST utils (`istTodayDate`, `formatLongDate` — with its non-YYYY-MM-DD pass-through gotcha in mind); date display uses `formatLongDate`; time display follows the 12-hour FE-formatting rule above (NFR-5); the summary's rule semantics stay server-owned — the FE only formats what the payload carries.
- A11y floor: the new tab carries an accessible label; the intro's CTAs are labelled; state headlines are headings; DS tokens only; plain-business-English copy (the 15-6 copy rule).
- New files ≤ ~300 lines; pure model + hook + dumb screen split; colocated `*.test.ts(x)`; `bun run test` (never bare `bun test`); `bunx tsc --noEmit` clean; full suite green before commit.
- Update `artifacts/implementation-artifacts/sprint-status.yaml` and this spec's Verification/Change Log in the same change that commits the story.

**Ask First:**
- Any BE change beyond `GET /attendance/me/summary` (contract gap found on device, deploy issue) — HALT and confirm; backend-first rule.
- Deep-linking notifications into specific attendance sub-screens beyond the tab root (richer screens arrive in 16+; confirm before inventing routes).
- Registering owner-side attendance cards, or adding a disable/end-date to any payload — each is a contract change; confirm.
- If the summary anchor and the access view ever disagree on device (office shown vs state), HALT — that is a BE defect (15-9 class), not an FE patch.

**Never:**
- No check-in/out UI, no location capture service, no permission-gated button states (AD-20/16-3/16-4).
- No leave UI, no calendar/day-status UI, no corrections (Epics 17/18/19).
- No fattening `me/access`, no new RPCs, no migrations, no direct PostgREST/RPC calls from the app.
- No polling fallback (AD-18); no offline queue; no NetInfo gating (AD-21: read screens may render last-loaded with a banner only).
- No MMKV/AsyncStorage persistence of access state or onboarding flags — session memory only; server truth is the only record ("shows once" is `onboardedAt`, never a local flag).
- No changes to the job tabs, Today/History/Profile screens, the owner tree, the wizard, or the roster.
- No intro carousel reimplementation — the intro is a single static screen per the mockup (the app's `OnboardingScreen` carousel is a different, pre-auth surface; not reused).
