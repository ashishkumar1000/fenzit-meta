## Intent

**Problem:** 15-5 ships the routes/RPCs for weekly offs (`GET/PUT /attendance/weekly-offs`, `…/overrides`) and holidays (`GET/POST/PATCH/DELETE …/holidays`, `…/holidays/impact`) but the Owner has no UI to read or change any of them. The 15-8 setup wizard's Weekly-off and Holidays steps need write surfaces, and FR-18/19/20 demand they also be reachable outside the wizard ("any time", per the story AC). The Owner also needs the FE mirror of `ATTENDANCE_NOTIFICATION_EVENT_REGISTRY` (15-5 backend established this as the source of truth — 15-6 inherits it).

**Approach:** Two owner-only settings screens under `src/features/attendance/settings/`, both routed via a small **Attendance Settings landing page** on Attendance Home (per user direction 2026-09-27 — IA-aligned, not wizard-deep-link only):

- **Weekly off screen** — 7 day pills (Mon–Sun, the 15-5 ISO 1..7 vocabulary, Sunday preselected on first open), inline helper text, "Save" CTA gated on changes + non-zero-working-days. The per-employee override list sits below the default and uses the existing `TechnicianPicker`-style row shape; each row opens a sheet with the same day pills + an effective-date field + a destructive **Remove override** action.
- **Holidays screen** — Upcoming/Past grouped list, date-badge rows, single **+** FAB that opens a Sheet-based add/edit form (date + name). When the chosen date overlaps an employee's approved leave, the **impact preview** (`GET /attendance/holidays/impact?date=…`) renders an inline amber `InlineError`-style banner above the Save button naming the affected employees (per EXPERIENCE.md — informational, not blocking).

**Plus** a small `src/features/attendance/notifications/notificationEvents.ts` file mirroring the BE registry (15-5 established this as the FE side's source of truth for `attendance.*` event type strings — this story creates the FE mirror; later attendance/leave emitters extend it). And one new minimal **Attendance Home shim** (`src/features/attendance/home/AttendanceHomeScreen.tsx`) — two tiles ("Offices", "Settings") — added to MoreScreen between the existing Offices row and the rest. The shim is the future dashboard's placeholder; later stories extend it without breaking 15-6 (per the IA's `Attendance Home (Owner) ├─ …` tree, there is no real Home today — MoreScreen's "Offices" row was the only Attendance entry — so 15-6 builds the minimal shim that 15-8 and 19+ will fill in). The "Settings landing on Attendance Home" answer to the 2026-09-27 user question is therefore **"from the new Attendance Home shim"**, not from a pre-existing Home.

**Scope decisions locked with the user (2026-09-27):**
- **Both screens live in 15-6.** Splitting them would invent two specs and two PRs for a tightly-coupled settings surface.
- **Settings landing on Attendance Home** (not wizard-deep-link only). The IA diagram already lists Setup / Settings sub-items under Attendance Home; this matches it and makes the screens reachable "any time" per the story AC. 15-8 will deep-link into individual steps, not replace this landing.
- **Spec first, then implement.** Same workflow as 15-4 / 15-5.
- **First-open preselect = Sunday, visual-only.** UX-DR mirrors FR-18 ("default Sunday") as an FE visual preselection with `isDirty=false` (no DB seed — 15-5's locked decision). The pill row shows Sunday selected but Save is disabled until the user diverges; this avoids a `PUT [7]` that the BE would 422 on (FR-18's hard rule: at least one working day must remain).

## Boundaries & Constraints

**Always:**
- BE-first / FE-second cross-repo ordering — 15-5 is merged and pushed (`0c00c3f`). This story is fenzo-app only; no `fenzit-be` change.
- Design system tokens/components (`@theme`, `@components/ui`); relative imports (the codebase still uses relative paths, per the 2026-09-09 review's reality note — match the surrounding code).
- One screen per route, ~300-line file limit, sentence-case copy, no emoji, lucide icons at stroke 2 (the app's house style).
- **Day-picker pills (Mon..Sun):** each pill carries the visible single letter AND a full accessible label (UX-DR Accessibility Floor — "Sunday, selected" / "Monday, not selected"). Two pills sharing a visible letter (the two S's, the two T's) must never share an accessible label.
- **Effective-date field:** today by default, any future date, no past dates (the BE clamps silently — but FE must not even offer it; past is blocked at the date-picker). On a save, the field shows "Effective from {date}" inline copy, mirroring the Office-timing-change pattern from 15-4.
- **Gating:** Save buttons disabled until (a) `isDirty` (any pill changed from the canonical initial state — Sunday-only counts as dirty only if the user tapped a pill) AND (b) the day selection has at least one working day (FR-18's mirror: 7-day selection → Save disabled with inline rule) AND (c) for overrides, an employee is chosen AND (d) for holidays, name is non-empty after trim. Saving without `isDirty` is a no-op (Save is disabled).
- **Optimistic save:** one PUT per call (no batching). Success → re-fetch (GET revalidates the response, like `OfficesScreen`'s form) → transient success banner via `InlineNotice tone="success"` (auto-dismisses after ~1500ms). Failure → `InlineError` banner; the form stays populated so the user can retry. **No `Alert.alert` for success confirmations** — the codebase has no toast library and `Alert.alert` is a blocking modal (poor UX for "Saved!"). `Alert.alert` stays reserved for destructive confirms (Delete holiday, Remove override), matching OfficeFormScreen's archive pattern.
- **Holidays list grouping:** client-side split on `date >= today` (the BE response is ascending; group at render). Past rows render muted + read-only with a small "(past)" subtitle; they can still be tapped to edit name (per FR-20's "past dates can be edited/removed" rule). Empty upcoming / empty past = section header hidden, never a "no upcoming holidays" gap.
- **Date-badge holiday row:** square `44×44` surface, `radius.sm`, two lines (day number large, month abbreviation uppercase), weekday-colored past rows. Lucide `CalendarDays` or no icon on the row (the date badge IS the icon — matches mockup). Tap → edit sheet.
- **Add/Edit sheet:** `Sheet` from `@components/ui`, two fields (date, name) + the inline impact-warning banner. Save disabled until both fields valid. Edit pre-fills from the row.
- **Remove/Delete holiday:** destructive confirm dialog ("Delete this holiday?") — destructive-action pattern the app already uses (per EXPERIENCE.md → Office archive pattern).
- **Impact preview:** debounced 300ms after date selection in the add/edit sheet (matches `useAddressAutosuggest`'s 300ms); latest-wins abort (same pattern). Empty list → no banner. Non-empty list → amber banner naming up to 3 employees; if more, "{n-3}+ more employees" suffix (cap visible rows).
- **Override employee picker:** the existing `SelectTechniciansScreen` is multi-select with `maxSelected` **not in scope today** (verified during review — no `maxSelected` prop exists in `src/features/newJob/technicianPicker/`); 15-6 uses the **existing screen as-is, treated as multi-select where Apply gated on ≥1**. Because 15-6 only ever adds/edits ONE override at a time, the "Apply" path passes a single-element array to `setOverride(employeeId, { days })` after the screen returns. This avoids inventing a new picker and matches the established 11-8 picker behaviour; the trade-off (user has to know to tap just one) is acceptable for an owner-only power-user flow.
- **Routing:** all five new routes registered in `src/navigation/types.ts` + `RootNavigator` (owner stack). Entry points: MoreScreen → Attendance Home (the shim) → Settings tile → Settings landing → Weekly off / Holidays. Plus the deep-link-friendly individual routes so 15-8's wizard can push directly.
- **Notification event registry mirror:** `src/features/attendance/notifications/notificationEvents.ts` mirrors `ATTENDANCE_NOTIFICATION_EVENT_REGISTRY` from BE (event strings + payload field names + dedupe-key shape), typed as the BE side is typed. No new UI surface consumes it in 15-6; this is the FE registry file 16+ will extend.
- **Sunday preselection behaviour:** on first open (no default row exists), Sunday is visually preselected BUT `isDirty=false` until the user taps a pill. Save is disabled while `!isDirty`. This way the FR-18 default is shown without sending a `[7]` write that the BE would 422 on. The dirty flag flips when the effective day selection **diverges** from the loaded canonical (a tap-then-untap-Sunday returns to the canonical and Save stays disabled). On every subsequent open, `isDirty` initialises from the loaded `default.days` and Save is disabled until the user diverges.

**Ask First:**
- None remaining — the `SelectTechniciansScreen` reuse decision is locked above; the holidays-list icon question is settled (no icon, the date badge is the visual signal — matches the mockup exactly).

**Never:**
- No seed/preset holidays list (FR-20 explicitly out of scope).
- No recurrence (out of scope).
- No per-employee holidays (out of scope).
- No test written before the user confirms the screens work on device (test-timing rule).
- No Nominatim / map / geocoding here — pure settings screens.
- No employee onboarding/enrolment here — that's 15-7/15-9/15-10.
- No service-role key on the FE.
- No bypass of the BE tenant-lock. The server's per-tenant "today" (`attendance_today`) is **mirrored, not read** — no attendance endpoint returns that date (see Spec Change Log 4) — so both screens take it from `useIstToday()`, which holds the IST calendar day and re-checks it as the clock moves. IST is exact for every tenant that can exist today: `tenants.timezone` defaults to `Asia/Kolkata` and nothing in the product writes it. What must never happen is the device's own local date deciding the grouping or the date floor.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Owner opens Weekly off, never configured | GET 200 `{ default: null, next: null, history: [] }` | Empty-state copy "No weekly off set yet"; day pills render with **Sunday visually preselected BUT `isDirty=false`**; Save disabled until the user touches a pill | — |
| Owner taps Save on first open without changes | Save still disabled (no dirty) | No request sent | — |
| Owner saves tenant default = Saturday + Sunday, no `effectiveFrom` | day pills `[6,7]`, today is the effective | PUT → 200; pill set updates from `[6,7]`; transient `InlineNotice tone="success"` "Weekly off saved" auto-dismisses after ~1500ms | 422 `ATTENDANCE_NO_WORKING_DAYS` if every pill is selected → Save disabled client-side, never sent |
| Owner selects all 7 days | day pills `[1..7]` | Save disabled inline (FR-18's mirror); helper text turns into the inline rule | No request sent |
| Owner picks a future `effectiveFrom` | `effectiveFrom = today+7` | PUT; success banner; row shows "Effective from {date}" | 422 `VALIDATION_ERROR` on bad date → inline field error |
| Owner opens an override row | GET overrides → employee row tapped | Bottom sheet opens with that employee's current selection, day pills pre-checked, Remove override button visible | — |
| Owner saves override = Friday only | PUT `/overrides/:employeeId` `{ days: [5] }` | Sheet closes; row subtitle updates ("Friday only"); transient success banner | 404 `ATTENDANCE_EMPLOYEE_NOT_FOUND` → sheet shows inline error, employee picker re-enabled |
| Owner taps "Remove override" | confirm → DELETE `/overrides/:employeeId` | Sheet closes; row removed from list (falls back to tenant default from today); transient success banner | 404 → inline error, sheet stays open |
| Owner opens Holidays | GET 200 list | Upcoming / Past groups; date-badge rows; past rows muted + tap-to-edit allowed | Empty list → EmptyState "No holidays yet" + FAB |
| Owner taps + FAB | empty sheet opens with today preselected | Impact preview fires; banner if affected employees | — |
| Owner picks a future date, no approved leave | impact returns `[]` | No banner; Save enabled when name has content | — |
| Owner picks a date overlapping approved leave | impact returns `[{ "Priya" }, { "Ramesh" }, …]` (pre-15-7 = empty list) | Amber banner "This date overlaps Priya, Ramesh, +2 more employees' approved leave. It will no longer count as leave for them."; Save still enabled (informational) | — |
| Owner taps a holiday row (past) | muted row tapped | Edit sheet opens with date read-only display + name editable + Save | — |
| Owner renames a future holiday | PATCH name | Sheet closes; list refreshes | 404 `ATTENDANCE_HOLIDAY_NOT_FOUND` → inline error |
| Owner deletes a holiday | destructive confirm dialog → DELETE | List refreshes; transient success banner; if future date, the BE emits `attendance.holiday_removed` notifications (no UI surface in 15-6) | 404 → inline banner; item stays |
| Owner adds a holiday on a taken date | POST 409 | Sheet shows inline "A holiday already exists on this date"; date field highlighted | — |
| Save fails on network drop | any PUT/POST/PATCH/DELETE | Inline error banner; sheet stays open; form state preserved | — |
| Technician JWT hits any new screen | JWT role ≠ owner | Navigation guard blocks (mirror the OfficesScreen gating — 15-4 added `@Roles(Role.OWNER)` server-side; FE never navigates a tech to these routes, but the apiClient 403 path also covered) | — |
| Date picker past dates | user opens calendar | Past dates are not selectable — the date picker only allows `>= today` for new holidays (matches BE semantics); for edit, the date is displayed read-only | — |
| **Day rolls over while a settings screen is open** | screen left mounted at 23:59 IST; the clock crosses IST midnight with no user action | The new day takes effect with no user action: the holiday list re-groups (a holiday that has just become past moves from Upcoming to Past) and the weekly-off effective-date floor + "upcoming changes" cut-off advance. Also holds when the app was backgrounded rather than the screen left focused (RN stalls timers; the resume re-syncs) | — |

## Design Notes

- **Day pills visual** — match the mockup exactly: single-letter glyph, `radius.pill`, selected = `colors.primary` fill + white text, unselected = `colors.surfaceCard` + `colors.textStrong`. Past-disabled (FR-18's mirror) = `colors.textMuted` + no fill. Each pill is exactly `touch.min` (44px) tall (UX-DR — every other control in this module meets the 44px floor; the calendar cells are the only stated exception).
- **Override rows** — reuse the `TechnicianPicker` row shape (avatar circle + name + chevron + subtitle showing the override days like "Friday only"). Remove override sits inside the bottom sheet, not on the row directly (destructive actions live behind a confirm, per the app's destructive-action pattern).
- **Holidays date-badge** — `44×44` square, `radius.sm`, two lines (day number large + month abbreviation uppercase). Past rows: `opacity: 0.6` and a "(past)" subtitle. The "+" FAB lives bottom-right (matches the mockup).
- **Impact banner** — amber, not red — this is information, not a failure (EXPERIENCE.md explicitly). `InlineError` is red-only (verified: hard-coded to `colors.status.cancelled.*`), so a new `InlineNotice` component is added in `src/components/ui/` (~80 lines, three tones: `info`/amber, `success`/green, `neutral`/gray — lucide `Info`/`CheckCircle2`/`Info` icons, optional dismiss). Impact banner uses `tone="info"`; transient success feedback uses `tone="success"`. The component is reusable for future attendance/leave stories (16/17/19) so it's not throwaway.
- **Effective-date helper copy** — "Effective from today" (default) or "Effective from {date}" (future). Mirrors the office-rule-edit pattern from 15-4.
- **Empty / loading / error states** — match the OfficesScreen patterns: spinner only on first load, list+InlineError on background refresh failure, EmptyState with the matching action CTA on truly-empty.
- **Accessibility floor** — every pill carries a full accessible label independent of its glyph (UX-DR). The two S's and two T's must have distinct labels. Day-of-week labels are localised via the same Intl date formatter the app already uses (`Intl.DateTimeFormat(locale, { weekday: 'long' })`).

## Spec Change Log

Amendments made after the 2026-09-27 sign-off, each with its reason. The Intent, Boundaries, Matrix and Acceptance Criteria above are otherwise unchanged.

1. **2026-09-27 — effective-date input is a DS `Calendar` + `DatePickerField`, not a local `EffectiveDateField` (user-approved).** The story was first implemented with a plain `YYYY-MM-DD` text input, which made the Owner hand-type a date and offered no way to see or avoid past dates beyond a validation error. It was replaced mid-story with `Calendar` (new pure-JS dep `react-native-ui-datepicker@3.3.0`) plus `DatePickerField`, so past dates are unselectable rather than merely rejected, and the picker is reusable by every later attendance/leave date surface (16–19). The dependency is pure JS — no native code, no rebuild needed, New-Architecture safe. This supersedes the earlier "no new date-picker dependency" note. The three write surfaces consume `DatePickerField`; `EffectiveDateField.tsx` and the interim `DatePickerSheet.tsx` are deleted.

2. **2026-09-27 — the three fetch hooks must carry the 15-4 latest-wins sequence guard (user-approved).** `useWeeklyOffs`, `useWeeklyOffOverrides` and `useHolidays` were first written without the guard that `useOffices` adopted in the 15-4 review, so a slow earlier refetch could overwrite a newer one's rows or error. The tests already written for this were correct; the hooks are fixed to match, rather than the tests being relaxed.

3. **2026-09-27 — the device walkthrough was confirmed before tests were written,** satisfying the test-timing rule ("implement feature → user confirms it works → write tests → review"). The tests therefore cover already-working behaviour; a failure now is a real defect or a broken test, not a feature gap — with the two exceptions recorded above, which are genuine implementation gaps the tests caught.

4. **2026-09-27 — "today" is the IST calendar day, mirrored live; the server's own date is a recorded deferral (user-approved).** Two changes to how the day is sourced:

   **(a) Mirrored, not read.** The Holidays AC reads "today's date from the server, NOT client-local" and the Boundaries section claimed it "arrives via `apiClient` correlation". Neither is literally true: no attendance endpoint returns the server's date — `GET …/holidays` returns only `{ id, date, name }`, and the endpoints that *use* the server's today (`GET …/offices` → `{ rule, nextRule }`, the weekly-off `default`) report the rule that applies, not the date they applied it on. Making it literal means a cross-repo change (a `today` field on an attendance GET, or a tenant-context endpoint) that buys nothing observable today, because `tenants.timezone` defaults to `Asia/Kolkata` and **nothing in the product writes it** — a grep of `fenzit-be/src` finds `timezone` only inside two `attendance_today` docblocks. So the FE mirrors the server on the product's home timezone (`istTodayDate()`), which is exact for every tenant that can exist today, and the literal server value is **deferred** with a named trigger (whichever story first lets a tenant set its timezone) in `deferred-work.md`. The substance of the AC is unchanged and still enforced: the device's own local date never decides the grouping or the date floor.

   **(b) Live, not a mount-time snapshot.** `istTodayDate()` was called once through `useMemo(…, [])` in both screens, so a screen left open across IST midnight kept yesterday's date for its whole mounted life: a holiday that had just become past stayed under "Upcoming", and the date pickers kept yesterday's floor and default. Both screens now take the day from a new `useIstToday()` hook, which re-checks on a 60s tick and on resume from background (RN stalls timers while backgrounded), and is a no-op on a tick that crosses no midnight. A new matrix row pins the behaviour and `src/hooks/useIstToday.test.tsx` covers it.

5. **2026-09-27 — the three review fixes the user approved are in and test-pinned.** All three came out of the same review pass and each changes observable behaviour, so each has its own test rather than being left implied:

   **(a) The holiday date floor is dropped (FR-20 back-dating).** The add form passed `minDate={today}` to the calendar, which disabled every past cell — so a holiday could not be back-dated even though FR-20 asks for add/edit/remove "incl. past", `CreateHolidayDto` says "Past dates allowed (statuses recompute on read)", and api-contracts.md §holidays says "Past dates are allowed and silent". A UI floor was blocking a backend-supported, spec-required capability. Removed; the picker now offers past dates and the POST carries the date unchanged. The weekly-off floor is **deliberately kept** (the BE clamps it with `greatest()`, so a past date there would be silently rewritten) — `WeeklyOffScreen.test.tsx` pins that asymmetry so a future "no floor" sweep cannot strip it too.

   **(b) The section labels are the DS `Eyebrow`.** The four hand-rolled label `Text`s ("Upcoming"/"Past", "Tenant default"/"Upcoming changes", "Per-employee overrides") used `typography.bodySm` with a local uppercase transform, and only the Holidays pair uppercased. This is not a casing preference: `Eyebrow` carries `typography.eyebrow` (the design system's one allowed caps use) **and** `accessibilityRole="header"`, which none of the copies had, so a screen-reader user could not jump between sections. All four now render `Eyebrow`; the dead local styles are deleted and `HolidaysScreen.test.tsx` asserts the header role.

   **(c) The ≤3 impact banner reads as a group possessive.** The branch joined names with a bare comma list, so three affected employees rendered "Ann, Ben, Cara's approved leave" — the possessive hung off the last name only, reading as Cara's alone. It now joins as "Ann, Ben and Cara's approved leave" via an exported `joinEmployeeNames` helper. The `>3` branch (spec-pinned: "names up to 3 plus `+{n-3} more employees'`") is untouched. 1- and 2-name boundaries are covered ("Ann's", "Ann and Ben's") so the conjunction never dangles.

6. **2026-09-27 — two build-time deviations from the task list, both recorded rather than silently ticked (no behaviour change).** Neither was a review finding; both are places where the build settled on a better fit than the spec's draft and the task text was left stale.

   **(a) `WeeklyOffOverrideSheet` is a component, not a route.** The Code Map and the navigation task originally listed `WeeklyOffOverrideSheet: { employeeId: string }` among the new routes. It was built instead as a DS `Sheet` rendered in-screen by `WeeklyOffScreen`, because the override flow needs to *return* an employee id from the shared `SelectTechniciansScreen` picker — so `AttendanceWeeklyOff` takes `selectedTechnicianId` as a route param and the sheet opens over the screen that owns the list. No route of that name exists and none is needed.

   **(b) The override picker's employees come from `useMyProfile`, not a new `useEmployeesForOverride`.** Task 128 named a wrapper over `getTechnicians`. `useMyProfile().profile.technicians` is already hydrated into the shared store (the same store the profile screens read), so sourcing from it adds no request and cannot disagree with the rest of the app. There is no `useEmployeesForOverride` file and none is needed.

7. **2026-09-27 — review decision: the Holidays FAB stays hidden in the empty state; the EmptyState CTA is the add path (user-approved).** The matrix row read "EmptyState 'No holidays yet' + FAB", but the shipped screen hides the FAB while the list is empty and the EmptyState's own "Add holiday" CTA is the single add path — one obvious action on an empty screen rather than two competing ones. The matrix's literal wording is corrected by this entry rather than by adding a redundant FAB.

8. **2026-09-27 — review decision: the technician nav guard is deferred to a dedicated story; the AC's wording is corrected to match.** The AC originally promised "none of the new screens are reachable" with a technician JWT via a FE nav gate. No FE role-gating pattern exists anywhere in the app and 15-4's Attendance row on MoreScreen is equally ungated, so a dedicated nav-guard story owns the gate (and surfacing 403s as permission errors rather than connection errors); see deferred-work.md. The substance the BE already enforces — a technician can read or write nothing (owner-only role guard 403s every attendance endpoint) — is unchanged.

9. **2026-09-27 — the MoreScreen "Offices" row was renamed "Attendance" (review-recorded deviation from the task text).** The task text named the settings surfaces but did not record that 15-6 repurposes the existing MoreScreen row label from "Offices" to "Attendance" (it now routes to the AttendanceHome landing, which links to both the offices and the new settings surfaces). Recorded here rather than silently ticked; the offices flow remains reachable from the Attendance home screen.

10. **2026-09-27 — three review-iteration-1 behaviour records (recorded, not changed; the shipped behaviour is the decision).**

   **(a) The impact preview never runs in edit mode.** The spec's interaction text said the debounced impact preview runs "in the add/edit sheet", but the shipped `HolidayFormSheet` runs it in ADD mode only (`active={visible && !isEdit}`): the date is immutable on PATCH (15-5), so an edit can never introduce a NEW overlapped date — the warning would be about a date nobody can change, pinned to the sheet forever. If a future story makes dates mutable, the preview comes back with it.

   **(b) Override rows open the sheet only via the Edit button, not row-tap.** The spec's interaction text described override rows as tappable ("each row opens a sheet"); the shipped `WeeklyOffOverridesSection` rows open the sheet only through the row's explicit **Edit** button. The row's tap affordance stays free for future per-row actions, and the Edit button gives the destructive-adjacent flow one obvious entry point.

   **(c) The Upcoming-changes panel is read-only by decision (2026-09-27).** The default block's "Upcoming changes" rows and the per-employee override rows' "From {date}: {days}" lines are display-only: cancellation or change of a scheduled edit is done by SAVING a new edit over it (the AD-8 algorithm clips/replaces the scheduled range), not by tapping the row. No edit affordance is planned for the panel itself.
