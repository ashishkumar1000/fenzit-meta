## Intent

**Problem:** FR-2/FR-6's ongoing owner surface does not exist. The wizard's Employees step (15-8) is enrolment-lite by design — enable with today's date only, no start-date picker, no reassignment, no way to change or cancel a future start — and it is unreachable once setup completes (the entry gate bounces completed tenants to `AttendanceHome`). The backend has shipped everything since 15-7 (deployed 2026-09-28): `PUT /attendance/enrolments/:employeeId` accepts `startDate` (today default, past clamped, "changes / re-states a future start date"), `PUT /attendance/enrolments/:employeeId/office` reassigns with `effectiveFrom` (FR-6), and `DELETE` cancels a future start outright ("removes the rows entirely"). None of it is consumed: an owner cannot future-date a new joiner (FR-2's "1 Nov" example), cannot move anyone between offices, and cannot adjust a future start after the wizard is done. UX-DR9's start-date contract ("defaults to today; picking a future date is one tap away") is half-shipped.

**Approach:** One new root-stack route `AttendanceEnrolments` in fenzo-app — the roster screen (every tenant technician, the same `GET /attendance/enrolments` rows the wizard reads), entered from a third tile on `AttendanceSettings` ("Team enrolment"). Per row: the 15-8 row style (Card, name, sub-line, `Switch` with accessible label) extended with the full UX-DR9 contract — an enable start-date affordance defaulting to today with one-tap expansion into the shared `DatePickerField` calendar; toggle-on-without-office still opens the office picker inline with the switch uncommitted (15-8 behaviour, unchanged); reassignment via an office sheet with an effective-date field; change/cancel of a future start. The `useEnrolments` hook and `OfficePickerSheet` move out of `setup/` into a new `enrolments/` feature folder (the roster screen is their primary owner now; the wizard becomes a consumer) and the hook gains `startDate` on enable and a `reassign` action. Raw-truth rule carried over unchanged from 15-8: per-employee state derives from the UNGATED fields (`attendanceStartDate`, live `officeId`) via `enrolmentCoversToday` — never the TENANT-module `attendanceEnabled` flag. No backend change — the BE is deployed; FE-only story.

**Scope decisions (proposed 2026-09-28 — pending user sign-off; frozen after approval):**
- **Spec first, then implement** — this file, reviewed by the user, precedes any code (15-5/15-7/15-8 precedent).
- **Entry from `AttendanceSettings` only** — a third tile beside Weekly off and Holidays. `AttendanceHome`'s shim keeps its two tiles (no redesign — 15-8's Never), MoreScreen stays dumb, and the wizard's Employees step is untouched behaviourally (it remains the guided first-run path; this screen is the ongoing-management path). Reachable regardless of setup state: enrolment writes are owner-only and the server does not gate them on setup completion (the wizard itself enrolls mid-setup); a pre-setup visit through a settings deep link is harmless and sometimes useful (adjusting the wizard's today-dated enrolments).
- **No "enable all" control (user-approved 2026-09-28)** — the epic intent's "bulk-enable" is served by per-row toggles exactly as its ACs describe; the only sanctioned bulk mechanism is an FE loop over the single-employee PUT (api-contracts), which multiplies per-row failure states for a convenience no AC asks for. Recorded in deferred-work as a candidate if the pain shows.
- **Enable fast path stays one-tap** — toggle on with an office already assignable and the start affordance untouched → PUT with `startDate` omitted (server default today), the same commit-on-pick flow the wizard ships. The start affordance is a PRE-PICK chip on not-yet-enrolled rows: "Starts today" → tap expands the `DatePickerField` calendar → a chosen future date relabels the chip ("Starts 1 Nov") and is carried on the next toggle-on PUT. Untouched = today = omitted param (AC 2 verbatim).
- **Upcoming rows can restate or cancel their start** — a row with `attendanceStartDate > today` shows "Starts {date}" with its switch DISABLED (the bare fast-path enable would silently cancel the future start — the server deletes future periods when `startDate` clamps to today). Controls: the start chip PUTs `{officeId, startDate}` as an explicit restatement (picking today deliberately pulls the start forward; the pick IS the confirmation — the row's date is already server truth, so this is an edit of an existing value, not a compose), and "Cancel start" DELETEs, removing the future rows outright (row returns to never-enrolled). Cancelling keeps plain copy ("Cancel the {date} start"), one tap — the same stakes as the wizard's toggle-off.
- **Reassignment is a sheet with an effective date** — "Change office" on any enrolled row (covering or upcoming) opens a reassign sheet: live-office rows (15-8 picker pattern) plus an effective-date `DatePickerField` and an explicit confirm button ("Move to {office}"). Defaults: covering rows → today (`minDate = today`, FR-6 "from the date it's made, or a future date"); upcoming rows → their `attendanceStartDate` (`minDate = attendanceStartDate` — the only in-enrolment dates; a later date is a legitimate scheduled move). Cancel at any point writes nothing. `effectiveFrom` is sent explicitly always (never omitted) so the wire shows what the owner saw.
- **A future-dated move is visible until it takes effect** — after a future reassignment the GET cannot show it (the view carries only the assignment covering today / the next period's start), so an unacknowledged move looks like a no-op and invites re-taps. The row renders a one-line note "Moves to {office} from {date}" from the confirmed write. The note is hook state — it lives for the screen mount (a remount loses it; it is a transient acknowledgement, not a record) — and clears the moment any of these holds: a refetch shows the move's office covering today (it took effect); the row stops being enrolled; the move's date has arrived but the row shows a different office (`move.date <= today && row.officeId !== move.officeId` — the move was undone by a disable/re-enable elsewhere); or a newer write supersedes it. Client-known intent, server-cleared — never merged into the row's server-truth fields, never persisted (no MMKV).
- **The checked-in-today reassign AC ships with Epic 16** — the epic's third AC ("already checked in today → prefill tomorrow, today disabled") has no implementable signal: `attendance_records` does not exist until Epic 16 and no endpoint exposes "checked in today". The server already owns the behaviour (15-7: the reassignment "applies from tomorrow automatically once attendance_records exists and the employee has checked in today"), so the FE flow stays correct when the data arrives; the prefill/note UI is recorded in deferred-work for Epic 16. The AC is deferred, not satisfiable today (user-approved 2026-09-28).
- **A backend pre-patch ships FIRST (user-approved 2026-09-28, backend-first)** — the adversarial spec review found the shipped `attendance_access_state` view anchoring the office join at the enrolment's period start, so after ANY reassignment every read (owner roster, `me/access`, `/users/me`) kept reporting the OLD office forever — breaking this story's reassignment AC and, in Epic 16, handing check-in the wrong office radius. The pre-patch (migration `20260928000001`, reassignment regression test in the real-DB integration suite, `scripts/probe-15-9-view-fix.ts` live probe, api-contracts anchor note) shipped before any FE work: fenzit-be `7db6e03`, migration applied via MCP, verified red/green (old view fails the new test at exactly the reassignment assertion) and green over local HTTP (10-step probe). The FE below is specced against the FIXED view.
- **Upcoming rows have no bare fast-path enable (review finding: a silent cancel)** — the server clamps an omitted/past `startDate` to today and deletes future periods (AD-8), so a bare toggle-on on an upcoming row would silently cancel their future start. On the roster screen the switch is DISABLED on upcoming rows (a11y hint: "Starts {date}"); their controls are the start chip (restates the date — picking today deliberately pulls the start forward) and an explicit "Cancel start" action (DELETE → rows removed → never-enrolled). The wizard's Employees step gets the same guard: its switch disables on upcoming rows with the hint (~3 lines + test — the one approved touch to 15-8 code; it prevents a data-destroying accident, it adds no feature).
- **The enrolment pieces move out of `setup/`** — `useEnrolments` (+ test) and `OfficePickerSheet` relocate to `src/features/attendance/enrolments/`; `wizardModel.enrolmentCoversToday` re-exports from the new `enrolmentsModel` (one-line re-export, no behaviour change, wizard tests untouched). Moved-file diffs are import-only EXCEPT the explicitly approved copy-prop on the picker (its empty-office copy says "step", wizard-speak on the roster) and the EmployeesStep guard above.
- **No further BE changes** — the pre-patch above was found and approved at spec time; if device verification exposes another backend defect or a deploy gap, that is a separate fenzit-be decision (backend-first rule; HALT and confirm).

A pre-picked chip is revalidated against `istTodayDate` at render AND at write time — a chip left mounted across IST midnight that is now in the past degrades to "Starts today" and the PUT omits the param (the server would clamp silently, and the chip must not claim a date the wire didn't send). `DatePickerField`/`Calendar` DS components only — no new date UI.

**Acceptance Criteria:**

- Given the start-date affordance on an enrolment row, when left untouched it reads "Starts today" and the enable PUT omits `startDate`; when the owner expands it and picks a future date, the PUT carries that date and the row shows the upcoming start (UX-DR9 / epic AC 2 / FR-2).
- Given an enrolled employee, when the owner reassigns their office with an effective date, then the PUT `/office` carries that date explicitly, the row updates from the post-write merge, and a future-dated move shows "Moves to {office} from {date}" until server truth catches up (FR-6).
- Given an upcoming (future-dated) enrolment, when the owner changes its start date or toggles it off, then the start is re-stated via enable-PUT or cancelled outright via DELETE, per the contract.
- Given any per-row write failure (404/409/422/network), when it happens, then the row shows its own banner, keeps its pre-write server state, and the documented recovery branch (refetch / offices refresh) runs.
- Given all previously green suites run after the change, then every one stays green and `tsc` is clean (additive FE story; the only pre-existing-code diffs are the approved mechanical moves/re-exports, the picker copy prop, and the wizard's upcoming-row switch guard).

## Design Notes

**Why a separate roster screen instead of extending the wizard step:** the wizard is a first-run, forward-only, server-marker flow; roster management is ongoing and stateless about progress. 15-8 explicitly deferred "the full roster UX (reassignment, start dates, bulk conveniences, UX-DR9's complete contract)" to this story — extending the step would couple a guided flow to everyday management and re-open its frozen gates. Both surfaces share the hook and the picker, so the raw-truth and merge rules have one implementation.

**Why the moved hook lives in `enrolments/` and not `setup/`:** ownership follows the primary consumer. The wizard borrows the roster for step 5; the settings screen is the roster's home. The move is mechanical (import-only diffs, tests travel) and prevents the roster feature from reaching into the wizard's folder — the same fix-placement logic the project applies to bug fixes, applied to features.

**Why the start chip is a pre-pick instead of a compose-then-confirm enable:** the common case (enable today, office known) must stay one tap — it is the flow device-validated in 15-8. A compose state would add a confirm step to every enable to serve the rare future-dated one. The chip inverts it: the rare case pre-picks its date, the common case ignores the chip entirely, and UX-DR9's "one tap away" is literal.

**Why the reassign sheet confirms explicitly while enable commits on pick:** enable-with-today is idempotent-ish and self-explanatory (the switch says what happens); a reassignment silently changes where people check in from a chosen date — FR-6's "Thane from 1 Nov" needs the date and the target visible together before committing. Same reason `effectiveFrom` is always sent: the wire records exactly what the owner confirmed.

**Why the scheduled-move note is client-held and server-cleared:** the roster GET structurally cannot carry future assignments (the view exposes the LIVE covering assignment only), so acknowledgement cannot come from the payload the normal way. Holding the note as ephemeral client intent — cleared the moment server truth can express it — avoids a second source of truth (no MMKV) while keeping FR-6's future move from looking like a no-op.

**Why no checked-in-today prefill now:** FR-6's "applies from tomorrow after a check-in" activates when `attendance_records` exists (Epic 16). The 15-7 server already owns the adjustment; a FE prefill keyed to data no endpoint exposes would be dead code guessing at Epic 16's shapes. Deferred with a pointer, not approximated.
