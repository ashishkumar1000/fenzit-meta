## Intent

**Problem:** FR-1's owner-side flow does not exist in the app. The backend shipped everything the wizard needs — `/attendance/setup` resume/start/step-marker/complete (15-2, `attendance_setup_progress`), offices + rules (15-3/15-4), weekly-offs/holidays (15-5/15-6), and the enrolments roster + lifecycle (15-7, deployed 2026-09-28) — but nothing consumes the setup routes, so the module can never be switched on from the app: `attendance_settings.enabled` only becomes true inside `attendance_complete_setup`, which only the wizard's final action calls. The standalone screens (Offices, Weekly off, Holidays) are reachable as settings but there is no guided first-run, no resume, and no client-side mirror of the completion gates. Also blocking the wizard's Weekly-off step: the 15-6 add-mode override-sheet bug (a Sunday-only override can never be saved — the add-mode sheet's baseline is the default day-set (e.g. `[SUNDAY]`), toggle-off→on restores that baseline, and `saveDisabled` requires dirty-vs-baseline, so a deliberate set equal to the default is unsavable; reported on device 2026-09-28, contradicts the spec-15-6 review decision that was never test-pinned).

**Approach:** One new root-stack route `AttendanceSetupWizard` in fenzo-app — an `AuthFlow`-style component state machine over the fixed five-step vocabulary (`offices → timings → weekly_off → holidays → employees`, UX-DR6), `StepIndicator {current,total}` chrome per step. Steps 1–4 push the existing deep-linkable routes for editing (the 15-4/15-6 screens were built for exactly this — "wizard deep-links (15-8) bypass this and push the individual routes directly") and render server-truth summaries in-step; step 5 is a new enrolment-lite Employees step over `GET/PUT/DELETE /attendance/enrolments`. Resuming reads `GET /attendance/setup` (`currentStep`); each Continue persists the step marker via `PATCH /attendance/setup` after the step's own data is already saved; Holidays shows "Skip for now" (marker advances, no data — 15-2 made skipping a FE concern). The final "Enable attendance" action calls `POST /attendance/setup/complete` and stays disabled client-side until the server gates are met 1:1 (≥1 live office AND ≥1 employee enrolled with a live office whose enrolment covers today). The entry gate lives in `AttendanceHome`: on focus, setup not completed → `replace` to the wizard (FR-3 owner side: the tile opens the wizard, not an empty dashboard). No backend change — the BE is deployed; FE-only story.

**Scope decisions (proposed 2026-09-28 — pending user sign-off; frozen after approval):**
- **Spec first, then implement** — this file, reviewed by the user, precedes any code (15-5/15-7 precedent).
- **Entry gate lives in AttendanceHome, not MoreScreen** — the More "Attendance" row keeps navigating to `AttendanceHome` (unchanged); `AttendanceHome` checks setup state on focus and `replace`es to the wizard only on an affirmative 200 with `started && setupCompletedAt == null`. The gate covers the Attendance entry point (tile and deep links landing on AttendanceHome); a direct deep link to a settings route pre-setup bypasses the wizard harmlessly (writes persist; resume is unaffected). A non-owner 403 on the gate GET renders the shim exactly as today (no redirect — a technician must never be pushed into an owner wizard that 403s on every call; the full nav-guard stays with the 15-6 D1 deferral story). MoreScreen stays dumb, and the existing `goBackSafely` comments already anticipate wizard deep links.
- **In-session Back steps backward through the wizard** — a Back control moves to the previous step (data persists server-side and the marker only advances on Continue, so backward movement loses nothing and violates nothing — the "no re-entry of earlier steps" AC governs resume, not in-session navigation; EXPERIENCE's "forward-only with a back option" reads exactly this way). Device back exits the wizard via `goBackSafely` (resume lands on the marker step).
- **Steps 1–4 reuse the shipped routes via push; no new editing UI** — the wizard step shows a summary (offices with their current rule; the saved default weekly-off; upcoming holidays count) + Continue, and pushes `AttendanceOffices`/`OfficeForm`/`AttendanceWeeklyOff`/`AttendanceHolidays` for any editing. Those screens already own loading/error/save handling; the wizard owns progress only.
- **"Timings & hours" (step 2) is a review step** — an office is created WITH its rules (15-3 shape: the office carries `rule`; OfficeForm collects rules inline with defaults radius 100 m / cut-off 15 min / 8 h / 4 h), so by step 2 every live office already has a rule. The step lists each office's current rule (start–end, cut-off, hours) and pushes `OfficeForm` (edit) per row; Continue is enabled when ≥1 live office exists and every live office has a `rule` (always true post-create — a gate against future drift, not busywork).
- **Employees step is enrolment-lite** — roster source is `GET /attendance/enrolments` (verified: it returns EVERY tenant technician joined with access state — `enrolments.service.ts` `listEnrolments` reads `users` role=technician then the view; "empty until anyone is enrolled" in api-contracts means the access-state rows, not the roster — the contract doc's prose is known-wrong, recorded for a BE-docs fix, not this story). Per row: a required office pick + an enable toggle. Toggling on without an office opens the office picker inline immediately and the switch does not commit until an office is chosen (UX-DR9 spirit); the PUT then uses the server-default start date (today). The picker and the completion gate count only live offices (`archivedAt == null`). Future start-date pickers, reassignment, and any bulk-enable control are 15-9's roster UI, not this step.
- **The step marker is PATCHed on Continue only, after the step's data is persisted** — in-step edits persist through the pushed screens' own saves; the marker is the resume pointer, not a save mechanism. PATCH failure → inline retry banner on the step, wizard does not advance, nothing entered is lost (AC-4).
- **Client-side completion gate mirrors the server 1:1** — "Enable attendance" disabled until (≥1 live office) AND (≥1 roster row with `attendanceEnabled && officeId && the enrolment covers today`, i.e. `attendanceStartDate == null || attendanceStartDate <= today` — the server's Gate 2 requires an enrolment range covering today plus a live covering assignment, so a future-dated row must not satisfy the mirror; the wizard itself only writes today-dated enrolments, but the gate must not silently break if one appears). The server's 422 `ATTENDANCE_SETUP_INCOMPLETE` remains the authority for races (banner + refetch, never a fake success).
- **Step 3 (Weekly off) is not skippable** — Continue is enabled only once a default weekly-off is actually saved server-side (the canonical GET result after a save — not the visual-only Sunday preselection that `useWeeklyOffDefaultForm` shows before any interaction), matching EXPERIENCE's rule that Holidays is the only skippable step.
- **The 15-6 add-mode override bug is fixed in this story** — it blocks the wizard's Weekly-off step. Semantics, split by mode: **add mode** — Save is enabled once the owner has touched the day set and the set is a valid override (not all seven days), even when it equals the default day-set (honours the spec-15-6 review decision "toggle off and back on enables Save", which shipped without its test); **edit mode** — unchanged dirty-vs-current-saved-rule semantics (a no-op toggle must not re-PUT). The fix lands in `weeklyOffModel`/`WeeklyOffOverrideSheet` with pinning tests for both modes. The three cosmetic nits reported alongside (edit-holiday helper text show-through, premature "Name is required.", technician-picker copy in the weekly-off context) are recorded in `deferred-work.md`, not here.
- **No BE changes** — if device verification exposes a backend defect or a deploy gap, that is a separate fenzit-be decision (backend-first rule; HALT and confirm).

Screens never touch `apiClient` directly; ATTENDANCE_* codes branched explicitly (`ATTENDANCE_SETUP_NOT_STARTED/ALREADY_COMPLETED/INCOMPLETE`, `ATTENDANCE_TENANT_NOT_FOUND`, `ATTENDANCE_EMPLOYEE_NOT_FOUND`, `ATTENDANCE_OFFICE_NOT_FOUND`, `ATTENDANCE_OFFICE_ARCHIVED`, `ATTENDANCE_ASSIGNMENT_GAP`).

- A11y floor: preserve `StepIndicator`'s shipped accessible "Step X of Y" labelling through any re-shell; the enable toggle, office picker and "Enable attendance" carry distinct accessible labels; DS tokens only (no hard-coded colours); plain-business-English copy throughout.

## Design Notes

**Why the entry gate is in AttendanceHome (not MoreScreen):** FR-3 says the owner's entry point opens the wizard before setup; the tile, deep links and back-stack all land on `AttendanceHome`, so gating there covers every path with one check and keeps MoreScreen free of attendance logic. The check is one light GET per focus, consistent with the attendance screens' focus-refetch contract. The pre-existing shim screens (Offices/Settings tiles) remain reachable post-setup exactly as shipped in 15-4/15-6.

**Why server-authoritative progress and no MMKV:** FR-1 requires progress to survive "closing the app or switching phones" — 15-2's `attendance_setup_progress` is that store. A local cache would be a second source of truth that drifts across devices (the exact bug class the resume AC targets). AuthFlow itself persists nothing; the wizard matches it.

**Why push-the-existing-routes instead of embedding step UI:** the 15-4/15-6 screens already own loading/error/save/a11y for their domains and were built deep-linkable with the wizard explicitly anticipated in comments; embedding copies would fork that behaviour. The wizard renders summaries from the same services and delegates all editing — one source of truth per domain.

**Why the marker PATCHes on Continue, not on every edit:** the marker is the resume pointer (15-2: "skipping is a FE concern, the step marker just advances"). Data writes have their own error handling in their own screens; tying the marker to Continue keeps "wizard advanced" == "step's data persisted" true by construction and gives AC-4 a single seam to guard.
