## 1. Fix-placement analysis (per the root-CLAUDE.md rule)

Every requirement lands **BE + DB**; the FE is untouched:

| Concern | Layer | Why |
|---|---|---|
| Corrections override + audit tables, `UNIQUE (employee_id, work_date)` | **DB** (two plain tables + one unique) | The audit trail and the uniqueness must hold for every writer and retry, and outlive processes (16-2 precedent). |
| FR-10 ten-rule engine, FR-11 credits, markers | **BE** (TypeScript, one implementation) | Lookups + arithmetic over already-read rows — the established Epic-16/17 relocation (AD-3 amendment). ONE module so the calendar, day detail and every Epic 19 read can never drift. |
| Range reads (per-employee-date facts over a grid) | **BE** (batched parameterised SQL in `day-status.read.ts`) | The day-context module's read half, generalised from one date to a range; no stored function (AD-3). |
| Write path (upsert override, append audit, acknowledge) | **BE** (`withTransaction` + `lockEmployee`, zero new RPCs) | The 15-7/16-1/17-1 transaction pattern. |
| `acknowledged_at` marker clearing | **DB** (plain `ADD COLUMN` on `attendance_attempts`) | Data lives beside the attempts it qualifies; no behaviour change to existing writers. |
| No notifications | **BE** (deliberate — nothing inserted) | FR-22's table has no correction/event entry; the closed list stays closed (adversarial-review posture since 15-5). |

## 2. Design decisions (locked before implementation)

**D1 — One migration: `attendance_day_overrides`, `attendance_corrections`, `attendance_attempts.acknowledged_at`.** Shapes per AD-12 and the spine's Structural Seed:

```sql
create table public.attendance_day_overrides (
  id                 uuid primary key default gen_random_uuid(),
  tenant_id          uuid not null references public.tenants (id) on delete cascade,
  employee_id        uuid not null,
  work_date          date not null,
  status             text,                -- present | half_day | absent | null (times-only correction)
  manual_checkin_at  timestamptz,         -- owner-entered; skips the location check
  manual_checkout_at timestamptz,
  deleted_at         timestamptz,         -- soft delete: the removal path (below); audit FK untouched
  created_by         uuid not null,
  created_at/updated_at timestamptz not null default now(),
  constraint attendance_day_overrides_status_check
    check (status is null or status = any (array['present','half_day','absent'])),
  -- unicity is the PARTIAL index above (a soft-deleted date can be corrected fresh)
);
-- composite FKs (employee_id, tenant_id) and (created_by, tenant_id) → users (id, tenant_id)
-- on delete restrict (15-7/16-1/17-1 pattern).
-- content rule: at least one of status / manual_checkin_at / manual_checkout_at:
--   constraint attendance_day_overrides_has_value_check
--     check (status is not null or manual_checkin_at is not null
--            or manual_checkout_at is not null);
-- pair rule (when both times set):
--   constraint attendance_day_overrides_time_order_check
--     check (manual_checkout_at is null or manual_checkin_at is null
--            or manual_checkout_at > manual_checkin_at);
-- partial uniqueness so a soft-deleted date can be corrected fresh:
--   create unique index attendance_day_overrides_empdate_uq
--     on public.attendance_day_overrides (employee_id, work_date)
--     where deleted_at is null;
--   [AMENDED 2026-09-29, review: implemented as the plain UNIQUE constraint
--   `attendance_day_overrides_empdate_uq` instead — the composite RESTRICT
--   FK from attendance_corrections cannot reference a partial index, and
--   the sole writer upserts (never inserts a second row) with the soft
--   delete re-used, so the audit chain stays intact.]

create table public.attendance_corrections (          -- FR-21 audit, append-only
  id           uuid primary key default gen_random_uuid(),
  tenant_id    uuid not null references public.tenants (id) on delete cascade,
  employee_id  uuid not null,
  work_date    date not null,
  actor_id     uuid not null,                          -- always an owner (FR-21)
  note         text not null check (char_length(note) between 1 and 500),
  old_value    jsonb not null,                         -- {status?, checkinAt?, checkoutAt?} | null-row marker
  new_value    jsonb not null,
  seq          bigint generated always as identity,    -- history ordering (17-1 D7 precedent)
  created_at   timestamptz not null default now()
);
-- composite FKs (employee_id, tenant_id), (actor_id, tenant_id) → users;
-- composite FK (employee_id, work_date) → attendance_day_overrides (employee_id, work_date)
-- on delete restrict (the override a correction refers to is never deleted;
-- overrides themselves are only ever upserted).
create index attendance_corrections_emp_date_idx on public.attendance_corrections (employee_id, work_date, seq);

alter table public.attendance_attempts
  add column acknowledged_at timestamptz;              -- null = not yet acknowledged
```

Grants hygiene exactly per 20260928000002 (RLS enabled + no policies, `REVOKE ALL … FROM anon, authenticated`, grant `service_role` only). No new trigger **[AMENDED 2026-09-29, review: one house `updated_at` trigger DOES ship on `attendance_day_overrides` — the benign hygiene exception; every other writer invariant holds as written]**: the override is written by exactly one TS upsert under the employee lock, and the audit table has no state machine to guard (a correction is an unconditional upsert — D4). No new stored function of any kind (AD-3 amendment). Also amended 2026-09-29 (review): the migration's pair rule is now a real at-rest CHECK (`attendance_day_overrides_pair_check` — status XOR manual instants), the tenant/date index is dropped (served by `empdate_uq`), and the history page index is `(tenant_id, employee_id, created_at desc, id desc)` — migration 20260929000003. **New ErrorCode enum values, added in the same change:** `ATTENDANCE_FUTURE_DATE`, `ATTENDANCE_DATE_NOT_TRACKED`, `ATTENDANCE_INVALID_RANGE` (all 422; none of these names exists in `error-code.enum.ts` today — the D6/D4 references are new entries, not reuses). **Routes-row amendment:** the spine's closed Routes allowlist (the "only:" row) is extended to admit `day-statuses` and `attempts` (the ack route) alongside the existing list — the same amendment note carries next to the AD-3 deviation above.

**D2 — The FR-10 engine: one pure TypeScript module.** `day-status.model.ts` is THE implementation of the FR-10 priority order and FR-11 credits. Inputs are one assembled `DayContext` per row (AD-22 — the existing `assembleDayContext`, reused verbatim) plus the day's `attendance_records` row(s), active leave day, override row and attempt facts. Exports:

- `STATUS_KEYS = ['not_tracked','not_checked_in_yet','in_progress','weekly_off','holiday','worked_on_holiday','leave','half_day_leave','present','half_day','absent','checkout_missing'] as const` — the 12 keys of UX-DR1, in FR-10 derivation order. The FE Badge vocabulary (18-3) is generated from this array's documentation; the engine is its own source of truth.
- `MARKER_KEYS = ['corrected','leave_pending','checkout_missing','fake_location_attempt'] as const`.
- `computeDayStatus(ctx, input)` — first-match-wins through the ten rules:
  1. An ACTIVE override present (`deleted_at IS NULL` in D1) →
     - **status-only rows** short-circuit: status from the stored status; `absent` → daysWorked 0, others graded per FR-11. `corrected` marker always set.
     - **times-only rows** REPLACE the day's check-in/out instants with the correction's (marked manual) and evaluation CONTINUES through rules 2–10 exactly as if those instants had been recorded normally — a corrected check-in on a Weekly off/Holiday therefore reaches rule 3 and grades `worked_on_holiday` (credit separate, FR-11), never `present` on an off-day. Rule 1's letter binds only "a correction **set a status directly**" (FR-10's own wording).
  2. Not tracked (`ctx.tracked` — enrolment covers the date, setup completed, module enabled, minus the FR-2 enable-day grace with `hasCheckIn` = a record or a times-only override exists) → `not_tracked`.
  3. (weekly off ∪ holiday) with a check-in → `worked_on_holiday`, graded by the same thresholds into `workedOnHolidayCredit` (≥ full-day hours → 1; ≥ half-day → 0.5; below → 0; open record (no checkout) on a past date → 0 + `checkout_missing` marker). `daysWorked` stays 0 — never mixed in (FR-11). **Late flags stay null/false on every off-day-derived status (`worked_on_holiday`, `weekly_off`, `holiday`)** — the decided v1 behaviour (PRD: "no Late flag on Weekly off / Holiday check-ins"); earlyCheckout likewise.
  4. Weekly off (no check-in) → `weekly_off`. Else holiday → `holiday`. **Both apply = `weekly_off` shown** (the ladder's literal order governs; a weekly off is the employee's own schedule and wins the label over the company-wide holiday — user ruling 2026-09-29, review D1).
  5. Approved full-day leave, no check-in → `leave` (leaveCredit 1, daysWorked 0).
  6. Approved half-day leave → `half_day_leave`; leaveCredit 0.5; the working half earns 0.5 when worked minutes ≥ halfDayHours, else 0 (G2-D1: `half_day_hours` is the threshold, not `fullDayHours ÷ 2`). **The open-record arm (working half 0 + `checkout_missing` marker) is evaluated only for PAST dates** — "open record by midnight" cannot be known on today; today's approved-half-day + open record falls through to rule 10 (`in_progress`).
  7. Check-in with check-out → workedMinutes = `workedMinutesBetween` (one implementation, imported); ≥ fullDayHours → `present` (1.0); ≥ halfDayHours → `half_day` (0.5); else `absent` (0, hours still shown in workedMinutes). **G2-D1 ruling (2026-09-29): the thresholds are the owner-configured `full_day_hours`/`half_day_hours` columns × 60 (`DayContext.fullDayMinutes`/`halfDayMinutes`) — the office window span drives only the late/early metrics; the no-rule permissive arm stays.**
  8. Past date, check-in with no check-out (by midnight) → `checkout_missing` (daysWorked 0 until corrected). The SAME arm applies to a times-only override with `checkinAt` set and `checkoutAt` null — the very correction FR-21 motivates (a forgotten checkout) must land here, not fall off the ladder.
  9. Past date, no check-in, no approved leave → `absent` (+ `leave_pending` marker instead of status change when a Pending leave covers the date).
  10. Today/future, no check-in yet → `not_checked_in_yet`; today, checked in, not out → `in_progress`. The `leave_pending` marker rides on rule 10 too: whenever a pending leave day (any part) covers the row's date, `leave_pending` is emitted regardless of status — the calendar keeps the leave indication on the one day it is most actionable.

- **No-rule grading (user ruling 2026-09-29, review D2):** when no office rule covers the date, any positive worked minutes grade `present` with full credit — a tracked day without a rule is a setup gap, not a fault to punish the worker for; the read path logs a warning (once per range read, not per date) so the gap is visible. Follow-up hardening: office setup must make the rule mandatory with a default prefilled value so owners don't miss it (fenzo-app UI + a BE validator).
- **Credit rules when leave is outranked (data only, no double-credit):** leave days suppressed by rules 3/4 (weekly-off/holiday wins) or rule 1 earn **no credits** (leaveCredit 0, daysWorked per rule 1's arm) — their `leave_request_days` row stays `approved` as data (Epic 17's contract: the leave keeps its requested range), and the row reads the winning status instead. Mirror gate (additive change to 17-1's apply validation): leave apply/on-behalf rejects a target date that already carries a **non-absent** override (corrected present/half_day — the same double-credit impossibility `LEAVE_CHECKED_IN_CONFLICT` closes for check-ins); an `absent` correction can validly be covered by approved leave afterwards (owner pulled someone in, later on-behalf leave supersedes — rule 1 short-circuits, no credits, probed in tests).

- `lateMinutes` / `earlyCheckoutMinutes` ride on top of every rule that has a stored check-in/out and a covering rule (D7 of 16-1: null when no rule) — computed by the imported `computeLateMinutes` / `computeEarlyCheckoutMinutes`; they never change the status. EXCEPT the off-day statuses above: no Late/Early on `worked_on_holiday`/`weekly_off`/`holiday` (decided v1 item).
- **Date-relative semantics:** "past" and "today" are evaluated against the tenant-local calendar via the DB clock (`dbNow` at the anchor, the 16-1 review precedent). Rule 8's `checkout_missing` applies only to dates < today; rule 10's states cover today; **future dates reuse the rule-10 states** (`not_checked_in_yet`, `weekly_off`, `holiday`, `worked_on_holiday` impossible — no record can exist; a pending leave there shows `leave_pending`). This keeps the calendar (18-3) at exactly 12 keys — no 13th "future" key — and costs nothing honest: nothing has been recorded yet. Future `not_tracked` still wins over everything (rule 2 outranks 10).

**D3 — Days-worked & credits (FR-11) per row.** `daysWorked` (decimal): present 1, half_day 0.5, `half_day_leave` earned half 0.5, everything else 0 (`checkout_missing` 0 "until corrected" — a later correction flips it live). `leaveCredit`: full-day approved leave 1, half-day leave 0.5. `workedOnHolidayCredit`: 1 / 0.5 / 0 per the rule-3 grade. These three columns are the entire FR-11 contract; sums over any range for Owner and Employee come from the same rows (Epic 19 totals read them — one implementation).

**D4 — Corrections write path (FR-21 + AD-12).** `PUT /attendance/corrections/:employeeId/:workDate`, owner only. **No idempotency header (AD-6's letter: "IdempotencyInterceptor is not applied to attendance routes"):** a correction is an unconditional owner upsert — FR-21's "Owner can correct it again" is the intended semantics, so a replayed PUT is not a duplicate-write hazard but a legitimate re-correction; AD-6's row-based guards (`UNIQUE (employee_id, work_date)` + the audit's `seq`) are the last-guard posture, and no `X-Idempotency-Key` is required or accepted. Body: **exactly one of** (a) `{ status: 'present'|'half_day'|'absent' }`, XOR (b) `{ checkinAt, checkoutAt? }` — owner-entered instants (ISO-8601 with the tenant offset; `checkoutAt` optional because a corrected check-in may not be checked out; a times-only row grades at read time and a later checkout correction completes it). Mixing status and times → 422 `VALIDATION_ERROR`. `note` required, 1–500 chars after trim. The write (ONE `withTransaction`): tenant + employee-scope checks → `dbNow` for the date comparison → `lockEmployee` (AD-5; also serialises the audit's `seq` ordering) → **gates** (below, in order) → capture `old_value` from the day's CURRENT EFFECTIVE facts — the prior override's shape when one exists, else the original `attendance_records` row's `{status, checkinAt, checkoutAt}` (its FR-10-derived grade), else empty — so the first correction still stores the value it displaced (FR-21: "old value"; AD-12: "old value, new value") → upsert the override (full current value replaces the previous one — `ON CONFLICT (employee_id, work_date) DO UPDATE` of status/times/created_by/updated_at) → append ONE `attendance_corrections` row (captured old value, the new observable shape, note, actor, now) → COMMIT. `attendance_records` is never touched (AD-12 — the original stays).

**Correction gates, in priority order:**

1. Employee resolves in the tenant → else 404 `ATTENDANCE_EMPLOYEE_NOT_FOUND` (no existence leak, 17-2 precedent). **Actor provenance:** `actor_id` (and the override's `created_by`) derive solely from the JWT (`@CurrentUser` → `requireTenant`, house pattern) — the DTO exposes no actor field and the service never trusts one. `note` additionally rejects control characters (C0 / zero-width) after trim, before the 1–500 check.
2. `workDate` ≤ tenant-today → future dates are 422 `ATTENDANCE_FUTURE_DATE` (FR-21: "any past or current date").
3. Tracked-date gate: the engine's row for that single date must not be `not_tracked` (D2 rule 2 — includes the FR-2 enable-day grace) → else 422 `ATTENDANCE_DATE_NOT_TRACKED` (the story AC's literal "PT422"; a NEW code, distinct from the actor-facing 403 `ATTENDANCE_NOT_TRACKED`).
4. Instants valid: `dateInTz(checkinAt) === workDate` (the check-in anchors the record's work_date exactly as 16-2 does — no "±" window) and `dateInTz(checkoutAt) === workDate` or `=== workDate + 1 day` (a checkout may fall after midnight — pure string compares, DST-safe; note live 16-2 check-outs can never produce the +1 shape since the service looks up today's record, which is fine for a manual correction); `checkinAt` not in the future relative to DB now → else 422 `ATTENDANCE_INVALID_RANGE` (NEW enum entry, D1; message names the field). Malformed/negative → DTO `VALIDATION_ERROR`.

**Removal path (soft delete):** `DELETE /attendance/corrections/:employeeId/:workDate`, owner only → one `withTransaction`: same gate 1/3 tenant + tracked checks (gates 2/4 apply where meaningful — non-tracked dates have nothing to remove → 422), then `UPDATE attendance_day_overrides SET deleted_at = now() WHERE employee_id = $emp AND work_date = $d AND deleted_at IS NULL` — zero rows answers 200 with `deleted: false` (an own retry of a removal is free); one row answers 200 `{ deleted: true }` and appends ONE audit row (old value = the removed override's shape, new value = empty `{}`, note "Removed correction", actor JWT) — the engine reads only `deleted_at IS NULL` rows from the next call on (the recompute-live contract, 18.1 AC4's spirit extends to corrections without any month lock). No hard delete anywhere: the audit's composite FK stays valid.

Gates re-read the day facts under the transaction (the read path `buildDayContext`-style for one employee-date) so a racing enrolment change cannot slip a correction onto an untracked date. **Audit growth is accepted and stated:** the unique pair bounds the override to one row, but `attendance_corrections` appends unboundedly by repeat corrections — this is the FR-21 contract (full history, owner-sourced, own-tenant data); the cursor-paginated history read must tolerate an arbitrarily long per-date chain.

**D5 — Fake-location acknowledge (AD-10 [ADOPTED]).** `POST /attendance/attempts/acknowledge`, owner only, body `{ employeeId, workDate }` → one `withTransaction`: employee resolves in tenant (404 otherwise), then `UPDATE attendance_attempts SET acknowledged_at = $now WHERE employee_id = $emp AND tenant_id = $t AND outcome = 'mocked' AND acknowledged_at IS NULL AND (attempted_at AT TIME ZONE $tz)::date = $workDate::date` — the cast order matters: `attempted_at AT TIME ZONE $tz` (an IANA name, validated by the 15-2 trigger) yields the tenant-local wall time, whose `::date` equals `dateInTz`'s Intl computation; both engines read the same IANA tz database (AD-7) → response `{ acknowledgedCount }` (200 even at 0 — an ack is a read-shaped write, own retries are free; the UPDATE is naturally idempotent). The day-status marker lifecycle: `fake_location_attempt` is set only while **unacknowledged** mocked attempts exist for that employee-date — acknowledging clears the marker on the next read (AD-10's literal "clears when the Owner acknowledges it"); the attempts rows are kept (the dispute view, AD-4 contract intact). No notification (FR-22 has no ack event).

**D6 — Day-statuses read routes (the 18-3/18-4 surface; Epic 19 aggregates on the same engine).**

- Owner: `GET /attendance/day-statuses?employeeId=&from=&to=` — single employee (the multi-employee aggregate is Epic 19); technician self: `GET /attendance/me/day-statuses?from=&to=`. `from ≤ to`, span ≤ 62 days (`ATTENDANCE_INVALID_RANGE`, 422; the calendar requests a month ≤ 31 days), dates tenant-local. Future dates are valid input (the calendar taps future cells). All routes tenant-verify identity/params with the **same 404-no-existence-leak gate as the write** (`ATTENDANCE_EMPLOYEE_NOT_FOUND`, never a distinguishing 403). **Access-state semantics for the `me` routes (AD-17 mirror):** access state `none` → 403 `ATTENDANCE_NOT_TRACKED`; `history_only` → history reads still allowed (in-progress-only reads honestly return rows for dates the employee's own records cover); a **disabled-but-in-tenant employee's history stays owner-readable** — an off-boarded technician's record remains reviewable, and dates after the disable read `not_tracked`.
- Response `{ employeeId, from, to, days: DayStatusRow[] }` with `DayStatusRow = { workDate, status, lateMinutes, isLate, earlyCheckoutMinutes, earlyCheckout, workedMinutes, daysWorked, leaveCredit, workedOnHolidayCredit, isWeeklyOff, holidayName, isWorkingDay, officeId, officeName, checkinAt, checkoutAt, checkinSource: 'gps'|'manual'|null, checkoutSource: 'gps'|'manual'|null, markers, latestCorrection? }`. `isLate` and `earlyCheckout` are the same booleans the FR-4 today-record derives from the same imported math (`lateMinutes > 0`, `earlyCheckoutMinutes !== null`). Instants ISO-8601 with the tenant offset (`toTenantOffsetIso`, AD-7); `latestCorrection` = `{ correctedAt, actorName, note, oldValue, newValue }` (the sheet's pre-fill + the "Corrected by owner" line employees see, FR-21) while the **full history** comes from the corrections read below.
- Corrections history: owner `GET /attendance/corrections?employeeId=&workDate=` (employeeId required; workDate optional filter), technician `GET /attendance/me/corrections?workDate=` (own dates only). Cursor pagination (house `PaginatedResponse`, scopes `'day-corrections-owner'` / `'day-corrections-me'` so a cursor minted on one endpoint can never replay on the other, 17-1 D13 precedent). Entries: `{ id, employeeId, workDate, correctedAt, actorName, note, oldValue, newValue }` — the Day Detail sheet's expandable full-history row (18.3 AC).
- Previews (AD-24): the correction sheet's pre-fill is NOT a preview of a state change — it displays already-stored facts (the day-statuses row + history), which are server-computed; no preview endpoint is added (FR-21 defines no preview; AD-24's "wherever the UX shows one of these before a write" is satisfied by the read). The only server-derived display value inside the sheet is the eventual status the engine computed for the current inputs — the FE re-derives nothing.

**D7 — Range reads (performance).** `day-status.read.ts` fetches the grid in ~11 parameterised statements inside ONE `withTransaction` (the leave-read.service `listMine`/`listForOwner` shape — the house GET read path; no read-only client exists and none is invented): tenant timezone; settings; enrolments overlapping the range per employee; assignments + offices; covering rules; weekly-off overrides + defaults; holidays; `attendance_records` rows in range (+attempt ids for the source flags and mocked mapping); `attendance_attempts` mocked/outcome facts for `fake_location_attempt`; active leave days (`pending`/`approved` across the span); overrides; corrections (latest per date, employee names resolved in one `users` round-trip). All matrices are cut by `valid && daterange` overlap; the in-memory assembly re-uses the imported `pickRuleForDate` / `pickWeeklyOffDays` (the 15-9 drift class stays closed at the type level) — no per-date SQL, NFR-7 budget for 50 employees × 31 days (~1,550 rows) covered by the integration probe (≤3s p95).

**D8 — No me/summary or check-in changes in this story — verified, not assumed.** 16-4's `readTodayRecord` and the check-in/out responses keep their contracts; the engine is additive. Ripple probe in tests: for today's employee, the engine row's late/early/worked numbers equal the FR-4 summary's `todayRecord` (the same imported math makes drift impossible, but the probe pins it — the 15-9 lesson).

**D9 — No notifications and no events.** Corrections and acknowledge trigger no notification (FR-22's closed list), no `notification-events` registry additions, no outbox writes. The only `attendance.*` events remain 16-1's set.
