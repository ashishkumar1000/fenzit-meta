## Intent

**Problem:** Leave has a per-tenant catalog with a paid flag (23-2) but no accrual program: there is no per-tenant leave policy (rate/CF/over-balance), no balance enforcement at apply time, no balance read for employees or owners, and no leave section on the payslip.

**Approach:** A FIXED four-type catalog per tenant — Earned Leave (monthly, default 1/month, CF on), Sick Leave (monthly, default 0.5/month, CF off), Bereavement (annual fixed grant, default 0 — blocks until the owner sets the number), Comp-Off (no accrual, paid, owner approves). Types cannot be created or deleted; the owner edits VALUES only (accrual rate/days, carry-forward, over-balance, paid, enabled); the accrual mode is inherent to each type's code, pinned by a DB check. The balance is DERIVED on read in the April–March FY — no scheduler, no year-end routine: `balance(Y) = credits(Y) + accrued(Y, as-of) + carryForward(Y) − consumed(Y)`, where consumed = (pending + approved) WORKING days of that type, half-day parts consuming 0.5, off-day rows carrying no debit. Apply-time check blocks with a plain-English 422 (`LEAVE_INSUFFICIENT_BALANCE`) unless the type allows over-balance; mode-none types are exempt. Read surfaces: employee types read (closes the 23-2 ledgered defer), own balances, owner per-employee balances. The payslip gains a leave-balance snapshot captured at run time as of the pay-period's last day. All backend (fenzit-be), zero RPC — DDL migration + NestJS raw SQL in pg tx.

## Boundaries & Constraints

**Always:** Zero new RPCs/DB functions — DDL + NestJS table writes only (epic-23 rule; `write_audit_row` is the existing RPC, reused not duplicated). New tables deny-by-default: RLS on with no policies, grants revoked from public/anon/authenticated, `service_role` only, table commented. Composite FKs `(col, tenant_id) → parent(id, tenant_id)` so a cross-tenant link is impossible at the storage layer — user-tenant columns target `public.memberships (user_id, tenant_id)` (users lost tenant_id at migration `20261020000004`; the composite user key is `memberships_user_tenant_key`). Explicit tenant scoping on every read/write. Every values-PATCH, enable/disable and credit write audits one row via the existing `write_audit_row` (old/new pairs, changed-field names); the migration's seed writes NO audit rows (system action). The balance check runs inside `applyTransact` AFTER `validateApplyFacts` + the payroll-lock gate and UNDER the existing per-employee advisory lock (concurrent applies already serialise); the two other balance-mutating paths outside that lock — `setRequestType` and the credit POST — take `attendance_lock_employee` in their own txs. Accrual math lives in a new module (`leave-balance.math.ts` pure + `leave-balance.service.ts`); `leave.service.ts` stays out of accrual; working-day facts reuse the shipped span-facts readers (`readSpanFacts` single-employee, `readPageSpanFacts` batched — `computeSpanFacts` itself is module-private, never re-implemented, no drift). All balance arithmetic rounds to 2dp half-up at every surface (house `roundMoney`, `src/payroll/formula.ts:265`) and the sufficiency comparison runs on the rounded values. Numeric day values respond as JSON numbers (house `Number()` conversion idiom). Plain-English copy says Employee; error messages carry the numbers ("you have 3.5 days left, this request needs 4"). Ledger scan done: `deferred-work.md:1256-1262` assigns the leave-typing read-side exposure to fenzit-web 23-10/23-11 — the employee types read here ships the BE surface that entry names, the entry stays open with the web stories; the 23-2 FK-index and case-insensitive-name defers stay in the ledger (pre-launch batch, owner unanswered); nothing else in the ledger names leave balances.

**Never:** No scheduler, no background job, no year-end routine anywhere. No excess-to-LOP auto-conversion (explicitly deferred; the payroll unpaid-day read at `payroll-run-engine.service.ts:896-912` is UNTOUCHED — disabled types' unpaid days still LOP because that read has no enabled filter). No name/code/accrual-mode editing; no type create/delete routes (retired, pre-launch break allowed); no web/mobile UI. No change to the leave state machine, the freeing paths (revoke/cancel/auto-cancel/disable sweep — derived consumption restores balance with zero extra code), the overlap index, or the day-status engine. No new permission (`leave.types`, `leave.own`, `leave.read_all` cover everything). No change to locked months — payslip snapshots stay frozen (a re-run never UPDATEs payslips; destroy-and-replace re-captures only on unlocked months). No tests written before the implementation exists (test-timing rule — this plan only NAMES them). No schema change to `leave_requests`/`leave_request_days` beyond what 23-2 shipped.

## Design Notes

- **Derived, never scheduled** — Frappe's ledger+scheduler model produces identical balances here with zero background state; consumed derives from `leave_request_days.state`, so revoke/cancel/auto-cancel/disable-sweep restore balance with no code. The 3-agent research digest is the source of the cut.
- **Mode pinned by DB check, not a setting** — the four (code, mode) pairs are the only legal combos; remnants (code NULL) can never be enabled, so a legacy row can never silently join the program.
- **Why TS-side working-day math** — `computeSpanFacts`' override-replaces-default / holiday-wins semantics are subtle; re-reading the three rule tables and reusing the canonical implementation prevents a second truth (no SQL mirror of weekly-off logic).
- **Half-day lives on the request** (`part`), day rows are one-per-date — weighting joins the request; a half-day on an off day is already `LEAVE_ALREADY_OFF` upstream, so 0.5 only ever lands on working days.
- **Payslip jsonb** — mirrors `earning_lines`/`deduction_lines`; destroy-and-replace means a re-run re-captures fresh (no UPDATE-exclusion problem), and locked months stay frozen by the existing lock machinery.
- **Credits are POST-only** — corrections are offsetting negative rows (auditable history) rather than edits; `source` is CHECK-pinned to 'manual' so a future carry-forward source can never double-count against the derived chain.
- **Open questions after the adversarial review — ALL RESOLVED** — Q1 (by spec wording: the current FY carries its completed prior FY's unused; only a future FY has CF 0, so a Mar→Apr spanning apply may block on the future segment; escape = allow_over_balance), Q2 (**owner-confirmed 2026-11-18: floor at 0** — negative balances never carry), Q3 (the chain is `memberships.join_date ?? enrolment floor ?? FY start`; the backfill set every membership's join_date so it is defensive-only; the never-enrolled tail lands on FY start — accepted, applies are gated by ATTENDANCE_NOT_TRACKED anyway), Q4 (by spec wording: balance endpoints return every mode≠none type, enabled AND disabled; ENABLED-only stays on the catalog read and the payslip capture where the spec pins it), Q5 (accrual_days > 0 on comp_off rejected — mode-none has no accrual to configure), Q6 (credit `created_by` NOT NULL, FK to memberships). Owner decisions 2026-11-18 on the review's two extras: **mid-FY config repricing accepted** (derived-on-read re-prices the whole FY at the current values — 1/month Apr–Oct then 2 from Nov reads 16, not 9; the story sentence "changes affect computations from the change onward" reads as "no snapshots, no monthly history"; frozen payslip snapshots excepted) and **leaver clamp accepted** (monthly accrual stops at `memberships.exit_date`'s month when the exit is on or before the as-of date).
- **Verified safe by the review** (kept as pinned): half-day requests are single-date-only so no multi-row half path exists; the weekly-rules-once batched read is mechanically sound (`pickWeeklyOffDays` re-validates each row's `valid` daterange per date, so mid-window rule changes apply correctly); concurrent applies/approve/revoke/cancel/auto-cancel/disable-sweep all serialise under `attendance_lock_employee` (xact locks are reentrant — no deadlock); a stale-pending rejection retroactively lifting CF is correct derived semantics (payslip snapshots stay frozen; app balances shift by design); manual credit rows re-granting carry-forward by hand cannot be structurally blocked by `source='manual'` — accepted, the audit trail is the mitigation; `monthEndOf` and March-run FY bucketing are correct as cited.
