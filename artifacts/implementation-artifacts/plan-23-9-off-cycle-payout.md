## Design decisions (pinned here; each flagged for the adversarial review)

1. **Status lifecycle — staged until it lands on a payslip.** Create always stages (even for a month that already completed a run: the line is not on any payslip yet — "staged vs applied made visible" reads as consumed-or-not, not has-run-or-not). The engine's write tx flips **consumed** staged → applied atomically with the payslip write; staged lines for **skipped** employees stay staged = **orphaned**. Applied lines re-feed every re-run of the month (re-run keeps the line intact — the engine reads status in (staged, applied)). **Flip discipline (review F3)**: the flip runs by the **exact id set captured in computeMonth** with a re-check in the WHERE (`where id = any($ids) and tenant_id = $1 and month = $2 and status = 'staged'`) — a line created after the compute read, or re-targeted between read and flip, can never be marked applied for a payslip that does not carry it. The staging surface serializes against runs and locks: `create` and `update` run in a pg tx that takes the target month's `payrollRunAdvisoryKey` **exclusively** first (the same key the engine's write tx and the lock service take); `update` additionally takes the line's CURRENT month's key (both keys sorted, taken in order — no deadlock). Edits wait out an in-flight run instead of racing it. **Accepted residual (review F7)**: an applied line whose employee a later re-run SKIPS keeps status applied while its payslip no longer exists — the contract's orphan definition covers staged only; the web list shows it against the month, accepted.
2. **Amount validation (service-side, plus a one-line DB belt).** Zero → 422 plain English ("an off-cycle amount cannot be zero — use a positive earning or a negative recovery"). Negative → allowed only with `acknowledged: true` (employer-liability acknowledgment, enforced server-side; unacknowledged negative → 422). Tag does not change the validation: a negative line is a recovery by design regardless of tag (flag: "per tag" in the carried note read as the note's own parenthetical, not two rules). DB belt: new migration adds `check (amount <> 0)` on `payroll_off_cycle_lines` — the trap the ledger named never re-opens for a future writer.
3. **Positive line → earning line.** Each positive line becomes its own `earning_lines` entry `{ name: 'Off-cycle: <label>', amount }` — a FLAT amount, never prorated by the divisor. The line-set still sums to `gross_earnings` (fixture G's break-up rule). Gross therefore already includes the lines, so the 50%-cap basis includes them with no extra wiring (the basis is the earning-line set story 6 sums).
4. **wage tag joins the PF base.** PF base for the employee = earned basic + Σ positive wage-tagged lines; PF = 12% × min(base, ceiling), covered rules unchanged. Bonus-tagged lines never touch it (fixture G: PF unchanged 2,076.92).
5. **Negative line → deduction line.** Entry `{ source: 'offcycle-recovery:<label>', amount: |amount| }` inside the capped deduction set (same cap treatment as the shipped `recovery:<month>` lines — the fixture's "recovery lines outside the base" phrase is about the BASE, not about cap exemption; variant D's excess recovery is itself "subject to the same cap check", so off-cycle recoveries are too). **Prefix is deliberately NOT `recovery:`** — the shipped engine reconciles recovery outstanding positionally over `recovery:*` lines, and a colliding prefix would pair the off-cycle line with a real recovery row and corrupt `payroll_recovery_lines.outstanding_amount` (review F1). The Form V "others" filter extends to the new prefix. Net: `capClamp` never floors — the final-run math (decision 8) is where a floor exists; regular runs keep the shipped geometry.
6. **TDS: the lines join the projection's annual.** `annual = structureTotal × monthsEmployedInFy + Σ signed off-cycle amounts (this month's lines)`; taxable/assessed/spread unchanged (re-spread over remaining FY months incl. the run month). Rationale: the projection's only monthly-amount lever is the annual, and "joins the TDS projection" has no other mechanically coherent reading. No fixture number pins TDS-with-line (variant D pins TDS via an override) — flag for review; ask the owner only if the review disagrees.
7. **Recovery month-restriction + re-run idempotency (engine fix, review F1/F2).** Recovery reads gain `.lt('month_raised', month)`: month M's run ignores recoveries M itself raised (a re-run of M neither absorbs nor duplicates its own excess); M−1-and-earlier excesses are absorbable. The filter also stops an October re-run from absorbing an excess November raised after a November-first run (out-of-order runs stay honest). **Write side must match or the filter un-masks a shipped duplicate**: today every breaching re-run plain-inserts a second recovery row (no unique). Pinned rule — the write tx, before inserting fresh excess, **deletes this month's own raised rows whose outstanding still equals original_amount** (never touched by any later month's absorption) and inserts the freshly computed excess; a **partially-absorbed** row is left alone and the re-run does not re-raise (its absorption progress belongs to a later month; a residual under-recording if the recomputed excess grew is accepted and noted). Story migration adds the belt: unique `(tenant_id, membership_id, month_raised)` on `payroll_recovery_lines`. **Reconciliation walk fixed in the same change** (review F1): the shipped engine pairs `recovery:*` lines to recovery rows by push-order index — two rows whose outstanding order disagrees with created_at order mis-pair, and any new prefix collision corrupts outstanding. The deduction line carries the recovery row's **id** (parallel map keyed by id) so decrements land on the exact row. Journey leg 6 re-pinned to assert exactly one recovery row for (A, 2026-10) with outstanding 2,646.15 after October's re-run.
8. **Leaver's final run.** `isFinalRun ⇔ exit_date ≠ null ∧ owner(exit_date) = run month` (owner(d) = d's month when day ≤ cutoff(d's month), else next month — the same ownership rule the gate uses; engine already resolves cut-offs). On a final run:
   - **TDS remainder in full**: no spread division — the projection's remainingTotal deducts whole (SPEC Run-arithmetic "a leaver's final run deducts the full remaining estimate"; the shipped `tdsProjection` comment claims "naturally" but `fyRemaining(month)` is calendar-based, so a leaver's final run currently deducts 1/N — a real gap this story closes). **TDS-override interplay**: an override replaces the computed projection entirely (the shipped override semantics — immutable per-period full amount), so "remainder in full" governs only the computed path; an overridden leaver month deducts the override value as-is.
   - **Unabsorbed recovery in full**: on a final run the employee's TDS and recovery deduction lines are exempt from the 50% clamp (deducted in full, not counted against the cap); other deductions cap as usual against the full base. New pure math in `offcycle-math.ts` — `finalRunTds` + `finalRunClamp` with the exact rules: exempt lines deducted first; remaining lines capped at 0.5 × gross as usual; `net = gross − all deductions` **floored at 0.00** (`capClamp` itself never floors — new math, unit-tested at the boundaries: deductions exactly = gross, one paise over, multiple recoveries spanning the floor). **Absorbed allocation when deductions > gross**: each recovery absorbs `min(outstanding, remaining headroom)` in created_at order; the balance keeps its outstanding amount (rolls forward; reported in the summary as still-outstanding for a departed employee — collection moves to final settlement outside the system). **No new excess rows are raised on a final run** — an excess an exited employee can never absorb is not planted as an eternal recovery row; the unabsorbable clamp excess is reported in the run summary instead. Flag: "in full" vs the statutory cap is the spec's own carve-out (story contract), not our invention.
9. **Run summary additions.** `offCycle: { staged, applied, orphaned: [{ employee, label, amount }] }` (orphaned = staged lines whose employee's payslip was not written this run; the zero-employee early return lists ALL the month's staged lines as orphaned) and `recovery: { outstandingBefore, outstandingAfter, raisedThisRun }` (story contract: the outstanding balance in every run summary, each month's excess adding to it).
10. **Lock confirmation upgrade.** `confirmation.stagedOffCycleLines` becomes the LIST `[{ employee, label, amount, tag }]` of the month's staged lines (count = list.length). Web story 11 reads it; the shipped number field changes shape — pre-launch, allowed.

## Journey legs (test/payroll-journey.e2e-spec.ts — real DB, fixture money verbatim)

1. **Staged line on first run** (fixture G leg): stage ₹5,000 bonus for A on unlocked October → October's run → payslip has the Off-cycle line, gross includes it, one payslip, line status applied.
2. **Re-run preservation**: re-run October → exactly one payslip, line intact (status applied, same money).
3. **D+bonus cap row** (fixture G): variant-D config (TDS override 12,000 + insurance head) + staged ₹5,000 bonus → deductions 14,761.54 clamped to 14,615.39, net 14,615.38, excess 146.15 raised, **PF unchanged 2,076.92**.
4. **No collateral**: the other employee's payslip numbers unchanged vs the pre-line run.
5. **Bonus ≠ PF**: same run as leg 1 — PF identical with and without the bonus (wage-tag contrast covered in units; a wage-tagged journey line joins PF asserted against the fixture's earned-basic arithmetic).
6. **Recovery month-restriction + re-run idempotency + roll-forward** (variant D legs): October raises excess 2,646.15 → **October's re-run ignores it AND does not duplicate it** — deductions unchanged, outstanding balance unchanged in the summary, and exactly ONE recovery row for (A, 2026-10) with outstanding 2,646.15 (the F2 rule) → November's run absorbs it subject to the cap; summary shows outstandingBefore/outstandingAfter/raisedThisRun; unabsorbable remainder rolls forward.
7. **Leaver's final run**: employee with exit after the cut-off (Oct-27 shape) — November is the final run: TDS remainder deducted in full, unabsorbed recovery deducted in full past the cap, net floored at zero, still-outstanding remainder reported.
8. **Orphan path**: stage a line for an employee the run skips (no join date) → stays staged, listed in the run summary's orphaned block AND the lock confirmation list → PATCH re-targets it to another unlocked month → consumed there (applied).
9. **Validation legs**: negative without acknowledgment → 422; zero → 422; future month → 422 plain English; month below the first payroll month → 422; locked month target → 409 `PAYROLL_MONTH_LOCKED`; no-structure employee → 422; duplicate (tenant, member, month, label) → 409; applied-line PATCH → 422 (build-time amendment above).
10. **Type-PATCH gate leg**: after locking October, `PATCH /leave/:requestId/type` on a request with a frozen date → 409 `PAYROLL_MONTH_LOCKED`; a request with only post-cut-off dates → 200 (the shipped boundary); a no-op re-type (same type) → 200 with no gate trip.
11. **Race legs** (review F3): a line created while a run is in flight stays staged after that run's flip (id-set discipline); a PATCH of a line the just-finished run consumed answers 409 applied — not a flipped wrong state.
