Real OTP Delivery via MSG91 SMS (DLT) — Validation Report

FAIR

Overall verdict (rubric): This is a strong, unusually well-grounded PRD: every brownfield claim checked is accurate (all §2 file/line references verified against the working tree), decisions are logged with dates in the frontmatter, the Non-Goals section does real work with reasons, and §11's architecture section constrains actual code rather than decorating. All seven rubric dimensions judge strong. The risks are concentrated in three places: FR-BE5's dev/prod otp-field gate is stated two conflicting ways (security-adjacent), the T2–T5 notification-sender backend work implied by §10 is never explicitly de-scoped or owned, and the §7 "≥ 98% signup success rate" metric has no instrumentation anywhere in the FRs to make it measurable.

Adversarial shift: The adversarial reviewer materially changes the picture. No dimension drops below strong, but six findings rank high by impact: OTP generation still uses Math.random() while the PRD makes verification a real security boundary; FR-BE5's mock-only otp field has no implementable mechanism that doesn't violate §11's own anti-pattern list (and the §9 rollout window would put plaintext OTP in production responses); FR-BE1's single-otp-param endpoint spec cannot deliver the 2–3-variable T3/T4 templates the same document says the port serves; and T3/T4 as worded likely fail DLT's non-consecutive-variable rule the PRD itself states. Rubric medium findings and adversarial findings overlap on four items (FR-BE5 gate, port/T2–T5 scope, the 98% metric's instrumentation, multi-variable support) — overlap is signal, not duplication: these are the PRD's real seams.

Adversarial review

review-adversarial-general.md

16 concrete findings, each citing a section and a load-bearing quoted phrase, with backend claims verified against the working tree. Severity badges below are assigned by the synthesis pass (the adversarial lens reports descriptions only). Findings 1–5 in particular are pre-implementation must-resolves: the RNG, the OTP-field gate, the rollout window, the multi-variable port gap, and the T3/T4 DLT wording.

high

OTP still generated with Math.random() — real verification verifying a predictable code

§2 table, FR-BE6 (auth.service.ts:84)
Math.random() is not a CSPRNG (V8 xorshift128+ — predictable from ~a few observed outputs). The PRD upgrades verification to a real security boundary while generation stays at mock quality; the RNG is never mentioned anywhere in the PRD.
Fix: add an FR switching generation to crypto.randomInt(100000, 1000000) (one-line change), or document the deliberate deferral with rationale.
high

FR-BE5's mock-only otp field has no implementable mechanism that doesn't violate §11's own anti-pattern

§4.1 FR-BE5, §3.3, §11
Implementing FR-BE5 literally requires the service to know which provider is active — a provider-identity check the §11 checklist bans. The alternative (NODE_ENV gating) contradicts FR-BE5's provider-based wording. The PRD never picks one.
Fix: gate on an explicit environment/config signal the service can read without knowing the provider (e.g. EXPOSE_DEV_OTP, default false); the mock keeps its own logging; the service-level OTP log line is deleted, not gated.
high

Deployment step 1 schedules plaintext OTP in production API responses

§9 step 1 + FR-BE5 + §7
§9 step 1 instructs Render production to run SMS_DELIVERY_PROVIDER=mock until the config flip — a window spanning DLT approval (days). During it, every production POST /auth/otp/send returns the plaintext OTP, contradicting the §7 metric the PRD sets for itself.
Fix: gate on environment (production never sees the field), and add an acceptance check at the step-3 flip asserting the response has no otp key.
high

The port signature can't deliver T3/T4 — variables[1..2] have nowhere to go on MSG91 v5 /otp

§4.1 FR-BE1 vs §10.1 T3/T4, §11 AD-1/AD-5/AD-2
FR-BE1 hardwires the adapter to the v5 /otp endpoint, which carries exactly one otp param; T3 and T4 need three variables. AD-2 calls the endpoint choice "vendor detail inside the adapter," but the port call carries no information from which the adapter could decide, and no FR covers the transactional path at all.
Fix: pin the mapping now (second adapter method or flow-endpoint mapping for multi-variable templates) or scope T2–T5 sending explicitly out of this PRD's port promise.
high

T3 and T4 likely DLT rejections — adjacent variables violate the non-consecutive rule the PRD itself states

§10 T3/T4 + ops one-pager
"New job {#var#} ({#var#})" and "Update for job {#var#}: {#var#}" sit variables back-to-back separated only by punctuation. DLT operators reject templates with no fixed text between variables — the very rule the PRD cites. Both launch-set templates contradict their own document's invariant.
Fix: rewrite with real fixed text between every variable pair (e.g. T3: "New job {#var#} for {#var#} service is scheduled for {#var#}."), re-check the ≤30-char budget, mirror into the ops sheet before the batch is submitted.
high

T2–T5 handed to ops as a launch set, but no FR covers their backend sending; T4 presumes an undesigned worker

§8, §10.1
§4 covers only T1. T2's inviteTechnician send, T3/T5 job-event sends, and T4's "SMS worker subscribes to notifications inserts" are unimplemented and undesigned — the worker appears only as a parenthetical in an ops-facing section. Approved templates can't be edited, while their exact wording depends on backend formatting choices that don't exist yet.
Fix: scope T2–T5 registration explicitly ("ops may register now; backend wiring is a separate future PRD/story; store IDs until then") or cut T2–T5 from the batch — approval is per-template, not batch-coupled.
medium

Registry sketch's getOrThrow contradicts the documented "unset → mock in dev" default

§11 AD-3 vs FR-BE2, §9
getOrThrow throws at boot on the documented dev path (var deliberately unset); the sketch also lacks the NODE_ENV=test short-circuit FR-BE2 requires.
Fix: resolve a default (isProduction ? 'msg91' : 'mock'), short-circuit test env, and validate the resolved key against the registry with a named config error.
medium

No cross-field env validation — msg91 with a missing auth key is a runtime login outage, not a boot error

§4.1 FR-BE3
Nothing requires MSG91_AUTH_KEY/MSG91_OTP_TEMPLATE_ID to be present when SMS_DELIVERY_PROVIDER=msg91. A manual flip with a typo'd key passes Joi and boots cleanly; every login then 502s in production.
Fix: Joi cross-field rule — msg91 requires a non-empty auth key and template ID; the app refuses to boot otherwise.
medium

FR-BE4's delete-on-failure races the 4s timeout — the user receives a code whose session was just deleted

§4.1 FR-BE4 + FR-BE1
AbortSignal.timeout(4000) aborts locally, but MSG91 may have already dispatched. The session is deleted; the user then receives a real SMS whose correct code returns OTP_EXPIRED — and re-requesting burns another rate-limit slot and ₹0.20–0.25. No test covers the deletion path (it falls between FR-T1 and FR-T2).
Fix: on timeout, keep the session (the SMS may still arrive) and log for diagnosis; on definite pre-dispatch failure, delete. Pin the chosen semantics with a test.
medium

FR-BE6's "exactly as written" inherits a TTL-reset bug — every failed verify extends the session by 5 minutes

§4.2 FR-BE6 (auth.service.ts:147)
The failure path re-stores the session with the full 300s TTL, so up to ~25 minutes of life vs the DLT template's "Valid for 5 minutes" promise; the response's expires_at (computed once at send) diverges from actual expiry after any failed attempt.
Fix: on failure, re-store with the remaining TTL; add a test asserting a session never outlives its advertised expires_at.
medium

The rate limiter's get→set increment is non-atomic — and it now caps real SMS spend

§2 table, FR-BE4 (in-memory-otp-session.store.ts:53)
Two concurrent sends can both read count=N and both write N+1. The code's own "not atomic; Phase 2 Redis" caveat never made it into the PRD's gap analysis, and §5 dismisses Redis on instance-count grounds, not atomicity grounds.
Fix: serialize per-E.164 with an in-process per-key promise chain, or explicitly accept the race with a stated bound ("worst case ~2× cap per burst").
medium

Deploys and restarts silently wipe in-flight OTP sessions on a single instance — real users will hit it

§5 Non-Goals, §6 Assumption
The Redis framing is multi-instance, but the failure triggers on a single instance too: every Render deploy restarts the process mid-flow; idle spin-down wipes sessions and rate counters. Post-launch, "SMS arrives → deploy lands → user types code" returns OTP_EXPIRED.
Fix: an accepted-risk paragraph in §6 naming restart invalidation of in-flight sessions and reset rate windows; time deploys/flip at low traffic.
medium

templateId is never pinned as DLT ID vs MSG91-panel ID — the API call, env var, and ops sheet can each mean something different

§8 step 5, §4.1 FR-BE1/FR-BE3, §10.4
Which string MSG91's v5 send call accepts depends on how the template was created in their panel; the PRD uses "DLT template ID" and MSG91_OTP_TEMPLATE_ID interchangeably, and §10.4's table records only the DLT ID.
Fix: pin that MSG91_OTP_TEMPLATE_ID is exactly the string that succeeded in §8's "Test DLT" run; add a "value that worked in Test DLT" column to the ops fill-in table.
medium

T1 hardcodes "Valid for 5 minutes" while the TTL is an adjustable code constant

§8 step 3, §10.1 T1, FR-BE1
Approved templates cannot be edited. If OTP_TTL_SECONDS is ever tuned, the SMS copy and actual expiry diverge — the template lies or the code does.
Fix: a guard note at the T1 block ("TTL constant is coupled to the approved wording; change both in one change-set or never") plus a test pinning the constant.
medium

§7's metrics have no instrumentation behind them (overlaps rubric medium on the 98% metric)

§7, §4
Measuring ≥98% or ~5 s delivery requires recording send attempts, provider outcomes, and verification outcomes; no FR produces that data — the only prescribed logging change removes a log line.
Fix: an FR for structured delivery-outcome logging (provider, outcome, duration, MSG91 response type — no new PII) sufficient to compute §7 by log query; plus a weekly manual wallet-balance check during launch.
medium

FE 45s resend timer vs the 5/10-min limiter — hitting 429 becomes a normal user path with real SMS, and FR-FE3 doesn't cover it

§2 table, §4.3 FR-FE3
Resend-until-arrival at the screen's cadence hits the ceiling in ~3–4 minutes of screen time. The only FE change (FR-FE3) handles OTP_SEND_FAILED and leaves the existing 429 path untouched — with real delivery, the app invites users into a 10-minute hard block with an unexplained error.
Fix: extend FR-FE3 to handle RATE_LIMIT_EXCEEDED with a countdown derived from the backend's Retry-After; or at minimum record a check that the existing 429 copy renders acceptably.
