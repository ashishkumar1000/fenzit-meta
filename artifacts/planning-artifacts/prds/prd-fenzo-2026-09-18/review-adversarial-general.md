# Adversarial Review — PRD: Real OTP Delivery via MSG91 SMS (DLT) (2026-09-18)

Lens: adversarial (`bmad-review/references/lens-adversarial.md`). Findings are
descriptions only — no severity ranking. Each finding cites the PRD section and
quotes the load-bearing phrase; triggers and consequences are concrete. Backend
code references verified against
`workspace/core/backend/fenzit-be/src/auth/` as of 2026-09-18.

---

## Findings

### 1. OTP is still generated with `Math.random()` — verification is becoming real, but the code itself is not cryptographically random

- **location**: PRD §2 "Wired and working" table, row "OTP generation + bcrypt hash" ("6-digit random, bcrypt cost 10"); FR-BE6 (§4.2). Source: `fenzit-be/src/auth/auth.service.ts:84` — `Math.floor(100000 + Math.random() * 900000)`.
- **trigger_condition**: The PRD's whole security story is "verification is now real: `bcrypt.compare` enforced" (§7). But the value being verified is produced by `Math.random()`, which is not a CSPRNG (V8 xorshift128+ — predictable from ~a few observed outputs). The PRD upgrades verification to a real security boundary while leaving generation as the mock-era convenience, and never mentions RNG anywhere.
- **guard_snippet**: Add an FR under §4.2: "OTP generation switches to `crypto.randomInt(100000, 1000000)`" (one-line change in `auth.service.ts:84`), with a note in FR-T1 asserting the generator is crypto-sourced (or at least documenting the decision to keep Math.random with its rationale, if deliberately deferred).
- **potential_consequence**: An attacker who can observe or infer the RNG state (same-process outputs are correlated) can predict other users' OTPs; `bcrypt.compare` then faithfully verifies a forged code. The headline metric "Wrong/absent OTP can no longer log anyone in" is achieved on paper while the actual entropy guarantee quietly stays at mock quality.

### 2. FR-BE5's mock-only `otp` field has no defined mechanism — and the two candidate mechanisms contradict each other

- **location**: PRD FR-BE5 (§4.1) ("The `sendOtp` response includes `otp` **only** when the active provider is the mock") vs §3.3 ("`NODE_ENV=development|test` → … the `otp` field remains in the `sendOtp` response") vs §11 anti-patterns ("❌ `if (provider === 'msg91')` anywhere outside the composition root").
- **trigger_condition**: To implement FR-BE5 literally, `AuthService.sendOtp` must know which provider is active — i.e. an `instanceof MockSmsDeliveryProvider` check or an injected "is mock" flag inside the service. That is exactly the provider-identity-in-service pattern the §11 checklist bans (the anti-pattern names msg91, but a mock-identity check is the same violation in spirit). The alternative — gate on `NODE_ENV` — contradicts FR-BE5's provider-based wording: §3.3 promises the field "remains in dev" even after dev keys are configured and `SMS_DELIVERY_PROVIDER=msg91`, while provider-based gating removes it. The PRD never picks one.
- **guard_snippet**: Replace FR-BE5's gating basis with an explicit environment/config gate the service can read without knowing the provider: e.g. a validated `EXPOSE_DEV_OTP` env var (default false, set true only in dev/test compose and CI), or gate on `NODE_ENV !== 'production'`. State in FR-BE5 that the mock provider itself does the logging (it already logs the code at `mock-otp-delivery.provider.ts:10`) and the service-level log at `auth.service.ts:99` is deleted, not gated.
- **potential_consequence**: The implementer either adds a banned provider-identity check in the service (eroding the §11 contract the PRD just locked in) or wires NODE_ENV gating that silently diverges from the FR text; reviewers then "fix" it in whichever direction they read first, and the dev-banner behaviour flips between environments with no spec to arbitrate.

### 3. Deployment step 1 puts production on the mock provider — plaintext OTP in production API responses is scheduled, not prevented

- **location**: PRD §9 step 1 ("lands with `SMS_DELIVERY_PROVIDER=mock` … no FE breakage — the `otp` response field still exists in dev") combined with FR-BE5 ("In production the field is absent") and §7 ("No plaintext OTP in any production API response or log line").
- **trigger_condition**: FR-BE5 gates the `otp` field on the *active provider*, not on the environment. §9 step 1 explicitly instructs the Render production environment to run with `SMS_DELIVERY_PROVIDER=mock` until step 3's config flip. During that window (which spans DLT header + template approval — 1–3 + 24–72 h minimum), every production `POST /auth/otp/send` returns the plaintext OTP and logs it, with real verification now on.
- **guard_snippet**: Either (a) change §9 step 1 to keep the field out of production by gating on environment rather than provider (see finding 2), accepting that internal testers get the code from server logs; or (b) state the window explicitly in §9 and §7 ("metric holds after step 3; between steps 1 and 3 prod responses carry the OTP because the mock provider is active") and add an acceptance check at the step-3 flip (assert response body has no `otp` key).
- **potential_consequence**: The PRD's §7 success metric is false for its own prescribed rollout; "manual prod check" (§7) is the only thing standing between the window and ship, and nothing in the doc reminds anyone the field must disappear at the flip.

### 4. The port signature `send(to, templateId, variables)` cannot deliver T3/T4 — FR-BE1 forwards only `variables[0]` and the chosen MSG91 endpoint is OTP-specific

- **location**: PRD FR-BE1 (§4.1) ("`otp` (`variables[0]` — our backend-generated code)") vs §10.1 T3 ("New job {#var#} ({#var#}) is scheduled for {#var#}") and T4 ("Update for job {#var#}: {#var#} by {#var#}") vs AD-1/AD-5 (§11) ("every message type (T1 OTP, T2 invite, T3 job assigned …) calls the same port with its own template ID and variables") vs AD-2 ("How a given provider handles message kinds internally — e.g. MSG91's OTP endpoint vs its transactional SMS endpoint — is vendor detail").
- **trigger_condition**: FR-BE1 hardwires the adapter to MSG91's v5 `/otp` endpoint, which carries exactly one `otp` param — so `variables[1]` and `variables[2]` have nowhere to go. T3 and T4 need three variables. AD-2 says the OTP-vs-transactional endpoint choice is "vendor detail inside the adapter", but the port call `send(to, templateId, variables)` carries no information from which the adapter could decide which endpoint to use, and no FR covers the transactional path at all. The "one adapter serves every message type" architecture (AD-5) is asserted but not implementable with the shape FR-BE1 specifies.
- **guard_snippet**: Either (a) add a note to FR-BE1/AD-2 that MSG91's transactional/flow endpoint is a second method or second adapter to be designed when T2–T5 backend work starts, with the port's single method acknowledged as OTP-shaped for now (and rename the claim accordingly); or (b) specify how the adapter selects the endpoint (e.g. a second registry key per template, or the variables payload mapped to the flow API's `#MSG91VAR#` mechanism) before the §10 batch registration is handed to ops.
- **potential_consequence**: When T2–T5 backend work starts against the frozen port (AD-1: "The port signature is frozen"), the implementer discovers the adapter silently drops variables 2–3 on T3/T4 — either undelivered-variable SMS (garbled notifications to technicians/owners) or a port-shape debate that contradicts the PRD's "never a change to this one" promise.

### 5. T3 and T4 violate the DLT non-consecutive-variable rule the PRD claims is "baked into every template"

- **location**: PRD §10 preamble ("Rules baked into every template: `{#var#}` variables only, max 3 (ideally 1), **non-consecutive**, ≤30 characters per variable value") vs T3 content (`New job {#var#} ({#var#}) is scheduled for {#var#}.`) and T4 content (`Update for job {#var#}: {#var#} by {#var#}.`); same content in the ops one-pager (`ops-dlt-sms-template-registration-2026-09-18.md`, rules §"Rules that cause rejection" and templates T3/T4).
- **trigger_condition**: In T3, variable 1 and variable 2 are adjacent — separated only by the literal " (" — and in T4, variables 1 and 2 are separated only by ": ". DLT operators reject templates where variables sit back-to-back with no fixed text between them (the rule the PRD itself cites via the Exotel reference in §12 and restates in §8: "max 2–3 **non-consecutive** variables"). Both launch-set templates contradict the stated invariant in the same document that states it.
- **guard_snippet**: Rewrite T3 and T4 so every pair of variables has real fixed text between them, e.g. T3: `New job {#var#} for {#var#} service is scheduled for {#var#}. …` and T4: `Job {#var#} update: status {#var#}, technician {#var#}. …` — then re-check the ≤30-char budget for the shifted variables, and mirror the fix into the ops one-pager before the batch is submitted.
- **potential_consequence**: T3 and/or T4 get rejected at Trueconnect, or worse, approved inconsistently and then fail message-level scrubbing at send time; the batch-registration plan ("register T1–T5 together in one batch", §8) burns its one shot and forces re-registration cycles that cannot be edited after approval.

### 6. The AD-3 registry sketch uses `getOrThrow('SMS_DELIVERY_PROVIDER')`, contradicting the "unset → mock in dev" behaviour FR-BE2 and §9 promise

- **location**: PRD §11 AD-3 sketch (`new SMS_PROVIDER_REGISTRY[config.getOrThrow('SMS_DELIVERY_PROVIDER')]()`) vs FR-BE2 (§4.1) ("otherwise `SMS_DELIVERY_PROVIDER=mock|msg91` decides (default `msg91` in production, `mock` in development until keys are configured)") vs §9 step 1 ("lands with `SMS_DELIVERY_PROVIDER=mock` (or unset → mock in dev)").
- **trigger_condition**: `getOrThrow` on an unset var throws at module load. In a dev environment where the var is deliberately unset (the documented default path), the app crashes at boot instead of selecting the mock. The sketch also has no production-default resolution and no `NODE_ENV=test` branch that FR-BE2 requires.
- **guard_snippet**: Amend the sketch to resolve a default: `const key = config.get('SMS_DELIVERY_PROVIDER') ?? (isProduction ? 'msg91' : 'mock')`, with the `NODE_ENV=test → mock` short-circuit above it, and validate the resolved key against the registry (throw a config error naming the bad value, not a bare undefined lookup).
- **potential_consequence**: The first dev boot after implementing the sketch crashes with an opaque DI/config error; or the implementer patches it ad hoc and the "default msg91 in production" rule drifts from what any test or doc says.

### 7. No conditional env validation — `SMS_DELIVERY_PROVIDER=msg91` without auth key / template ID is discovered as a runtime login outage, not at boot

- **location**: PRD FR-BE3 (§4.1) ("New env vars in the Joi schema (`app.module.ts`) + `.env.example` + `render.yaml`: `MSG91_AUTH_KEY`, `MSG91_OTP_TEMPLATE_ID`, `SMS_DELIVERY_PROVIDER`") and FR-BE4's `502 OTP_SEND_FAILED`.
- **trigger_condition**: The PRD adds the three vars to the Joi schema but specifies no cross-field rule: nothing requires `MSG91_AUTH_KEY` and `MSG91_OTP_TEMPLATE_ID` to be present when `SMS_DELIVERY_PROVIDER=msg91`. The step-3 config flip (§8 step 6) is a manual Render change; a flip with a typo'd or missing key passes Joi (all three vars are individually optional) and boots cleanly.
- **guard_snippet**: Add to FR-BE3: "Joi schema validates cross-field: when `SMS_DELIVERY_PROVIDER=msg91`, `MSG91_AUTH_KEY` and `MSG91_OTP_TEMPLATE_ID` are required (and `MSG91_AUTH_KEY` non-empty); the app refuses to boot otherwise." Optionally add a startup health log line from `Msg91SmsDeliveryProvider` constructor confirming the template ID is non-empty.
- **potential_consequence**: Every `POST /auth/otp/send` in production 502s with `OTP_SEND_FAILED` — a total login outage for the whole app, discovered only when the first real user tries to sign up after the flip.

### 8. FR-BE4's delete-on-failure has a timeout race: MSG91 can dispatch after the adapter's 4s AbortSignal fires, so the user receives a code whose session no longer exists

- **location**: PRD FR-BE4 (§4.1) ("if the MSG91 call throws or returns a non-success response, the just-created session is deleted") with FR-BE1's "timeout via `AbortSignal.timeout(4000)`"; journey §3.1 step 4 ("Expired/locked session → same `OTP_EXPIRED` … recovery").
- **trigger_condition**: `AbortSignal.timeout(4000)` aborts the fetch locally, but MSG91 may have already accepted and dispatched the SMS. The adapter throws (abort), FR-BE4 deletes the session, the user then receives a real SMS containing the OTP — and typing that (correct) code returns `OTP_EXPIRED`. FR-T2 only tests request building and error mapping; no test covers the deletion path at all (FR-T1 covers service paths, FR-T2 covers adapter paths — the interaction falls between them).
- **guard_snippet**: Add to FR-BE4: "deletion happens only when failure is determined *before* the request could have been dispatched (connection error, non-success body read); on timeout, keep the session (the SMS may still arrive) and log for diagnosis" — or accept the race explicitly and add an FR-T4: "provider failure deletes the session" plus "timeout keeps the session", so the chosen semantics are pinned by a test.
- **potential_consequence**: During MSG91 latency spikes the user experiences the worst possible loop: SMS arrives, correct code rejected as expired, re-request burns another rate-limit slot and sends a second SMS — each occurrence consuming ₹0.20–0.25 of wallet and eroding the ≥98% success metric with no test or doc explaining it.

### 9. FR-BE6 "activating the existing attempt-increment and lockout logic exactly as written" inherits a TTL-reset bug: every failed verify extends the session by the full 5 minutes

- **location**: PRD FR-BE6 (§4.2) ("activating the existing attempt-increment and lockout logic **exactly as written**"). Source: `auth.service.ts:147` — `await this.otpSessionStore.set(otpSessionId, session, OTP_TTL_SECONDS);` on the failure path.
- **trigger_condition**: The failure path re-stores the session with the *full* `OTP_TTL_SECONDS` (300s), resetting the expiry clock. Each wrong attempt buys another 5 minutes of session life. The lockout caps attempts at 5, but the session (and its still-valid correct code) lives up to ~25 minutes instead of the 5 the DLT template text ("Valid for 5 minutes", §10 T1) and the API's `expires_at` claim. Note `expires_at` is computed once at send (§2, `auth.service.ts:101-103`) and is never updated — so the response's `expires_at` disagrees with the session's actual expiry after any failed attempt.
- **guard_snippet**: Amend FR-BE6: "on a failed attempt, re-store the session with its *remaining* TTL (or track `expiresAt` in the session and pass the delta), keeping the response `expires_at` truthful; add a `FR-T1` case asserting a session does not outlive its advertised `expires_at`."
- **potential_consequence**: A brute-forcer gets up to 25 minutes per session rather than 5; and a user whose `expires_at` has passed can still verify successfully (or be rejected inconsistently), because the two notions of expiry diverge — with a DLT template and UI copy both promising 5 minutes.

### 10. The rate limiter's get→set increment is non-atomic, and the PRD leans on it to cap both abuse and real SMS spend

- **location**: PRD §2 table ("Rate limiting (5 sends / 10 min per number, 429 + Retry-After) … Working") and FR-BE4 ("The rate-limit counter already having incremented is accepted (prevents bypassing the limit via a failing provider)"). Source: `in-memory-otp-session.store.ts:53` — "Note: this get→set is not atomic; Phase 2 Redis migration should use INCRBY instead."
- **trigger_condition**: Two concurrent `sendOtp` calls for the same number both read count=N and both write N+1 — the cap can be exceeded, and it is now attached to real money (§6: ~₹0.20–0.25 per SMS + GST, wallet prepay) instead of a mock log line. The PRD declares the limiter "Working" without carrying the code's own caveat into the gap analysis, and the non-goal §5 ("Redis-backed OTP session store … only needed for multi-instance") dismisses Redis on instance-count grounds, not on atomicity grounds.
- **guard_snippet**: Add a gap/FR noting the limiter's known non-atomicity, and either (a) serialize per-E.164 via an in-process per-key mutex/promise chain in the in-memory store (cheap, no Redis), or (b) explicitly accept the race with a stated bound ("worst case ~2× cap per burst") so the SMS-spend exposure is a decision, not an oversight.
- **potential_consequence**: A scripted burst of parallel sends slips past 5/10-min and drains the MSG91 wallet faster than the PRD's abuse model assumes; the "attempts that respect the rate limit" framing in §7 never notices the limit itself is soft.

### 11. In-memory store + single Render instance: deploys, restarts, and idle spin-down silently wipe in-flight OTP sessions and reset rate limits once real users depend on it

- **location**: PRD §5 Non-Goals ("Redis-backed OTP session store — only needed for multi-instance deployment; single Render instance today") and §6 Assumption ("single backend instance (in-memory session store sufficient)").
- **trigger_condition**: The Redis framing is multi-instance, but the live-OTP failure triggers on a *single* instance too: every Render deploy restarts the process (wiping all unexpired sessions mid-flow), and if the service runs on a tier with idle spin-down, a 15-min-quiet period wipes sessions and rate counters. Post-launch, "send SMS → app deploy lands → user types code" returns `OTP_EXPIRED` for codes the user received seconds ago. Rate-limit windows also reset on restart, softening the throttle (compounding finding 10).
- **guard_snippet**: Add an accepted-risk paragraph to §6: "process restarts invalidate all in-flight OTP sessions and reset rate windows; deploys during active signups produce `OTP_EXPIRED` for just-received codes — accepted for launch, revisit if deploy cadence × traffic makes it visible." Optionally add a deploy-order note: flip config (§9 step 3) at low-traffic times, since the flip itself restarts nothing but deploys around it do.
- **potential_consequence**: The §7 metric "OTP SMS delivered within ~5 s" and "≥ 98% end-to-end success" both degrade in ways nobody attributes to store volatility; support sees "my code says expired" reports clustered around deploys with no runbook explanation.

### 12. `templateId` is never defined as DLT ID vs MSG91-panel ID — the API call, the env var, and the ops sheet can each mean something different

- **location**: PRD §8 step 5 ("create the template in MSG91 … pasting the **DLT template ID**"), FR-BE1 (`query: template_id (DLT-approved template mapped in the MSG91 panel)`), FR-BE3 (`MSG91_OTP_TEMPLATE_ID`), and §10.4 step 2 ("paste the DLT template ID + exact approved content").
- **trigger_condition**: MSG91's panel creates its own template records for DLT-mapped content; whether its v5 `/otp` call expects the MSG91-internal template ID or the raw DLT ID depends on how the template was created (the PRD's own references distinguish "map your DLT entity" from "create template … to send via API"). The PRD uses "DLT template ID" and `MSG91_OTP_TEMPLATE_ID` interchangeably without pinning which string the HTTP call must carry, and §10.4's fill-in table records only the DLT ID.
- **guard_snippet**: Add one sentence to FR-BE1 or §8 step 5: "the value configured in `MSG91_OTP_TEMPLATE_ID` is exactly the string MSG91's v5 send call accepts — captured during §8 step 5's 'Test DLT' run, not assumed from the Trueconnect approval." Extend §10.4's fill-in table with a "value that worked in Test DLT" column.
- **potential_consequence**: The config flip (§9 step 3) goes live with the wrong identifier flavor; every send fails (MSG91 error mapped to `502 OTP_SEND_FAILED`) — a login outage that only appears in production, on a day the ops sheet already said "record the DLT template ID back into this sheet" as if that were the whole contract.

### 13. DLT template T1 hardcodes "Valid for 5 minutes" while the TTL is a code constant the PRD treats as adjustable

- **location**: PRD §8 step 3 / §10.1 T1 content ("Valid for 5 minutes."), FR-BE1 (`otp_expiry` (5, matching `OTP_TTL_SECONDS)`), §2 (`OTP_TTL_SECONDS = 300` at `auth.service.ts:36`).
- **trigger_condition**: The 5-minute TTL is a code constant plus an `otp_expiry` param; the DLT template's fixed text repeats it; approved templates "cannot be edited after approval" (§10 preamble). If `OTP_TTL_SECONDS` is ever tuned (e.g. 10 minutes to cut resend rates), the SMS keeps promising 5 minutes, and the UI's `expires_at` countdown tells the truth while the message lies — or vice versa if only the template's copy is regenerated.
- **guard_snippet**: Add a guard note next to the T1 registration block: "`OTP_TTL_SECONDS` is coupled to the approved T1 wording ('Valid for 5 minutes') — changing the constant requires re-registering T1 as a new template; treat the constant as frozen or change both in the same change-set." Consider a unit test asserting `OTP_TTL_SECONDS === 300` with a message pointing at this coupling.
- **potential_consequence**: A well-meaning TTL change ships with a stale DLT template (or vice versa); users receive codes that expire at a different time than the SMS claims, generating support load and failed first-verification attempts that the PRD's metrics would misattribute to MSG91 delivery.

### 14. T2–T5 are handed to ops as a "launch set — register together" but no FR covers any of their backend sending; T4 presumes a whole new worker component

- **location**: PRD §8 closing note ("the ops team should register T1–T5 (the launch set) together in one batch") and §10.1 T4 ("Backend: SMS worker subscribes to `notifications` inserts (the table is already the designed Phase-2 outbox) rather than new calls inside services").
- **trigger_condition**: The PRD's functional requirements (§4) cover only T1. T2 (`inviteTechnician` SMS), T3/T5 (job-event sends), and T4's `notifications`-insert subscriber are all unimplemented and undesigned — the "SMS worker" is a new architectural component (polling? LISTEN/NOTIFY? Supabase Realtime?) that appears only as a parenthetical in an ops-facing section. Meanwhile templates are approved un-editable, and the exact wording depends on backend formatting choices (date formats, status labels, truncation) that don't exist yet.
- **guard_snippet**: Either (a) scope T2–T5 registration explicitly as "ops may register now, backend wiring is a separate future PRD/story" with that sentence in §8 and §10, plus a note in the fill-in table that IDs must be stored until the sending work starts; or (b) cut T2–T5 from the batch and register T1 alone now (approval is per-template, not per-batch-coupled).
- **potential_consequence**: Approved-but-unwired templates age while the eventual backend design drifts (e.g. T4's status labels or T3's date format change during implementation), forcing re-registration of "final-candidate" copy; or the T4 worker gets built ad hoc inside whatever service touches `notifications`, against the PRD's own AD-style discipline.

### 15. §7's success metrics have no instrumentation behind them — nothing in the FRs produces the data the metrics need

- **location**: PRD §7 ("End-to-end signup … success rate ≥ 98% of attempts that respect the rate limit", "OTP SMS delivered within ~5 s") and FR-BE4's `502 OTP_SEND_FAILED` (the only new failure signal).
- **trigger_condition**: Measuring a ≥98% success rate or a ~5 s delivery requires recording send attempts, provider outcomes, and verification outcomes. No FR adds logging, metrics, or an audit field; the only prescribed logging change (FR-BE5) *removes* a log line. MSG91 wallet balance, per-template failure rates, and delivery latency are equally untracked, despite §6 making SMS spend pay-as-you-go.
- **guard_snippet**: Add a small FR: "FR-BE8: delivery outcomes are logged (structured, no PII beyond the E.164 already logged today): provider name, outcome (ok/timeout/error), duration, and MSG91 response type — sufficient to compute §7's metrics by log query; plus one weekly manual check of the MSG91 wallet balance during the launch window."
- **potential_consequence**: The first month of real OTP delivery runs on vibes: a degraded MSG91 route or an expiring wallet balance shows up only as user reports and "manual prod checks", while the PRD's numeric success criteria remain unfalsifiable.

### 16. The FE resend timer (45 s) is tuned against a limiter that rejects after 5 sends/10 min — with real SMS, hitting the ceiling becomes a normal user path, and FR-FE3 doesn't cover it

- **location**: PRD §2 table ("FE OTP screen (6-digit input, 45s resend) … Working"), §4.3 (FR-FE3 adds handling only for `OTP_SEND_FAILED`), and FR-BE2/§4.1 rate limit (5 sends / 10 min → 429 `RATE_LIMIT_EXCEEDED` + Retry-After).
- **trigger_condition**: A user who requests and resends at the screen's cadence hits the 429 ceiling in ~4 minutes of screen time (5 sends at 45 s spacing ≈ 3 minutes). Once real delivery is live, resend-until-arrival is a natural behaviour (slow carrier routes, finding 8's expired-then-resend loop), so 429s stop being an edge case. The PRD's only FE change (FR-FE3) adds retry copy for a *different* error code and leaves the existing 429 path untouched.
- **guard_snippet**: Extend FR-FE3: "handle `RATE_LIMIT_EXCEEDED` on the OTP screen with a countdown derived from the `Retry-After` value (already returned by the backend) and resend disabled for that window"; or at minimum verify the existing `sendOtpErrorMessage` path renders the 429 message acceptably and record that check in FR-FE4's "contract is stable" claim.
- **potential_consequence**: With the mock, an over-eager tester just sees a raw error; with real delivery, the app's own UI invites the user into a 10-minute hard block with an unexplained error state — surfacing as the dominant support ticket in the launch week even though delivery itself works.
