# PRD Quality Review — Attendance & Leave (prd-Fenzo-attendance-2026-09-25)

## Overall verdict
This is a solid, build-oriented PRD. The decisions are firm, the scope is honest, the security and server-authority NFRs fit this product, and nearly every FR has testable consequences. Two things are at risk. First, the Day status engine (FR-10), which every summary, metric and view depends on, has gaps in its precedence rules and an undefined "today, in progress" state. Second, the PRD never admits that in-app-only delivery weakens the reminders and the revoke flow, which carry SM-2, SM-4 and UJ-3. Fix those, confirm the assumptions that carry real weight, and it is ready for UX, architecture and stories.

## Decision-readiness — adequate
Decisions are written as decisions, not "considerations". For example: "Pending request never auto-expires" (FR-13), "Checkout missing (counts as 0.5)" (FR-10 rule 7), "iOS: there's no reliable mock signal … known limit" (FR-7). The memlog shows each one was actually discussed. Non-Goals and Out of Scope are concrete. A decision-maker could act on this.

What is missing is the cost of each choice. The PRD almost never says what was given up. Several choices put a burden on one party and this is not stated. Pending leave counts as Absent, so the Employee pays for the Owner's slowness, and this works against the §2.1 Employee JTBD "fair, visible record". Checkout missing = 0.5 is a fixed penalty or reward whatever the real hours were. A 100 m accuracy limit with a 50 m minimum Radius lets a fix pass even when its uncertainty is twice the Radius, which weakens the Owner "trust" JTBD. §9 says "None open", and there is not a single `[NOTE FOR PM]` anywhere. The memlog marks some product rules as "(Claude's call)", but the PRD presents them as confirmed.

### Findings
- **[high]** Agent-made product rules shown as confirmed decisions (§4.5 FR-14, §5 NFR-10) — The memlog says "Revoke/cancel of today's leave allowed only before Office Start time (Claude's call)" and "Push waves … (Claude's call)". FR-14 states the Start-time cut-off as settled fact, with no `[ASSUMPTION]` tag and no Index entry. This rule decides whether the Employee or the Owner wins a same-day dispute. *Fix:* Tag FR-14's "Today can also be revoked if the Owner acts before the Office Start time" and the NFR-10 wave split as `[ASSUMPTION]`, add them to §10, or get explicit user confirmation.
- **[medium]** Trade-offs in the core rules are not named (§4.4 FR-10 rules 7–8, §4.3 FR-7) — "Pending … count as Absent", "Checkout missing … 0.5" and "accuracy worse than 100 m" against "Radius range is 50–1000 m" are each presented without the downside. *Fix:* Add one line per rule on who it disadvantages and why that is acceptable. Or add a `[NOTE FOR PM]` where the tension with the "fair record" and "trust" JTBDs is real, especially accuracy > Radius.
- **[low]** "Open Questions: None open" hides open items (§9) — There are about 20 `[ASSUMPTION]` tags, plus two architecture decisions deferred in the addendum (A2 map library/key, A5 nightly job vs compute-on-read). *Fix:* Point §9 to the few assumptions that need a product answer, not just "confirmation".

## Substance over theater — strong
There is no furniture. The personas (Rakesh, Priya, Arjun) each drive specific rules: multi-office, Late + reminder timing, partial revoke. The JTBDs split cleanly into Owner and Employee and map to FRs. The Vision is specific to this product ("paper, WhatsApp or memory", "only do it while physically at their office"), not category boilerplate. The NFRs carry real thresholds and domain-specific rules (NFR-2 server authority, NFR-4 named constraints, NFR-5 UTC + IANA). There is no differentiation section pretending to be novel.

### Findings
- **[low]** NFR-9 uses an adjective, not a bound (§5 NFR-9) — "Logs never contain raw coordinates beyond what's needed for debugging" contradicts itself: it says never, then allows some. *Fix:* State the rule: for example, coordinates are logged only in the rejected-attempt table, never in app or request logs, and rounded to N decimals if logged at all.

## Strategic coherence — adequate
The thesis is clear: "simple, trustworthy" attendance inside the job app, with server-verified location. The features follow it: geofenced check-in, fake-GPS, audit trail, month view. Scope is problem-solving MVP, and the cuts (payroll, quota, push, export) follow from the thesis. Counter-metrics exist and are well chosen. SM-C1 guards the trust thesis against loosening validation to lift SM-2.

The weak point is the link between the metrics and the delivery channel. SM-2 and SM-4 list FR-23 Reminders as a driver. But FR-23 admits that reminders are "only seen when the app is opened", and UJ-2 is written as if Priya "gets" the 18:22 reminder in time. The same gap breaks UJ-3: a revoke is in-app only, so Arjun may never see "Revoked (Thu–Fri)" before Thursday. He would then be marked Absent, which is exactly the dispute the Vision promises to end. SM-1 also cannot be measured as written.

### Findings
- **[high]** No-push gap undercuts UJ-2, UJ-3, SM-2 and SM-4, and is not acknowledged (§2.3 UJ-2 Resolution, UJ-3 Climax/Resolution, §4.9 FR-23, §8 SM-2/SM-4, §7.2) — "Priya gets an in-app 'You haven't checked out' reminder" and "Arjun checks in on Thursday as normal" both assume the user sees an in-app Notification without opening the app. §7.2 defers push with no note on this cost. *Fix:* Either (a) add a `[NOTE FOR PM]` stating that reminders and revokes depend on the app being opened, and adjust the UJ-2/UJ-3 wording and the SM-2/SM-4 attribution, or (b) set a minimum notice rule for revoke (for example, revoke of tomorrow must happen before X). Otherwise, bring Wave-1 push into scope.
- **[medium]** SM-1 denominator cannot be computed (§8 SM-1) — "% of active tenants with ≥ 1 non-field Employee". The Glossary says office staff "are technicians in the system", so there is no field vs non-field attribute to count. *Fix:* Redefine the denominator using data that exists (for example, active tenants with ≥ N technicians), or add a way to capture it.
- **[low]** No metric for the Employee-side thesis (§2.1 Employee emotional JTBD, §8) — "Fair, visible record … not disputed" has no signal. SM-5 (corrections) is Owner-side data quality. *Fix:* Optional. Add a secondary metric such as Revoke rate, or the share of Absent days later converted by correction.

## Done-ness clarity — thin
Most FRs are strong. FR-5, FR-7, FR-12 and FR-13 have precise, testable consequences, with exact messages, ranges and idempotency. But the rubric asks us to be unforgiving here, and the core engine has holes. FR-10 is the rule set that every view, summary and metric depends on. Several real combinations fall through its precedence, and the "exactly one Day status" consequence is false for today. Three view FRs have little or no acceptance.

### Findings
- **[critical]** FR-10 precedence has undefined combinations (§4.4 FR-10) — (1) Half-day leave + Check-in with no Check-out: rule 5 needs Worked hours, which don't exist, and rule 7 (Checkout missing, 0.5) comes later, so the result is undefined. (2) Weekly off/Holiday + Check-in with no Check-out: rule 2 says "Worked on holiday (with Worked hours)", but there are no hours, and FR-23 sends no checkout reminder on those days. (3) Worked on holiday has no Hours rules, so a 5-minute Sunday check-in counts the same as 9 hours. (4) Pending leave covering today when the Employee checks in: FR-9 only handles Approved leave. Approving it later goes against rule 4 "(no Check-in)", and the Working-day count is undefined. *Fix:* Add explicit rows for each combination to FR-10 (a small truth table is best), and a consequence for "Pending leave + Check-in".
- **[high]** Today-in-progress has no Day status (§4.4 FR-10 rule 9, §3 Day status) — Rule 9 introduces "Not checked in yet", which is not in the Glossary's list of 10 statuses. There is also no status for "checked in, not yet checked out, before midnight". Yet the consequence says "Every Tracked employee-date has exactly one Day status". FR-24 and FR-26 must show exactly this state. *Fix:* Add provisional statuses (for example, "Not checked in yet" and "Checked in") to the Glossary as non-final, and say they are excluded from Days worked until midnight.
- **[medium]** Pending leave with some dates already passed has no cancel rule (§4.5 FR-15) — "Pending → Cancelled entirely, if no date has passed". FR-12 allows back-dated and in-progress Pending requests, and those never expire (FR-13). Nothing says what Cancel does for them. *Fix:* State whether the passed dates can be withdrawn (likely yes, since they are not yet approved) or whether a split applies.
- **[medium]** Reminder timing is unclear for on-time check-ins (§4.9 FR-23 row 2) — "End time + actual minutes late". Late is only set after Start time + Late cut-off (§3). For a check-in at 10:10 with a 15 min cut-off, the reminder could be at 18:00 or 18:10. Early check-ins are also not covered. *Fix:* Define it as "End time + max(0, Check-in − Start time)", or as "End time + Late minutes (0 if not Late)".
- **[medium]** FR-24, FR-17 and FR-26 have little or no acceptance (§4.5 FR-17, §4.10 FR-24, FR-26) — FR-24 has no Consequences block. It doesn't say whether the snapshot updates in real time (UJ-2 says "the owner's dashboard shows the same"), or how "Late" and "on leave" handle half-day leave. FR-17 has none. FR-26 has only the access rule, while FR-25 gets loading/empty/error states. *Fix:* Add consequences: refresh behaviour, counting rules, loading/empty/error states (NFR-8 applies generally, but the stories will want it per FR), and the sort order of the Pending queue.
- **[low]** FR-18 effective date: past dates allowed? (§4.6 FR-18, §4.4 FR-10) — "effective from a date the Owner picks (default today)". If a past date is allowed, FR-10's "do not recompute dates before their effective date" still leaves the dates between the effective date and today unclear. *Fix:* Limit it to today or later, or say that the dates from the effective date to today are recomputed.
- **[low]** "7 days back" unit (§4.5 FR-12) — Calendar days or Working days? *Fix:* Say "7 calendar days before today (Tenant timezone)".

## Scope honesty — strong
Omissions are explicit and specific: §6 Non-Goals, §7.2 (13 items), and per-feature "Out of Scope" lines under FR-9, FR-20 and FR-27. There is an `[ASSUMPTION]` on almost every inferred value, and the index round-trips. De-scoping is done openly (export, push, iOS fake-GPS with the reason). The number of open items (about 20 assumptions, 0 NOTE FOR PM) is fair for a build PRD. Most are low-risk defaults. FR-9 half-day, FR-11 Worked-on-holiday handling and FR-20 holiday removal change the numbers and should be confirmed before story creation.

### Findings
- **[medium]** Lifecycle edges for disabled Employees are silent (§4.1 FR-2, FR-3) — What happens to a Pending or future Approved leave when an Employee is disabled? Is an Office required when re-enabling or bulk-enabling ("enable attendance for all", FR-2, against "exactly one Office", FR-6)? *Fix:* Add consequences: for example, pending requests are auto-cancelled with an Owner notice, and bulk enable asks for an Office per Employee or a default Office.
- **[medium]** Location data retention and consent are not stated (§5 NFR-11, FR-7) — Coordinates are stored with every Check-in and every fake-location attempt, but no retention period is given. The only consent step is "told this during onboarding". For Indian tenants (DPDP Act 2023), employee location is personal data. *Fix:* State the retention period (or "kept while the tenant is active") and what the onboarding notice must say. Or mark it `[NON-GOAL for MVP]` with a `[NOTE FOR PM]` if this was deliberately deferred.
- **[low]** Missing notifications are not declared as intentional (§4.9 FR-22) — There is no Notification when an Employee is enabled or disabled, reassigned to another Office, has their Weekly off changed, or has a correction made. Their absence may be deliberate, but it isn't stated. *Fix:* Add one line: "No Notification for enablement, reassignment, Weekly off change or correction in v1" (or add them).
- **[low]** Tenant timezone has no setting surface (§3, §5 NFR-5) — The field is stored, with default IST, but no FR lets anyone change it. *Fix:* Say explicitly that it is not editable in v1 (it is set by the system).

## Downstream usability — adequate
This PRD sits at the top of the chain (UX → architecture → stories), so this dimension matters. There is a Glossary, and terms are mostly used consistently. The UJs have named protagonists. The FRs cite the UJs they realize. The addendum clearly separates feasibility from requirements, and its brownfield references checked out (`src/utils/distanceUtils.ts`, `react-native-nitro-geolocation ^1.4.3`, `react-native-webview` present and no map library, migration `20260920000008_notifications_job_id_nullable.sql`, pg_cron migrations, the `pushed_at` outbox). What drags it down: the UJ-4 example numbers, some flags and markers that are not in the Glossary, and numbering out of order.

### Findings
- **[medium]** UJ-4 summary numbers are impossible (§2.3 UJ-4) — "days worked 21.5, late 3, leave 2, weekly offs 8, holidays 1, worked on holiday 1, absent 0". With Sat+Sun offs (UJ-1), a 31-day month has about 22 Working days. But 21.5 Days worked needs at least 22 dates, plus 2 leave days, which is already more than 22 before counting the other statuses. Testers and UX will copy this example. *Fix:* Recompute a consistent example, for example: 30-day month, 8 weekly offs, 1 holiday, 21 Working days = 18.5 worked (17 Present + 3 half-value days) + 2 leave + 0.5 …, and state which month it is.
- **[medium]** Markers and flags are not in the Glossary or the grid spec (§4.3 FR-7, §4.4 FR-10 rule 8, §4.8 FR-21, §4.10 FR-25) — "Leave pending" marker, "Fake location attempt" flag, "Corrected by owner" and "manual" are each introduced once. FR-25's cell spec lists only "Day status and Late/Early flags". *Fix:* Add a Glossary entry "Day flags" listing Late, Early checkout, Leave pending, Fake location attempt and Corrected, and reference it from FR-24, FR-25 and FR-26.
- **[low]** UJ-1 step (1) cannot work as written (§2.3 UJ-1) — "drops a pin using his current location … then adds 'Thane' the same way". He can't be at both offices. *Fix:* Have Thane use address search or map drag. This also exercises the FR-5 paths (b) and (c).

## Shape fit — strong
This is a multi-stakeholder B2B mobile feature (Owner and Employee), so UJs are load-bearing, and there are five of them, which fits. It is brownfield, and the separation rule (NFR-12) plus the addendum's reuse/generalise/build tables show the right respect for existing code. It is not over-formalized. UJ-4 and UJ-5 are shorter, which suits their simpler flows. No findings.

## Mechanical notes
- **ID ordering:** FR-27 sits between FR-23 and FR-24 (§4.9). NFR-12 comes before NFR-11 (§5). The IDs are unique and have no gaps, but the order is off. Renumber or reorder before sharding.
- **FR-22 title:** "Leave event notifications", but the table includes Holiday and fake-location events. Rename it to "Attendance & leave event notifications".
- **Glossary drift:** FR-27 uses "technician" throughout while elsewhere the text uses "Employee". This is defensible, because untracked technicians are included, but add a line to the Glossary noting it. The FR-10 rule 5 wording "half the Hours rules" and then "Full-day hours ÷ 2" disagree on whether the Half-day threshold is also halved. Pick one.
- **FR-5 validation sentence:** "Validation: 0 < Half-day hours < Full-day hours ≤ (End time − Start time) is **not** required … Only Half-day < Full-day is enforced." This is hard to read. Also, is 0 < Half-day enforced? Restate it positively.
- **Assumptions Index roundtrip:** Every inline `[ASSUMPTION]` is indexed, and every index entry appears inline. The index order is off: FR-7 is listed before FR-6 (§10 lines 478–479). The two memlog "Claude's call" items (FR-14 cut-off, NFR-10 waves) are missing from both inline tags and the index (see Decision-readiness).
- **UJ protagonists:** All five are named. UJ-4 and UJ-5 have no Entry state. Acceptable.
- **Required sections:** All are present for a chain-top build PRD. The title is still marked "*Working title — confirm.*" (line 9).
