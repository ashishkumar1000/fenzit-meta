- (constraint) Inherits fenzit-be's existing architecture (docs/architecture.md): modular monolith, feature modules never cross-import, common/ hosts shared cross-cutting concerns, AR-9 idempotency pattern, AR-10 atomic-rpc-only for multi-step mutations, AR-13 global JwtAuthGuard+RolesGuard, AR-14 single error shape via GlobalExceptionFilter, AR-17 Joi env validation, AR-19/AR-23 abstract-provider DI-swap convention, AR-11 migrations via Supabase MCP only
- (constraint) Reconciliation finding: fenzo-app AddCustomerSheet.tsx already collects and submits an 'area' field (line 107), but fenzit-be customers table/DTO has no area column anywhere (grep confirmed) - pre-existing latent gap where Area is silently dropped today. Not caused by this feature but this migration is the natural place to fix it.
- (decision) AD-1 Paradigm: new fenzit-be PlacesModule as an independent top-level feature module (src/places/, sibling to customers/auth), service-only (matches accepted AR-2 drift, no abstract repo layer). Depends only on CacheModule (no Supabase/DB access - pure external-API proxy). FE: new src/features/addressPicker/ feature folder matching existing src/features/customers/ convention.
- (decision) AD-2 Google Places integration: Autocomplete (New) + Place Details (New), never Text Search. Abstract PlacesProvider class + GooglePlacesProvider impl using Bun native fetch (no new HTTP client dependency), mirrors existing OtpDeliveryProvider/OtpSessionStore DI-swap convention (AR-19/AR-23). Timeout via AbortSignal.timeout (recommend 4s).
- (decision) AD-3 Session token lifecycle: FE-generated UUID v4, created when AddressPickerScreen opens, attached to every autosuggest call and the terminating resolve call, discarded on close/select. BE treats it as an opaque passthrough string only - never generates, stores, or inspects it.
- (decision) AD-4 API contract: GET /places/autosuggest?q=&sessionToken= and GET /places/resolve/:placeId?sessionToken= , both behind JwtAuthGuard + @Roles(Role.OWNER) (matches POST /customers restriction - only owners add customers). sessionToken required (DTO-validated, not optional) so cost controls are structural not conventional.
- (decision) AD-5 Server-fixed request params (never client-configurable): includedRegionCodes=['IN'], Place Details field mask = id,formattedAddress,location,addressComponents,postalAddress (Essentials tier only, no displayName). Postal code read from postalAddress.postalCode; city/area from addressComponents types locality/sublocality_level_1.
- (decision) AD-6 Cost/rate control: self-contained per-request-count limiter inside PlacesModule using the same cache-manager increment-counter pattern as in-memory-otp-session.store (key places:rate:{tenantId}), not extracted into a shared common/ utility yet (avoid touching working OTP code / premature abstraction for a single second consumer - deferred). Plus a short-TTL (default 300s, reuse global CacheModule TTL) cache keyed on normalized query text + region for autosuggest, and on placeId+fieldmask for resolve, to dedupe repeat lookups across users.
- (decision) AD-7 Customer schema migration (additive, Supabase MCP-applied SQL per AR-11): customers.area TEXT (new - fixes the pre-existing gap), customers.formatted_address TEXT, customers.pincode TEXT, customers.latitude DOUBLE PRECISION, customers.longitude DOUBLE PRECISION, customers.place_id TEXT (nullable, kept for a possible future refresh-from-Google use case, cheap to add now). Existing address/city columns unchanged and remain user-editable free text - all new fields nullable so a customer can still be created with manual free-text address only, no coordinates (preserves current behavior as fallback).
- (decision) AD-8 FE navigation/return-data pattern [ASSUMPTION - not yet runtime-verified]: no existing pattern in the app for a pushed screen to return data to a caller. Chosen: navigation.navigate('AddressPicker', { onSelect }) - a callback function passed via route params. React Navigation's native-stack keeps lower screens (and the mounted AddCustomerSheet + its local state) alive while a screen is pushed on top, so the callback ref stays valid for the session. On selection, AddressPickerScreen calls route.params.onSelect(resolvedAddress) then navigation.goBack(). No global store (Zustand/Context) introduced for this - the empty src/store/index.ts stub stays unused, avoiding a disproportionate abstraction for one flow.
- (decision) AD-9 Error boundaries: Places provider failure -> GlobalExceptionFilter shape {statusCode:502, error_code:'PLACES_UPSTREAM_ERROR'}. No results -> 200 with empty array, not an error. Own rate limit tripped -> 429 'RATE_LIMITED' returned before calling Google at all. FE: address free-text field remains always editable regardless of picker success/failure - manual entry is the permanent fallback, matching the existing requirement that the user can still edit the address after picking.
- (decision) AD-10 Config: GOOGLE_PLACES_API_KEY added to the existing Joi schema in app.module.ts (AR-17 convention), consumed via ConfigService.getOrThrow, IP-restricted server key (never client-side) per verified research finding [8]. User has said they will supply the key when implementation starts.
- (question) Open: exact UX affordance for opening the picker (tap whole field vs a dedicated icon button) left to implementation/UX pass, not an architectural invariant.
- (question) Open: rate-limit threshold number (e.g. 60/min per tenant) not fixed - needs a real number chosen at implementation time, informed by expected technician/owner volume.

- (constraint) Direct code check (CustomersScreen.tsx:96-100, NewJobScreen.tsx:275-276) DISPROVES original AD-7 rationale: area is NOT a dropped/latent gap. Both screens already concatenate area into address as '<address>, <area>' before calling POST /customers, with an explicit code comment explaining why. This is a deliberate, working, documented convention, not a bug. AD-7 revised: no new area column; keep the existing concatenation convention untouched, Places auto-fill just populates the same existing City/Area inputs that already feed it.
- (constraint) Direct code check (TechnicianPicker.tsx) confirms the adversarial reviewer's finding: the only existing 'pick something, tell the caller' component in this app is an INLINE component (rendered in the same tree, onSelect prop, no navigation) over a small preloaded list - doesn't transfer directly to an async remote-search UI needing full-screen space, but its onSelect-prop shape (not callback-in-route-params) is the relevant precedent. Also confirmed: JobsScreen.tsx:161 already uses navigation.setParams({ scope: undefined }) to clear a consumed param - this IS the app's real 'return a value to the previous screen' precedent.
- (decision) AD-8 REVISED: drop the callback-in-route-params design. AddressPickerScreen navigates back via navigation.navigate('Customers'|'NewJob', { pendingAddress: ResolvedPlace }) - fully serializable. The destination screen reads route.params.pendingAddress in a useEffect, feeds it into AddCustomerSheet's (now extended) local state, then calls navigation.setParams({ pendingAddress: undefined }) to clear it - mirrors the existing JobsScreen precedent exactly.
- (decision) AD-2 REVISED: PlacesProvider.resolve() returns the AD-4-normalized ResolvedPlace shape, not Google's raw JSON - GooglePlacesProvider owns the Google-shape-to-ResolvedPlace mapping (including null-normalization for missing addressComponents). MockPlacesProvider returns fixture ResolvedPlace objects directly - no Google-shape knowledge needed in either consumer or mock.
- (decision) AD-4 REVISED: location is NOT guaranteed non-null by Google for every placeId (undocumented edge case per adversarial review) - if Place Details omits location for an otherwise-valid placeId, GooglePlacesProvider treats it as a provider failure (502 PLACES_UPSTREAM_ERROR), never a null-coordinate success response. city/area/pincode are always string|null (never omitted, never ''), normalized in GooglePlacesProvider's mapping.
- (decision) AD-6 REVISED: rate-limit cache key includes an endpoint discriminator - places:rate:{tenantId}:autosuggest and places:rate:{tenantId}:resolve as two separate counters/budgets, since autosuggest fires far more often (per keystroke) than resolve (once per selection) and sharing one budget would let autosuggest starve resolve.
- (decision) AD-7 REVISED (final): migration adds only formatted_address TEXT, pincode TEXT, latitude DOUBLE PRECISION, longitude DOUBLE PRECISION, place_id TEXT - no area column (see constraint above). CreateCustomerDto (BE) and CreateCustomerRequest (FE) both gain these 5 optional fields alongside existing name/countryCode/phoneNumber/address/city - closing the rubric-walker's found FE-BE contract gap for the amended POST /customers body.
- (decision) AD-1 REWORDED (no rule change, wording fix): CacheModule is global (isGlobal:true) so no module explicitly imports it (AuthModule doesn't either, despite using it) - AD-1's actual rule is a dependency-boundary rule (no SupabaseModule/other-feature-module dependency), not a literal NestJS imports:[] list.
- (decision) AD-5 labeling fix: 'id' field is its own free 'Essentials IDs Only' SKU, technically separate from the 'Essentials' SKU that formattedAddress/location/addressComponents/postalAddress fall under - no cost or behavior change, wording only.
