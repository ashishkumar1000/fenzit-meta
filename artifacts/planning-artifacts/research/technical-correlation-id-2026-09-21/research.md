# technical research: Correlation key design for fenzo-app → fenzit-be

**Decision this research serves:** Finalize a correlation-key plan for fenzo-app (React Native) → fenzit-be (Node backend): generation strategy, header naming, uniqueness scope, backend logging and propagation.

## Executive summary

**Do not make the correlation key unique per user — make it unique per request, layered.** The evidence is unambiguous: no engineering guide or platform prescribes per-user scope for a request correlation ID; the ecosystem pattern is three separate layers — a **fresh ID per HTTP request** (correlation), a **stable ID per app session** (journey grouping), and the **user identity** the backend already knows from auth [12][13]. One ID per user would make it impossible to tell which of a user's requests a log line belongs to — the exact thing the key exists for.

**The three findings that drive the design:**

1. **There is no RFC** for a correlation/request ID header — `X-Request-Id`/`X-Correlation-ID` is a de facto convention still shipped by Heroku, Rails, Envoy and ASP.NET; Microsoft's API guidelines define the most-cited shape: client may supply, service generates when absent, echo it back [1][2][3][4]. W3C `traceparent` is the standards-track alternative but is built for distributed tracing — practitioners run a business correlation ID *alongside* it, not instead [7][10].
2. **The backend must sanitize, never trust, the client ID.** Fastify's own docs warn that honoring a client-supplied ID means "any caller can set reqId to any value with no validation" [28]; echoing unvalidated IDs is a documented log-injection vector [13][14]; Smithy Rust deliberately distrusts client IDs [24]. Validate charset/length, fall back to server-generated.
3. **Every log line gets the ID via AsyncLocalStorage + a pino `mixin`** — not by threading a `reqId` parameter through every function; and the ID must be re-attached at boundaries it cannot cross (outbound HTTP, job queues, EventEmitters), each of which is a documented leak [29][30][31].

**Biggest caveat:** retry semantics are genuinely contested (reuse the ID across retries vs mint a new one per attempt) — the design must pick one explicitly. Also, two claims rest on thin evidence and are marked low/medium confidence below (complementary mobile headers; the exact pino `mixin` pattern).

## 1. Standards & landscape — what the ecosystem actually uses

**There is no RFC for a correlation/request ID header.** The IETF HTTPAPI working group has no request-id draft (its closest artifact, the Idempotency-Key draft, expired Oct 2025) [1]. `X-Request-Id` is deprecated only by style: RFC 6648 (BCP 178, 2012) discourages the `X-` prefix for *new* parameters but recommends no migration, and no vendor has deprecated the header in fact — Heroku, Rails, Envoy and ASP.NET all still ship it [2]. The RFC-clean spellings are bare `Request-Id` / `Correlation-ID`.

**The de facto convention, practice:** Microsoft's REST API Guidelines define the most-cited spec — `X-Correlation-ID` for an end-to-end transaction (required on all API calls, propagated unmodified, generated by the service when the caller omits it) vs `X-Request-ID` per request (recommended GUID), plus an `X-Correlation-Status` response header echoing validity [3]. Heroku's router generates a UUID request ID, accepts client-supplied values (20–200 chars, restricted ASCII, invalid values replaced) and correlates router↔dyno logs with it [4]. Rails generates a per-request UUID when the client doesn't supply one and tags logs with it (`config.log_tags = [:request_id]`); the pattern is mirrored across Node (express-request-id), Django, Java, PHP [4][26]. Platform-native variants exist but are not for clients to adopt: AWS `X-Amzn-Trace-Id` (X-Ray), Vercel `x-vercel-id`, Envoy `x-request-id` + `x-client-trace-id` [5][6].

**W3C Trace Context (`traceparent`) is the standards-track option.** A W3C Recommendation since 2021-11-23, format `00-{32 hex trace-id}-{16 hex parent-id}-{2 hex flags}`, with strict validation (unparseable → ignored, trace restarted) [7]. The spec explicitly permits non-tracing participation: minimum compliance is MUST-propagate even without collecting trace data, so a backend can accept/forward `traceparent` without any tracing stack [7]. It mandates no PII in these headers and prefers random over timestamp/IP-derived IDs [7]. Azure Monitor supports legacy `Request-Id`/`X-Request-Id` alongside `traceparent` [8].

**Correlation ID vs OpenTelemetry — complementary, not competing.** OTel's default propagator is W3C TraceContext; practitioner consensus is to run both: trace-id for latency debugging (traces retained only ~7–30 days), a separate business/correlation ID for support workflows and longer retention, joined by injecting the trace-id into log lines; business context can ride W3C `baggage` (RFC 9552) [9][10][11]. The split is "debug correlation" (trace-id) vs "business/support correlation" (separate ID) — a mobile-app support key is the latter.

## 2. Generation, scope & client implementation (React Native)

**Scope: per-request, layered — never per-user.** No engineering guide found prescribes per-user scope for a request ID; a per-user ID appears only as an implicit identity field, not a correlation key [12]. The recommended shape is layered identifiers: a fresh ID per HTTP call plus a stable session ID per app sitting, with the request ID optionally composed `${sessionId}-${timestamp}-${counter}` for sortability [12][13]. Retries are a genuinely contested point: one guide reuses the original request ID across retries with attempt count in a separate `X-Retry-Count` header, another mints a new request ID per retry under the same correlation ID — the invariant both agree on is that one logical operation must remain one queryable unit, with attempt-level detail kept separate [14][15]. This is a naming choice the design must make explicitly; the "correlation key" framing leans correlation-ID-style (stable across retries).

**Generation on-device:** `expo-crypto`'s `Crypto.randomUUID()` is a v4 UUID from cryptographically secure random, supported on iOS/Android/Web [16]. The npm `uuid` package needs `react-native-get-random-values` imported *before* `uuid` (import order is critical) to polyfill `crypto.getRandomValues` [17]. UUIDv7 (RFC 9562, May 2024) has a 48-bit millisecond timestamp prefix so IDs sort in creation order — better for log correlation — at the cost of leaking creation time to ms precision; `uuid` gained `v7()` in 10.0.0 (June 2024) and is ESM-only from v12 [18][19]. A per-request ID should not persist across app relaunches (by scope); persistence in the sources applies only to device IDs.

**Implementation pattern: one interceptor, not per-call plumbing.** The standard is a centralized request interceptor — `axios.interceptors.request.use(config => { config.headers['X-Request-ID'] = uuidv4(); return config; })` — explicitly *not* `axios.defaults.headers`, which is shared and would stamp one value on every call; a fetch wrapper is the equivalent for non-axios apps [20]. No dedicated RN correlation-ID library exists — every source implements it as an interceptor or wrapper. The one RN-specific gotcha found is native-layer header handling (a custom `user-agent` via `fetch()` on Android overrides the WebView's UA — facebook/react-native#27962), so plain custom headers like `X-Request-ID` are safer than headers the native stack manages [21].

**Complementary headers and the echo.** Mobile observability guides recommend also carrying app version (`X-App-Version`), device ID and session ID alongside the request ID for release-by-release comparison and user-journey correlation, masking sensitive values before they leave the device (lower confidence — vendor community sources) [22]. Echoing the ID back in response headers is a documented pattern that turns the user into a first-line debugger, with a hard requirement: validate incoming IDs (length/charset) before echoing, to prevent log injection [13][14]. The closest "copy debug info" UX precedent is Sentry's event-ID flow — show `Error ID: {eventId}` to the user, support searches it — noting the event may have been dropped by sampling [23].

**Trust boundary:** Smithy Rust RFC-0024 deliberately prefers *server-generated* IDs and distrusts client-supplied ones (duplicate/missing/malicious); the .NET correlation protocol says caller-generated with callee-fallback [24][25]. Together with the echo-validation finding, the rule is: accept the client ID, sanitize it, never blindly trust or echo it.

## 3. Backend logging & propagation (Node)

**Middleware: read, sanitize, fallback-generate, echo.** The established Express pattern is a first middleware — registered before routes/CORS/body-parsing — that reads `req.headers['x-request-id']`, falls back to `crypto.randomUUID()` when absent, and echoes the ID back via `res.set('X-Request-Id', ...)` [26][27]. Fastify has this built in (`requestIdHeader`, `genReqId` called only when the header is absent, log label `reqId`) and its docs carry the exact warning this design needs: honoring the header means *any caller can set reqId to any value with no validation* — consider length/format checks, or minting your own ID even when a client ID arrives [28].

**Attach to every log line with AsyncLocalStorage.** Node's official docs present AsyncLocalStorage as the built-in way to propagate per-request data across async operations (stable since v16.4.0, with a canonical HTTP-server per-request-id example), preferred over hand-rolled async_hooks [29]. Pino's recommended integration is the `mixin` option — a function reading the ALS store that merges `reqId` into every log line, with `mixinMergeStrategy` so store values win (medium confidence — the pino doc could not be fetched directly this run; the pattern is quoted consistently across search results) [30]. `cls-hooked` appears nowhere as current practice — ALS is the successor. No authoritative doc prescribes one canonical JSON field name (`requestId` vs `correlationId` vs `reqId`); only Datadog's reserved `dd.trace_id` is normative.

**Propagation has known boundary leaks.** For downstream HTTP calls the canonical pattern is an axios interceptor reading the ALS store and setting the header per call — setting it on a shared axios singleton's *defaults* is a documented anti-pattern that leaks one user's ID into another user's request under concurrency (axios discussion #5955) [31]. ALS context does not survive a job-queue boundary: either `AsyncLocalStorage.snapshot()` at enqueue time, or carry the correlationId in the job payload and have the worker re-run `als.run()`; cron jobs mint their own ID [32]. EventEmitter listeners run with the context active at *emit* time — bind them with `AsyncResource.bind()`, and prefer `run()` over `enterWith()` which Node's docs warn leaks context past its boundary [29].

**OTel overlap — the two systems are complementary.** With `@opentelemetry/sdk-node` + auto-instrumentations, `traceparent` is extracted from inbound and injected into outbound requests automatically — no manual propagation code [33]. But that makes manual middleware redundant only for *trace* propagation, not for app-level correlation: the plain-stdout-log searchability by a client-supplied ID still needs the explicit field, and the two systems then need bridging (OTel trace-id ↔ your correlationId log field). Datadog, for reference, joins logs↔traces via `dd.trace_id` auto-injected into pino/winston JSON logs, with a remapper rule for custom field names [34].

## Cross-dimension insights

- **The "unique per user" instinct maps to the session layer, not the correlation key.** The client and backend dimensions independently converge on the same layered model: per-request ID (correlation) + per-session ID (journey) + user identity (auth, already server-side). A per-user key alone defeats per-request log joining — the primary use.
- **"Don't trust the client" shows up twice, from independent traditions.** The backend dimension's Fastify warning (no validation on client IDs) and the client dimension's Smithy/.NET trust-boundary split arrive from tracing and API-design cultures separately — sanitize-and-fallback is the universal rule.
- **De facto header vs W3C standard is not an either/or.** A bespoke `X-Correlation-ID` is fully defensible (no RFC constrains it), while `traceparent` costs more format discipline but enables OTel later. Either can be added after the other — the log field is the load-bearing part for support search in plain stdout logs.

## Recommendations

1. **Adopt `X-Correlation-ID` (client-generated, unique per request, stable across retries of the same logical operation) + `X-Session-ID` (stable per app sitting).** Basis: de facto convention across Microsoft/Heroku/Rails/Envoy practice [3][4]; per-user scope found in no guide [12]. Confidence: high on convention, medium on retry semantics (contested [14][15]) — pick stable-across-retries to match the "correlation key" framing.
2. **Generate v4 UUIDs on-device via `expo-crypto` `Crypto.randomUUID()`** (no polyfill dependency); v7 is a viable alternative if time-sortable logs matter more than ID-opaqueness. Basis: Expo docs [16]; UUIDv7 trade-off [18][19]. Confidence: high for v4; medium for v7 trade-off.
3. **Inject via one axios/fetch request interceptor in fenzo-app** — never per-call plumbing, never shared defaults. Basis: axios interceptor docs and guide consensus [20].
4. **In fenzit-be: first middleware reads the header, validates charset/length, falls back to `crypto.randomUUID()` on missing/invalid, stores in AsyncLocalStorage, echoes back in the response header.** Basis: Express/Fastify practice and Fastify's no-validation warning [26][28]. The user identity and session ID go into the log context from auth middleware — no extra header needed for "which user".
5. **Attach `correlationId` to every log line via a pino `mixin` reading the ALS store**, as a single JSON field. Basis: Node ALS docs [29], pino mixin pattern [30] (medium confidence — doc not fetched directly). Field name `correlationId` is a defensible choice (no canonical name exists in the sources).
6. **Propagate at boundaries: outbound axios interceptor reads ALS (not shared defaults — concurrency leak [31]); job payloads carry the ID and workers re-run `als.run()` [32].**
7. **Defer `traceparent`/OTel adoption** — the bespoke correlation ID is sufficient for the support/debug use case; add OTel later without conflict (practitioner consensus: run both [9][10]).

## Open questions

- **Canonical log field name** (`correlationId` vs `requestId` vs `reqId`) — no authoritative source; pick one and document it internally. (Resolvable by internal convention, not research.)
- **Pino `mixin` pattern** — quoted consistently across search results but the primary pino doc could not be fetched this run; verify against the pino repo when implementing.
- **`uuid` v7 monotonicity under Hermes** — unverified whether same-millisecond counter behavior matches Node; only relevant if v7 is chosen.
- **Render stdout log search** — no Render-specific guidance surfaced; test searching logs by correlation ID in the Render dashboard after first deployment.
- **Grafana/Loki or New Relic header-extraction conventions** — not read this round (budget); only needed if those platforms are adopted.
