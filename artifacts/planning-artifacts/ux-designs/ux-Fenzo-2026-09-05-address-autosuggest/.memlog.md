- (decision) Fast path: user explicitly asked for own research + a finished design rather than heavy elicitation. Drafting both spines directly, [ASSUMPTION] tags on ambiguous product calls, flagging open questions rather than silently deciding on the genuinely ambiguous ones (current-location quick-add, match-text highlighting, resolve-in-flight cancellation).
- (decision) Foundation: mobile, React Native (iOS+Android), inherits 100% from the existing Fenzit Design System (fenzo-app/src/theme + src/components/ui) - no new brand/color/typography, only 3 new component specs for this feature's screen.
- (decision) Research grounding: Baymard autocomplete UX research (baymard.com/blog/autocomplete-design) - mobile should show 4-8 suggestions max, minimize competing chrome (hide sticky headers/ads while list is open), generous tap targets, avoid inline scrollbars; general search on Indian food-delivery apps (Zomato/Swiggy) confirms the 'address search screen with list, no drag-pin-to-adjust in the base flow' pattern is standard, not an outlier choice.
- (decision) No-match / can't-find-it flow: rather than a magic 'use this text as typed' fake-selection button, the empty/no-results state offers 'Enter address manually' which just goes back to the bottomsheet's existing free-text field - avoids inventing a fake placeId/fake resolve, matches AD-4's requirement that only a real placeId resolve produces coordinates.
- (decision) Selecting a suggestion triggers the resolve network call BEFORE navigating back (not an optimistic instant pop) - row shows an inline loading state (spinner replaces trailing chevron) since resolve has real latency; screen does not pop until resolve succeeds or fails with a retryable inline error.
- (decision) Handoff back to AddCustomerSheet: no toast/snackbar acknowledgment - the address field visibly populating is itself the confirmation. Added a brief (200ms) soft primary-tinted border pulse on the address Input on return, matching the design system's motion durations (120-320ms, no bounce), so the change registers even if the user's eye hasn't refocused yet.
- (assumption) [ASSUMPTION] Technician job-detail maps row (FR10) gets NO visual change (no 'precise vs approximate location' badge) - the affordance's promise (tap to navigate) is unchanged, only its underlying accuracy improves; adding a badge for a distinction the technician can't act on differently would be visual noise, against the design system's minimal-decoration ethos.
- (question) OPEN: 'Use my current location' quick-add (GPS + reverse geocode) at the top of the results list is a very standard pattern (Uber/Swiggy/Google Maps) and would be valuable for owners adding a walk-in customer on-site, but is NOT in the architecture spine (no geolocation-permission flow was architected) - explicitly deferred to a future story, not designed here. Flagging for the user's product call, not silently added or dropped.
- (question) OPEN: highlighting the matched portion of the query within each suggestion (Baymard best practice) requires Google Autocomplete's match-offset data (structuredFormat may or may not include it depending on exact response fields requested) - not confirmed against the architecture spine's fixed response shape. Deferred as a visual enhancement pending that confirmation, not blocking v1.
- (question) OPEN: if the user backgrounds the app or force-quits mid-resolve (after tapping a suggestion, before the resolve call returns), what should happen on return - resume, silently drop, or show a stale error? Not specified; flagging as an edge case for implementation-time decision, not designed here.
- (override) User feedback: 'don't deviate much from the app design theme' - caught real deviations in the first draft. Corrected: (1) suggestion rows change from invented full-bleed/hairline-divider rows to the EXACT TechnicianPicker 'rows' variant card style (borderWidth 1 borderSubtle, radius.lg, surfaceCard bg, s2 gap) - the app has no full-bleed-hairline list anywhere; (2) invented 'inline-status-banner' component dropped entirely, replaced with the app's real existing components: EmptyState (full-screen icon+title+description+CTA, used by Technicians/Jobs/Customers zero-data screens and CustomerDetailScreen's not-found state) for no-results and full-blocking-error states, and InlineError (dismissible AlertTriangle banner, status.cancelled colors) for the resolve-failure-with-results-still-visible case, per InlineError's own docstring guidance; (3) header changes from an invented generic back-chevron spec to the exact existing pattern: SafeAreaView edges={['top']}, StatusBar barStyle='dark-content', IconButton variant='ghost' size='md' wrapping ChevronLeft size={22} color={colors.textStrong} strokeWidth={2} - copied verbatim from CustomerDetailScreen.tsx/TechJobDetailScreen.tsx headers, with the header's title-Text slot swapped for the search Input (not a new header shape, a reuse of the existing header row with one slot substituted).
