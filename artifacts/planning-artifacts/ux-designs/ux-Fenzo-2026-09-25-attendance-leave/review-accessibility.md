# Accessibility Review — Fenzo Attendance & Leave

## Overall verdict
The written spec's *intent* is good — FR-25's "never colour alone" rule is stated up front and DESIGN.md builds a whole icon+label table around it — but the actual mockups don't consistently deliver on it: two of the twelve Day statuses are drawn with the literal same icon glyph in the calendar cell, one status is coloured with the wrong hue family in one mockup versus another, and the permission-denied path required by FR-4 simply isn't drawn anywhere. Touch-target and contrast numbers, checked against the real hex values and real CSS box math (not just the prose), also fail in a few concrete, fixable spots. None of this needs a redesign — it's mockup-fidelity and spec-completeness gaps that should be closed before build.

### Findings

- **critical** Onboarding's permission screen has exactly one affordance — "Allow location access" — with no "Not now" / "Continue without location" / Settings deep-link visible anywhere on that screen or state-mapped in EXPERIENCE.md. FR-4 requires that a denied user can still browse records and apply for leave, but nothing shows what that user sees on *this* screen (first entry, or a returning user who denied at OS level and can't be re-prompted) once they don't tap Allow. (`mockups/key-onboarding-states.html:34-50` "First entry — Onboarding intro + permission ask"; PRD FR-4, `prd.md:147-152`). *Fix:* add a secondary "Not now" / "Continue without location" text link on this screen, and add an explicit "permission denied" onboarding state to EXPERIENCE.md's State Patterns table describing exactly what a denied user sees (the summary screen minus check-in, plus a persistent low-vision-safe hint on how to grant it later via Settings).

- **critical** EXPERIENCE.md's Accessibility Floor states flatly "All press targets ≥ `touch.min` (44px)" (`EXPERIENCE.md:159`), but this is contradicted by DESIGN.md's own admission two sections earlier that calendar cells are "minimum 40×40pt... below `touch.min` in raw size" (`DESIGN.md:113`), and by the actual CSS math in the mockup: `mockups/key-month-calendar.html` uses `.content{padding:12px 16px}` and `.grid{grid-template-columns:repeat(7,1fr);gap:4px}` inside a 375px device frame → cell width ≈ (375−32−24)/7 ≈ 45.6px, which only clears 44px on a 375px-wide phone. On a 360dp-wide Android device (a very common budget class in India, the app's core market), the same formula gives (360−32−24)/7 ≈ 43.4px — under the 44px floor the Accessibility Floor section claims is universal. *Fix:* either shrink the grid horizontal padding/gap on narrow devices to keep cells ≥44px, or correct the Accessibility Floor bullet to explicitly carve out the calendar-cell exception DESIGN.md already admits, with a stated minimum (e.g. "≥40px, tap area only") instead of claiming a blanket 44px.

- **high** Same-hue Day statuses are not reliably disambiguated by icon at cell size, contradicting the spec's own "by construction" claim. In `mockups/key-month-calendar.html`, cell 9 (Half day, amber) and cell 14 (Checkout missing, amber) render the *identical* SVG path (`<circle cx="12" cy="12" r="9"/><path d="M12 7v6"/>`, line 90 vs 96) — same icon, same background, same text colour — distinguished only by a subtle 2px blue inset ring on cell 14. At the stated 12×12px icon size (`.cell svg{width:12px;height:12px}`, line 30) inside a ~45px cell, this ring is the *only* practical signal, which is itself a colour-only cue. The calendar's own legend admits the collision: "Present / Worked holiday" and "Half day / Checkout missing" are each shown as one merged swatch (`mockups/key-month-calendar.html:117-120`), not four distinct entries — the mockup's own legend concedes these pairs read as one thing, not two. (Cf. DESIGN.md's status table, `DESIGN.md:131-144`, and Do's/Don'ts "pair every status/flag with an icon and a text label," `DESIGN.md:229`.) *Fix:* give Half day and Checkout missing visually distinct icon glyphs (DESIGN.md already assigns different Lucide icons — `Clock` vs `AlertCircle` — the mockup just didn't implement them), and split the legend into four entries instead of two merged ones.

- **high** "Checkout missing" is coloured inconsistently across mockups. DESIGN.md's status table places it in the amber/partial family (`DESIGN.md:141`), and `mockups/key-owner-dashboard.html` and `key-month-calendar.html` render it amber correctly. But `mockups/key-monthly-employee-list.html:55` renders the same status as `<span class="mchip flag">Checkout missing 1</span>`, and `.mchip.flag{background:#FEF2F2;color:#A61F1F}` (line 35) is the red/blocked family — the same hue used for "Absent" and fake-location. This flips a routine "needs attention" flag into what visually reads as a danger/failure state, on the one screen (monthly summary) where an owner is scanning many rows quickly by colour. *Fix:* change `.mchip.flag` to the amber tone (`#FEF6EB`/`#92490A`) to match DESIGN.md's own family table, and reserve the red `mchip` treatment for genuinely blocked-family counts (Absent, Fake-location) if/when those appear in this row style.

- **high** The office map picker's draggable pin and radius slider have no accessibility treatment anywhere in EXPERIENCE.md, even though "Offices (list → add/edit → map picker)" is explicitly named in the Information Architecture (`EXPERIENCE.md:50`) and FR-5 requires the Owner to be able to set an office location. Two of the three entry paths (current-location, address-search) are inherently screen-reader-friendly, but the third — drag-to-fine-tune the pin, and the custom radius slider/knob in `mockups/key-office-map-picker.html:44-46` — has no stated non-visual equivalent (e.g. arrow-nudge buttons, a numeric lat/long or radius text input, announced value-change on the slider). A low-vision or screen-reader owner is left with only "roughly near the address" placement, with no way to confirm or correct the final pin precisely. *Fix:* add an accessible fallback to the map picker (nudge buttons or a numeric radius input read as a standard accessible slider/stepper with live value announcements), and add a line to the Accessibility Floor covering this surface explicitly.

- **medium** `mockups/key-setup-wizard.html` (Step 5 of 5, lines 124-128) shows Arjun's employee-enable switch already rendered in the "on" (blue) state while the adjacent text reads "No office assigned — pick one" in red. This contradicts EXPERIENCE.md's own written rule: "the switch itself doesn't visually commit to 'on' until an Office is chosen" (`EXPERIENCE.md:115`). A user glancing only at switch colour (as many low-vision or quick-scanning users do) sees "enabled," not "blocked." *Fix:* redraw this mockup frame with the switch in its pre-commit/neutral state until the office picker resolves, matching the written behaviour.

- **medium** Contrast failures measured against the actual Fenzit hex values (`workspace/core/frontend/fenzo-app/src/theme/colors.ts`) and the mockups' own CSS:
  - Weekly-off / "off" calendar cell text and icon stroke, `#9CA3AF` (gray400) on `#F3F4F6` (gray100) in `mockups/key-month-calendar.html` (`.cell.off`, line 36) = **2.31:1**, well under the 4.5:1 AA floor for this small text/icon. This is a deviation from the design system's own `colors.status.neutral.fg` token (gray600, `#4B5563`), which would give 6.87:1 — the mockup appears to have used the wrong grey.
  - The onboarding privacy disclosure — "Fenzo only reads your location the moment you check in or out — never in the background" (the one sentence realising NFR-11) — is rendered at 12px in `#9CA3AF` on `#F9FAFB` (`mockups/key-onboarding-states.html:45`) = **2.43:1**, also failing AA. It is the least legible line on the one screen carrying the app's location-privacy promise.
  - The leave-apply character counter ("32/500") uses the same `#9CA3AF` on white = **2.54:1** (`mockups/key-leave-apply.html:34,86`) — lower severity since it's non-essential metadata, but still fails AA for text.
  - By contrast, the amber700-on-amber50 and green700-on-green50 status-badge text pairs used elsewhere (Checkout missing/Half day/Present labels) all measure 6.1–7.4:1 and comfortably pass — so this is a scoped set of grey-token mistakes, not a systemic palette problem. *Fix:* replace `#9CA3AF` with `#6B7280` (textMuted, 4.63:1 on the page background) or `#4B5563` (neutral.fg, 6.87:1 on gray100) in these three spots.

- **medium** The tenant-default Weekly-off day picker (`mockups/key-weekly-off-holidays.html:56-59`) shows seven single-letter pills "S M T W T F S" with no visible or stated disambiguation between the two S's (Sunday/Saturday) or two T's (Tuesday/Thursday). Nothing in EXPERIENCE.md's Accessibility Floor addresses this control, despite "Weekly off" being named in the IA (`EXPERIENCE.md:52`, FR-18/19). A screen-reader user tabbing through would hear "S", "S" with no way to tell which is selected without opening each one. *Fix:* give each pill a distinct accessible label ("Sunday", "Monday", ... spelled out) independent of its one-letter visible glyph, and confirm selected/unselected state is announced (e.g. "Saturday, selected").

- **low** DESIGN.md's own Do's list requires every status/flag to pair "an icon and a text label" (`DESIGN.md:229`), but the Monthly Employee List's summary chips (`mockups/key-monthly-employee-list.html`, `.mchip` rows, lines 52-56, 65-67) show colour + text only, no icon. This still clears FR-25's minimum bar (text is present, so it isn't colour-alone), but it's an inconsistency against the module's own stricter stated rule, and removes a redundant cue that would help at a glance. *Fix:* either relax the Do's line to allow icon-or-label for compact summary chips specifically, or add the small icons for consistency.

- **low** Calendar-cell status icons are fixed at 12×12px (`mockups/key-month-calendar.html:30`) and are the *only* status signal inside the cell (DESIGN.md: "no text label inside the cell — no room," `DESIGN.md:186`). EXPERIENCE.md's Dynamic Type note covers "status labels, flag tags and form fields" reflowing (`EXPERIENCE.md:162`) but never states whether this icon scales with the OS accessibility text-size setting. If it doesn't, a user who has increased text size — precisely the population this note is meant to protect — loses the one piece of in-cell information the design relies on. *Fix:* explicitly state in EXPERIENCE.md whether/how the calendar glyph scales with Dynamic Type, or confirm the Day Detail sheet (which does show the full label) is considered the accessible fallback for this case.

- **low** Only the green family (Present vs Worked on holiday) and the amber family (Half day vs Checkout missing) same-hue collisions are actually drawn in any mockup. The three-way blue/"planned" family (Leave, Half-day leave, In progress) and four-way grey/"neutral" family (Weekly off, Holiday, Not tracked, Not checked in yet) are never shown together in a populated calendar frame, so whether their icons (CalendarOff/CalendarClock/Play, and Moon/Flag/MinusCircle/Circle) are actually distinguishable at 12px is untested, not just unresolved — the two collisions found above are likely the tip of the iceberg. *Fix:* before build, render (even as a quick throwaway mock) a calendar month that includes at least one day from each of the 12 statuses, at the real 12px icon size, and eyeball it at arm's length.
