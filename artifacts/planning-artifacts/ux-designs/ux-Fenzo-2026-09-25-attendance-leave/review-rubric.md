# Spine Pair Review — Fenzo Attendance & Leave

## Overall verdict
This is a strong spine pair: every token resolves to a real hex/scale value in `fenzo-app/src/theme`, the canonical DESIGN.md/EXPERIENCE.md section shapes are followed exactly, and the five PRD journeys, FR numbers and Day-status/flag vocabulary are carried over verbatim with almost no drift. The gaps are real but narrow and mostly additive, not corrective: two surfaces (`Skeleton`, and the notifications inbox's technician generalisation) are cited as if already reusable-as-is when both are real, currently-unbuilt work per addendum.md; two settings screens with their own mockups (Weekly off, Holidays) have no DESIGN.md visual spec at all; and a couple of PRD edge-cases/rejection states got dropped or left unstyled in the retelling. Nothing here should block the architecture/story-dev pass, but a handful of these gaps would force a builder to invent behavior the spec should have specified.

## 1. Flow coverage — adequate
Checked all five PRD journeys (§2.3 UJ-1…UJ-5) against EXPERIENCE.md → Key Flows for a named protagonist, numbered/clear steps, a labelled climax, and a failure path where the PRD has one. UJ-1, UJ-2 and UJ-4 are strong — protagonist, steps, an explicit `*Climax:*` line, and (for UJ-1/UJ-2) the PRD's edge case folded into the narrative.
### Findings
- **medium** UJ-3's flow drops the PRD's cancel edge case entirely ("If Arjun had cancelled the leave on Wednesday instead, only Thu–Fri could be cancelled") — PRD `prd.md` §2.3 UJ-3 vs EXPERIENCE.md → Key Flows → UJ-3 (only the revoke path is narrated). *Fix:* add one sentence covering the cancel-split case, or state explicitly that it follows the same split rule as revoke.
- **low** UJ-5 has no labelled `*Climax:*` beat, unlike UJ-1–UJ-4 (EXPERIENCE.md → Key Flows → UJ-5). This mirrors the PRD's own thin UJ-5 (no Climax/Resolution/Edge case there either), so it's inherited thinness rather than an authored gap, but it still fails the rubric's per-flow check. *Fix:* add a one-line climax, e.g. seeing "Days worked: 14.5 so far" without needing to ask anyone.

## 2. Token completeness — strong
Extracted every frontmatter token and every `{path.to.token}` reference in DESIGN.md prose, and checked each against `colors.ts`, `typography.ts`, `radius.ts` and `spacing.ts`. All colour tokens (`colors.status.{done,progress,scheduled,cancelled,neutral}`, `colors.primary`, `colors.primarySoft`, `colors.danger`, `colors.surfacePage`, `colors.surfaceCard`, `colors.textStrong`, `colors.textMuted`) resolve to real hex-backed values; all typography, radius, spacing and touch references resolve to real scale entries. No missing-hex critical issues.
### Findings
- **low** `radius.circle` / `radius.circle.fill` (frontmatter `colors:` block, lines 19–20) are named with a `radius.` prefix but hold *colour* values (`colors.primary` / `colors.primarySoft`), not corner-radius values — confusable with the real shape tokens in the `rounded:` block a few lines below. *Fix:* rename to something like `map.circleStroke` / `map.circleFill`.
- **low** `checkin.time: "{typography.display} @ fontSize 36"` (frontmatter line 34) overrides `typography.display`'s fontSize (48) with a bare magic number instead of citing the scale token it actually equals (`fontSize['3xl']` = 36). Traceable, but not a clean reference. *Fix:* write `{typography.display} @ {fontSize.3xl}`.
- **low** `radius.circle.fill: "{colors.primarySoft}"`'s inline comment ("not a token today — see Do's/Don'ts", frontmatter line 20) is confusing: `colors.primarySoft` is a real, resolvable token (`colors.ts:82`, `#EFF4FE`). Whatever the comment means to flag as unbuilt (a dedicated ~20%-opacity map-overlay variant, presumably), it reads as if the colour reference itself is unresolved, which it isn't — and no Do's/Don'ts bullet actually addresses this. *Fix:* reword the comment to say what's actually new (the opacity treatment on a map overlay), not imply the colour token is missing.

## 3. Component coverage — thin
Extracted every component name in both files and checked for a paired DESIGN.md → Components row and EXPERIENCE.md → Component Patterns row with real behavioral rules.
### Findings
- **high** `Skeleton` (generic loading skeleton) is used as load-bearing state vocabulary in EXPERIENCE.md → State Patterns ("Loading (any list/calendar) | Skeleton, never a blank flash") but has no row anywhere in DESIGN.md → Components, and it doesn't exist in source — only `features/reports/components/ReportSkeleton.tsx` exists today. `addendum.md` §B2 explicitly lists "`ReportSkeleton` → generic `Skeleton` in `components/ui`" as a Generalise-bucket item, i.e. real build work that neither spine flags as new/generalized. *Fix:* add a DESIGN.md Components row and note it as a generalisation, same treatment given to StatusBadge.
- **high** "Weekly off" and "Holidays" settings screens are named IA surfaces in EXPERIENCE.md (FR-18/19, FR-20) with their own mockup (`key-weekly-off-holidays.html`), but DESIGN.md → Components has no entry for either — no visual spec for the weekly-off day-picker or the holiday add/edit/remove list. *Fix:* add two Components rows, even if they're "composed from existing X/Y" one-liners like the other reused-component entries.
- **medium** "KPI tiles" and the dashboard's "Flags" strip are named in both files (EXPERIENCE.md IA; DESIGN.md's Layout & Spacing ASCII wireframe) but neither gets a dedicated Components/Component Patterns row — both are dismissed inline as "(existing tile card)" / "same OverdueStrip pattern as Home" with no behavior spec (tappable? does tapping "Late" filter the flags list below?).
- **medium** `StatusBadge` and `Flag tag` have full visual specs in DESIGN.md → Components (colour/icon/label tables) but no corresponding EXPERIENCE.md → Component Patterns subsection; their only behavioral coverage is scattered under Accessibility Floor (screen-reader announcement text), not centralized where the rubric expects it.
- **low** Component-name drift between files: DESIGN.md "Setup wizard **shell**" vs EXPERIENCE.md "Setup wizard"; DESIGN.md "Enrolment **row**" (singular) vs EXPERIENCE.md "Enrolment **rows**" (plural). Same component, not identical headings.

## 4. State coverage — adequate
Walked every IA surface (Owner: Dashboard, Monthly view, Leave, Setup/Settings; Employee: Onboarding, Upcoming, Today, My calendar, My leave) against empty/cold-load/focus/error/offline/permission-denied states.
### Findings
- **medium** FR-12's "request overlaps a Pending or Approved leave → rejected" rule has no UI/message treatment anywhere in EXPERIENCE.md — only the "already off" rejection copy is specified (Voice and Tone table; Leave apply form pattern). A builder has to invent the overlap-rejection message and where it surfaces.
- **low** Setup wizard has no defined behaviour for a save failing mid-step (network drop while persisting a completed step) — only the success-path "resumes at the last incomplete step" is described.
- **low** GPS-fix timeout isn't named as its own CheckInOutButton state, distinct from "low accuracy" / "Blocked" — NFR-8 requires an explicit timeout treatment but the state table doesn't call it out.

## 5. Visual reference coverage — adequate
All 10 files in `mockups/` (`key-checkin`, `key-enrollment-toggles`, `key-leave-apply`, `key-month-calendar`, `key-monthly-employee-list`, `key-office-map-picker`, `key-onboarding-states`, `key-owner-dashboard`, `key-setup-wizard`, `key-weekly-off-holidays`) are referenced by at least one spine — no orphans. `<title>` tags and internal `Frame A`/`Frame B` anchors were spot-checked against the spine text (e.g. Correction sheet's "see key-month-calendar.html Frame B" — confirmed present) with no broken references.
### Findings
- **medium** 3 of 10 mocks (`key-owner-dashboard.html`, `key-onboarding-states.html`, `key-weekly-off-holidays.html`) get an inline link *with a stated illustration purpose* only in EXPERIENCE.md (IA tree / State Patterns preamble). In DESIGN.md they appear only in the rolled-up "every load-bearing surface is mocked" list at the top of Components — there is no dedicated DESIGN.md subsection (no "Owner Dashboard", "Onboarding states", or "Weekly off / Holidays settings" component entry) tying the mock to visual-spec prose, consistent with the Component coverage gaps in §3.

## 6. Bloat & overspecification — strong
No persona/FR restatement blocks, no pixel values duplicating token coverage, ASCII wireframes used efficiently instead of prose, `[ASSUMPTION]` tags kept short and inline, tables preferred over prose throughout.
### Findings
- **low** DESIGN.md's Components section occasionally states navigation/tap behaviour that belongs to EXPERIENCE.md's declared boundary (DESIGN.md's own line: "this file owns visual identity... Spines win on conflict"; EXPERIENCE.md: "this section covers only behaviour"). Examples: MonthCalendar's DESIGN.md entry says "tapping any cell opens the Day Detail sheet"; Employee list row's entry says "Tapping the row opens that employee's MonthCalendar" — both restated (consistently, not contradictorily) in EXPERIENCE.md's own Component Patterns. Harmless duplication today, but it blurs which file is the source of truth for behaviour.

## 7. Inheritance discipline — strong
`sources:` frontmatter (prd.md, addendum.md, DESIGN_SYSTEM.md, TabBar.tsx, MoreScreen.tsx, features/notifications) all resolve to real files — confirmed by direct lookup. UJ names match the PRD verbatim. All 12 Day statuses and both today-only statuses are used identically across DESIGN.md, EXPERIENCE.md and the PRD glossary. Every `{path.to.token}` in EXPERIENCE.md/DESIGN.md prose resolves into DESIGN.md's own frontmatter.
### Findings
- **low** Spelling drift: DESIGN.md/EXPERIENCE.md consistently write "**Fake-location** attempt" (hyphenated) where the PRD glossary and FR-7 write "**Fake location** attempt" (no hyphen). Cosmetic, but it's exactly the kind of drift the rubric flags, since a story-dev workflow may grep for the PRD's exact string.
- **low** See §3's component-heading drift ("Setup wizard shell" vs "Setup wizard"; "Enrolment row" vs "Enrolment rows") — same issue, filed once here for the inheritance-discipline angle (identical component, non-identical name across the two files).
- **medium** EXPERIENCE.md's `sources:` frontmatter describes `src/features/notifications` as "existing shared inbox, made role-aware per FR-27" — read plainly, this states current fact, but it isn't true today. Direct check of `OwnerRealtimeBridge.tsx` confirms the bridge still gates on `session?.role === 'owner'` (line 24), and addendum.md §A6/§B1/§C2 lists the technician generalisation (nullable `jobId`, event-type registry, role-agnostic realtime bridge, `GET /auth/realtime-token` allowing technicians) as real, currently-blocked build work, not something already in place. Same class of gap as the `Skeleton` finding in §3 — a component/surface is cited as reusable-as-is when it actually needs non-trivial generalisation the spine never calls out as such. *Fix:* reword the sources annotation to "existing shared inbox — Owner-only today; FR-27 requires generalising it to be role-aware (see addendum §C1/§C2)," and add a line to EXPERIENCE.md's Component Patterns or Open Questions naming this as build work, not a given.
