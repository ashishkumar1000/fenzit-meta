# Adversarial Review — Fenzo Attendance & Leave UX

## Overall verdict

DESIGN.md and EXPERIENCE.md cover the happy paths and the majority of state-model plumbing (attendanceAccess four states, module separation, notification inbox reuse, the FR-13 double-owner-action race, the map-unavailable fallback) solidly and consistently. But several PRD-mandated "testable consequences" — mostly the ones the PRD calls out as edge cases rather than headline behaviour — have no corresponding screen behaviour anywhere in the two files: the leave/holiday confirmation dialogs are not wired into the CheckInOutButton's own described press-flow, Revoke/Cancel have no dedicated screen spec at all (unlike every other action), Holiday-vs-Leave collision handling is entirely absent, and the "haven't checked in" reminder and the enable-after-start-time edge case are simply missing. A developer building only from DESIGN.md/EXPERIENCE.md would ship a materially different (and non-compliant) leave/holiday/reminder experience.

### Findings

- **critical** FR-9, FR-7 (holiday check-in) The CheckInOutButton's described press-flow ("On press: request a fresh high-accuracy GPS fix → submit → server decides") never mentions the two required pre-flight confirmation dialogs ("You're on leave today... Continue?" and "It's a holiday. Check in anyway?"). Both dialogs exist only in the Voice & Tone copy table, disconnected from the component's actual interaction spec — there's no statement of *when* they fire relative to the GPS fix, and no mention that the leave-cancel dialog must NOT appear on a Half-day leave date (FR-9's explicit no-auto-cancel exception). (EXPERIENCE.md → Component Patterns → CheckInOutButton, lines ~93-98; Voice and Tone table, lines ~81-82). *Fix:* Add a "pre-flight check" step to the CheckInOutButton flow: before requesting GPS, check today's Day status; branch to the leave-cancel confirm (full-day leave only) or holiday confirm as needed, then proceed to GPS/submit only on confirm.

- **critical** FR-14, FR-15 Unlike Correction sheet, Leave apply form, and Pending queue → detail sheet — each of which gets its own named Component Patterns subsection — there is no "Revoke" or "Cancel" screen/sheet described anywhere in DESIGN.md or EXPERIENCE.md. FR-14 requires the Owner to see the split outcome (e.g. "Thu–Fri revoked, Mon–Wed stay Approved") at the moment they act; UJ-3 only narrates what the *Employee* later sees ("Revoked (Thu–Fri): Audit visit Thursday"). FR-15's Cancel action for the Employee (entire vs. split-on-in-progress) has no entry point, screen, or confirmation described at all. (EXPERIENCE.md → Component Patterns, entire section; Voice and Tone table only has the employee-facing revoked copy). *Fix:* Add dedicated "Revoke sheet" (Owner) and "Cancel" (Employee, from a leave-history row) Component Patterns subsections, each specifying the required-reason field (Revoke) and the immediate on-screen split-result confirmation before/after confirming.

- **critical** FR-20 Both "Holiday added over approved leave" and "Holiday removed inside a leave range" are explicit PRD consequences (each triggers an Employee Notification) with zero UX coverage: no warning/confirmation on the Holidays screen when the Owner adds or removes a holiday that intersects an employee's leave, and no notification copy in the Voice and Tone table for either event. (EXPERIENCE.md has no mention; DESIGN.md's Holidays reference is limited to the list/add mockup). *Fix:* Add an inline warning step to the Holidays add/remove flow ("This date overlaps Arjun's approved leave — it will no longer count as leave") plus two new rows in the Voice and Tone table for the resulting Employee notifications.

- **high** FR-2 The edge case explicitly named in the PRD — "If enabled after today's Start time, today is Not tracked unless the Employee checks in today" — has no corresponding screen behaviour anywhere in EXPERIENCE.md/DESIGN.md (Enrolment rows section only covers the future-start-date case). Related: "Before the start date... the Employee doesn't appear in the Owner's not-checked-in summaries" is never reflected in the FR-24 Owner Dashboard's tile-count description (key-owner-dashboard.html and DESIGN.md give no rule for excluding not-yet-started employees from Tracked/Not-checked-in tiles). *Fix:* Add a State Patterns row for "enabled today, after Start time" (shows Not tracked unless a check-in happens) and state explicitly that dashboard tiles exclude employees whose start date hasn't arrived.

- **high** FR-7 / addendum §C2 EXPERIENCE.md's CheckInOutButton has only one permission-related state ("Location permission not granted" → "Turn on location to check in"). The addendum explicitly requires "Approximate" (Android) / "Precise off" (iOS) to be handled as its *own* state, not conflated with denied, with copy guiding the user to enable precise location. This state is entirely missing from the component's state table. (DESIGN.md → CheckInOutButton state table; EXPERIENCE.md → CheckInOutButton bullets). *Fix:* Add a third button/permission state — "Precise location off" — with its own guidance copy, distinct from both "Ready" and "permission not granted."

- **high** FR-23 The "You haven't checked in" reminder (Tracked employee) and the Owner's two reminders (daily not-checked-in summary per Office; daily pending-leave summary) have no copy, card description, or screen reference anywhere — the Voice and Tone table only specifies the "You haven't checked out" reminder. A developer has no spec for three of the four FR-23 reminder types. (EXPERIENCE.md → Voice and Tone table, row "Missed-checkout reminder" is the only reminder row present). *Fix:* Add three rows to the Voice and Tone table (or a dedicated Reminders subsection) with copy for "haven't checked in," the Owner's per-Office summary, and the Owner's pending-leave summary, and note the Midpoint-adjusted timing for half-day-leave days doesn't change the copy, only the trigger time.

- **medium-high** Tab-bar / IA consistency (attendanceAccess trap) `mockups/key-checkin.html` renders a 4-tab bar literally labelled "Today, History, Attendance (active), Profile" — but EXPERIENCE.md's own Information Architecture nests "Today" and "My calendar" (history) as *screens inside* the single "Attendance" tab, not as sibling top-level tabs. The mockup contradicts the written IA it's supposed to visualise. Since "Spines win on conflict with any mock" (DESIGN.md, EXPERIENCE.md), the mock should be corrected or the IA re-checked, but nothing in the text flags the discrepancy for a builder who works mock-first. (mockups/key-checkin.html tabbar markup vs. EXPERIENCE.md → Information Architecture, "Employee (Tracked)" tree). *Fix:* Redraw the mock's tab bar to match the documented IA — 3 existing tabs (whatever they are: presumably Home/Jobs/Profile) plus one new "Attendance" tab, with Today/History as in-tab screens, not separate tabs.

- **medium** FR-5 No UX behaviour exists anywhere for archiving an Office, including the PRD-required blocked state ("An Office with Tracked employees assigned can't be archived until they are reassigned"). The IA only lists "Offices (list → add/edit → map picker)" — no archive action, no blocked-state message, no reassignment prompt. (EXPERIENCE.md → Information Architecture, Owner → Setup/Settings → Offices). *Fix:* Add an Archive action to the Office list/detail screen with an inline blocked-state message and a path to reassign the blocking employees.

- **medium** FR-12 Four of FR-12's leave-apply validation consequences have no described error/blocked UI: past dates beyond 7 days, dates before the employee's start date, a past date where the employee already has a Check-in, and a range overlapping an existing Pending/Approved leave. Only the "every date already off" rejection ("These days are already off") has specified copy (EXPERIENCE.md → Component Patterns → Leave apply form). *Fix:* Add inline rejection messages for each of the four missing cases, following the same "surface on Submit, don't pre-disable" pattern already used for the off-days case.

- **medium** FR-6 Office reassignment (picking an effective date, and "if changed after today's Check-in, applies from tomorrow") has no Component Pattern at all — only initial office assignment (wizard/enrolment) is described. (EXPERIENCE.md → Component Patterns has no "reassign office" section; DESIGN.md's Enrolment row description covers only enable/disable + start date). *Fix:* Add a reassignment flow to the Employees settings screen with an effective-date picker and the "applies from tomorrow if already checked in today" rule surfaced as inline copy.

- **medium** FR-18 / FR-19 The Weekly Off mockup and spec only support "effective from today" (static text, no date picker) even though FR-18/19 explicitly let the Owner pick any effective date for a tenant-default or per-employee change. Per-employee overrides also have no visible "remove override" affordance — only a chevron to a detail view. (mockups/key-weekly-off-holidays.html; EXPERIENCE.md has no Component Pattern for Weekly off at all). *Fix:* Add an effective-date field to the Weekly Off edit screen and an explicit "Remove override" action in the override detail view.

- **low-medium** FR-25 The Day Detail sheet description (DESIGN.md → MonthCalendar) lists "the full StatusBadge with its label, times, flags and (if present) the correction note" but omits "distance," which FR-25 explicitly requires as part of day detail. *Fix:* Add distance to the Day Detail sheet's listed fields.

- **low-medium** FR-21 "The audit trail is visible to the Owner" (FR-21) implies a full history of corrections (who/when/old/new/note) for a date corrected more than once, but Day Detail only shows the current correction's note — there's no described view of a multi-correction history. *Fix:* Add a "correction history" expandable row/link in Day Detail when a date has more than one correction.

- **low** FR-7 DESIGN.md's CheckInOutButton state table lists "Blocked (too far / low accuracy / fake GPS)" as one state that "returns to Ready," but doesn't separately capture the rate-limited state, which behaves differently (retry is blocked for 10 minutes, not immediate). *Fix:* Add "Rate limited" as its own row in the state table, specifying whether the button stays disabled/shows a countdown for the cooldown window.

- **low** FR-4 "The summary screen stays reachable later" (FR-4) has no described persistent entry point (e.g. a settings row under the Attendance tab) for re-viewing the onboarding summary after first entry. *Fix:* Name the screen/entry point (e.g. a "My Office" row) that keeps the onboarding summary reachable post-onboarding.

- **info** FR-28 (removed employees) is correctly left unaddressed in the UX spec — the PRD explicitly scopes it as future-ready rules only, with no removal feature being built now, so there is nothing for DESIGN.md/EXPERIENCE.md to specify yet. The one place this matters today is the FR-5 Office-archiving gap above, which will need the "Removed employees don't block archiving" rule once both features exist.

- **info** Correctly covered, no gap found: FR-13's double-owner-action race ("This request was already handled" sheet-closes behaviour), the FR-5 map-unavailable fallback, NFR-12 module separation (job banners/refreshes explicitly excluded for attendance notifications), and the FR-16 owner-on-behalf immediate-approval copy distinction ("Approve" vs. "Submit for approval").
