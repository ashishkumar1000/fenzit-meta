Headline: BE has only POST/GET for customers (no PATCH); jobs link to customers by FK plus a service_location snapshot, but job-detail/sync/report reads live-join customer fields; AddCustomerScreen (design-v2 route) can be parameterized for edit following the OfficeFormScreen single-route precedent; spec-customer-map-pin-picker explicitly deferred Edit Customer as future work — this spec is that work and lifts that non-goal.
- (decision) Feasible and reuse confirmed: edit reuses the Add Customer screen (route gains an edit mode) instead of a new screen; user direction honored, OfficeFormScreen is the in-repo single-route add+edit precedent. Blocked on a new BE PATCH /customers/:id — FE cannot ship ahead of it.
- (capability) CAP-1 Owner edits a customer: open a customer, change its details (name, phone, address/location, address details), save; customer detail and list reflect the saved changes. Success: edit form opens prefilled with current values; saving persists via PATCH /customers/:id; detail screen (focus refetch) and list show updated data.
- (capability) CAP-2 Location editing with map prefill: the saved coordinates/formatted address render in the edit form and prefill the shared map-pin picker; re-pinning, search, and manual entry behave exactly as in create. Success: opening the picker from edit centers on the saved pin (initialLatitude/initialLongitude passed); a confirmed re-pin persists new coordinates; manual entry saves null coordinates without clearing addressDetails.
- (capability) CAP-3 Completed-job history integrity: editing a customer never writes to any job-side row — jobs, steps (template stamp), attachments, activity_logs, notifications stay untouched; completed jobs keep their original service_location snapshot, status, steps, photos, signatures, logs. Success: after editing every editable customer field, all job rows referencing that customer are byte-identical before vs after.
- (capability) CAP-4 Owner-only tenant-safe update API: PATCH /customers/:id updates only the caller-owning tenant, owner role only, following house conventions (error envelope, mapping). Success: technician JWT gets 403 FORBIDDEN; cross-tenant id gets 404 RESOURCE_NOT_FOUND (no 403 leak); duplicate phone gets 409 DUPLICATE_RESOURCE; invalid payload gets 422 VALIDATION_ERROR; success returns the full updated customer mapped to the existing response shape.
- (constraint) Reuse the Add Customer screen for edit (explicit user direction; no new screen). Route AddCustomer gains an optional customerId param; mode presence switches title, button copy, discard-dialog copy, and submit target. All existing add-flow tests must stay green unchanged.
- (constraint) An edit may write ONLY the targeted customers row — no writes to jobs or any job-side table; no backfill jobs. Cross-repo ordering applies: additive BE change (PATCH + optional updated_at migration) ships before the FE change.
- (constraint) BE update follows existing owner-update conventions: @Roles(Role.OWNER) at the controller; tenantId-missing gives 400 VALIDATION_ERROR (company-setup message); createAdmin() with explicit .eq(tenant_id) filter (RLS bypassed by service role — drift note C1); empty result = 404 RESOURCE_NOT_FOUND, cross-tenant indistinguishable; PG 23505 maps to 409 DUPLICATE_RESOURCE with the house duplicate-phone message; response uses the existing toResponse camelCase mapping; coordinates re-validated like create; optional updated_at column + update_updated_at_column() trigger per repo convention.
- (constraint) FE update follows existing edit precedents: diff-based PATCH payload (buildUpdatePatch pattern from OfficeFormScreen), entry point on CustomerDetailScreen (Edit affordance in identity row or header-right, returnRouteName CustomerDetail), cache refresh via upsertCustomer(updated) + loadCustomers({ force: true }), edit entry loads via getById (never the list row — list rows lack coordinates/formattedAddress), CustomerDetail FE type extended to carry pincode/latitude/longitude/placeId, AddCustomer tested guards (CAP-6 discard guard, in-flight back guard, read-once pickedAddress) preserved in both modes, MapPinPicker office mode behavior untouched.
- (assumption) Owner means JWT role owner; the edit UI lives only in the owner navigation tree (Customers/CustomerDetail), so no extra client-side role gate is needed beyond the serverside 403.
- (assumption) Pre-launch project (per meta-repo AGENTS rules): DB/schema changes are allowed, so adding customers.updated_at is acceptable without data-preservation migration concerns.
- (assumption) The create-flow merge of street + area into the single address column is kept; in edit the merged line prefills Street and Area starts empty (splitting on the comma is lossy and rejected).
- (question) OQ-1 (the load-bearing decision): customer fields are live-joined into completed-job views (job detail embed, technician sync name+address, future reports), so editing a customer changes what PAST completed jobs display for name/phone/address/coords — while the job's own record (service_location snapshot, steps, photos, signatures, logs) stays intact. Is display-current-contact-info-on-past-jobs acceptable (recommended; normal CRM semantics), or must historical job views freeze customer info as of job time (requires a per-job customer snapshot migration — do it pre-launch or never)?
- (question) OQ-2: is the phone number editable in edit mode? Phone (with country code) is the per-tenant dedupe key (unique index); edits colliding with another customer must surface the 409 duplicate message, and changing phone does not merge or link records. Alternative: leave phone immutable in v1.
- (question) OQ-3: technician freshness — delta sync is keyed on jobs.updated_at, so a customer edit does not re-push to technicians until the job row itself changes; a technician opening a cached completed job may still see the old name/address. Acceptable for pre-launch, or does the sync model need a customer-touch signal?
