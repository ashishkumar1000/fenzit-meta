- (direction) Owner ask (2026-10-04): build a BE config API; FE initializes with shipped defaults and overrides them when the config response arrives (server-driven); FE also sends app and device data in API request headers so the server can drive config; research the industry pattern first and check the requirement via BMAD.
- (decision) Adopt the remote-config pattern (Firebase Remote Config model): defaults shipped in the binary, background fetch, atomic activation, last-known-good persisted locally, fail-open on any error. NOT server-driven UI — no layout or component JSON over the wire.
- (decision) Config endpoint is public pre-login: GET /api/v1/config/app under the existing @Public() decorator (global JwtAuthGuard + RolesGuard already wired in app.module); payload carries no user-specific data.
- (decision) Config storage: Supabase app_config table (key text PK, value jsonb, description, updated_at) as the single source of truth editable without deploys; BE serves it through a short in-memory cache (~60s) so a config read costs no DB round trip.
- (decision) Response shape: flat typed JSON values plus config_version; ETag (payload hash) with If-None-Match 304 and Cache-Control public max-age=60 so the CF worker edge can serve repeats without reaching Render (matters given the measured per-request RTT floor).
- (decision) Client metadata headers v1: X-App-Version (package.json semver, already synced into native files by scripts/sync-version.js), X-Platform (ios|android), X-OS-Version (Platform.Version); X-App-Build (versionCode) if cheaply available; device model DEFERRED (needs a new native dependency); no device identifiers ever.
- (decision) BE logs the metadata headers on every request via the correlation logger and may branch config resolution on them; requests without the headers must never be rejected (older clients and curl probes keep working).
- (decision) Every shipped default equals todays current behavior — a config key used as a kill switch must fail safe to the current behavior when config is unavailable.
- (capability) CAP-1 intent: the app picks up operational and feature configuration from the backend at runtime so behavior changes ship without an app release. success: changing a value in app_config is reflected in an installed app on its next launch or foreground without any app update.
- (capability) CAP-2 intent: the app boots instantly on shipped defaults and overlays the best-known server config so config never delays or breaks startup. success: a fresh install in airplane mode is fully functional on defaults; after one successful fetch, a kill plus offline relaunch runs with the persisted server values, not defaults.
- (capability) CAP-3 intent: every API request carries app and platform metadata headers so the server can log, triage, and target by client attributes. success: any fenzit-be request log line identifies app version, platform, and OS version; config resolution can branch on these attributes.
- (capability) CAP-4 intent: the server can flag an unsupported app version (minimum supported version) so field clients update before breaking API changes. success: setting a min version above an installed app version in app_config triggers the in-app update UX on that device without shipping anything.
- (capability) CAP-5 intent: config values can resolve differently per client platform and app version (attribute targeting via the metadata headers). success: the same endpoint returns platform-appropriate values when clients with different platforms or app versions ask.
- (constraint) No secrets or PII in the config payload; no persistent device identifiers in headers (Play policy plus privacy).
- (constraint) API base URL bootstrap stays compile-time — config cannot relocate the server the config itself is fetched from.
- (constraint) Fail-open: config fetch uses a short dedicated timeout and never blocks boot; any failure keeps last-known-good or defaults.
- (constraint) Forward compatibility: clients ignore unknown config keys; the server only adds keys and never repurposes existing ones (sideloaded old clients must keep working).
- (constraint) bun only; headers are implemented at the single FE choke point (apiClient request interceptor); config serving is owned by a new BE config module.
- (note) Non-goals: no server-driven UI (values only, never layout); no A/B experiments, percentage rollouts, or per-user/per-tenant targeting in v1; no realtime push (pull on start and foreground only); no admin UI in v1 (SQL or Supabase dashboard edits).
- (assumption) MMKV (already a dependency) persists last-known-good config; no new native dependency ships in v1, which is why the device-model header is deferred.
- (assumption) App version source of truth is package.json (sync:version keeps the native files in sync); the JS bundle reads it at build time via JSON import or a generated constant.

- (direction) Owner requirement (2026-10-04): config responses must be cached on Cloudflare with a TTL — edge speed is a hard requirement, not a nice-to-have.
- (decision) Edge-cache mechanism (deployed): Cache API (caches.default) inside fenzit-api-proxy for GET /api/v1/config/app only; cache key = bare URL; Authorization stripped from the cached path because the app attaches the bearer token to every request and Cloudflare auto-bypasses caching for Authorization-bearing requests; only 200s cached; TTL 60s owned by the worker constant CONFIG_EDGE_TTL_SECONDS emitted as Cache-Control public, max-age=60; x-cache HIT/MISS response header for verification.
- (decision) Staleness bound: an owner config edit reaches all clients within max-age (60s) of TTL expiry; instant purge via the CF API is explicitly deferred until a key needs faster propagation.
- (capability) CAP-6 intent: config reads are served from the Cloudflare edge so a config fetch costs an edge lookup instead of a Render plus cross-region-DB round trip. success: two back-to-back GETs of /api/v1/config/app within the TTL — the second returns x-cache HIT with Render never contacted (Render logs show only the first); TTL expiry re-fetches from origin.
- (constraint) The config endpoint stays parameterless while the payload is identical for everyone; when attribute targeting (CAP-5) lands, the edge cache key must grow the targeting attributes with it or clients get cross-partition values.
