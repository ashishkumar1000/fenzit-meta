topic: Technician GPS location capture on job workflow step completion
goal: Owner can require technicians to share GPS location when completing job steps; per-step capable on backend, single job-level toggle on frontend for MVP
updated: 2026-09-13T11:41
---

- (direction) Owner defines a job and can require the technician to capture lat/long when completing each step; must be configurable
- (direction) By default each step requires location; backend should support per-step configuration, but for now owner is only given a single job-level toggle (on by default) — per-step config UI is future work
- (constraint) jobs table (fenzit-be) has no latitude/longitude columns after all migrations; only a free-text service_location TEXT column exists (verified against final column list: id, tenant_id, job_number, customer_id, technician_id, service_location, scheduled_start, scheduled_end, status, current_step, priority, description, notes_for_technician, created_at, updated_at, completed_at, skill_id, workflow_template_id, workflow_template_version)
- (constraint) workflow_templates.steps JSONB already carries requires_photo/requires_signature booleans per step; shape is enforced by BOTH a Postgres CHECK function workflow_steps_valid() (migration 20260911000003) AND a TypeScript parseStep() mirror (workflow-template.model.ts) — any new step attribute like requires_location needs both updated in lockstep
- (constraint) advance_workflow_step RPC (latest def: 20260909000003_rpc_notify_owner_on_advance.sql) signature is (p_job_id, p_tenant_id, p_actor_id, p_step, p_new_status, p_expected_current_step) — no location params, and the RPC does NO step-content validation at all; photo/signature presence validation happens entirely in NestJS WorkflowService before the RPC is called
- (constraint) activity_logs table already inserts one row per step advance (event_type = 'step_' || p_step) with a free-form metadata JSONB column already used elsewhere for structured payloads (e.g. job_reassigned, confirm_attachment) — this is a natural place to store step-completion location without a new table
- (constraint) customers table already has latitude/longitude/formatted_address/pincode/place_id (DOUBLE PRECISION, nullable, Story 1.3); jobs table has none of these; customer coordinates are optional and may be null
- (constraint) no haversine/distance/geofence calculation exists anywhere in the backend codebase (verified via repo-wide grep) — would need to be built from scratch to support any geofence validation
- (constraint) CreateJobDto and AdvanceWorkflowDto (fenzit-be) currently have zero location fields; AdvanceWorkflowDto only carries `step: string`
- (constraint) historical precedent: jobs table used to have require_completion_photo/require_completion_signature as JOB-LEVEL booleans, but these were dropped in migration 20260911000003 in favor of per-step JSONB flags — the feature we're building is effectively reviving a job-level toggle pattern that already existed once
- (constraint) fenzo-app (frontend) is a bare React Native CLI app, NOT Expo — no expo-location or any Expo package is available or installed
- (constraint) NewJobScreen.tsx builds serviceLocation as derived plain text only ("customer.address, customer.city"), never coordinates; there is no editable location field on this screen at all (flagged as a known gap in the file's own comments)
- (constraint) AddressPickerSheet is used in exactly one production site — AddressPickerField.tsx inside AddCustomerScreen — for customer address only; it is never wired into job creation or NewJobScreen; there is no existing job-specific location picker
- (constraint) CreateJobRequest and ApiJob (fenzo-app services/resources/jobs.ts) carry no latitude/longitude fields at all; the only coordinates in the job domain come from the embedded customer object in GET /jobs/:id (JobDetailCustomer.latitude/longitude, optional)
- (constraint) WorkflowTemplateStep (FE type) already mirrors requiresPhoto/requiresSignature/setsStatus/advancesOn — a new requiresLocation field should follow this exact shape
- (constraint) useWorkflowAdvance.ts has an established divert pattern: if targetStep.requiresSignature, it navigates to a dedicated capture screen (SignatureScreen) instead of posting advanceWorkflow directly (capture -> upload -> advance) — this is the pattern a location-requiring step should follow
- (constraint) fenzo-app has no AsyncStorage and no NetInfo dependency; local storage uses react-native-mmkv; offline queueing is explicitly deferred via "EPIC4" TODO comments in useWorkflowAdvance.ts and useSignatureSave.ts — current convention for retry-safety is a per-action idempotency key (keyRef) reused until the server answers, with inline failure + manual retry, not a queue engine
- (constraint) permission pattern in fenzo-app uses PermissionsAndroid.request directly (not react-native-permissions), Android-gated with a named denial-message constant; iOS handles camera permission implicitly via the native picker library, but geolocation on iOS requires an explicit authorization request unlike camera
- (constraint) no geolocation library is installed anywhere in fenzo-app (no expo-location, no react-native-geolocation-service, no @react-native-community/geolocation) — must be added from scratch
- (decision) Use react-native-geolocation-service (bare-RN compatible) instead of expo-location, since fenzo-app has no Expo runtime
- (decision) Do not build a new AsyncStorage-based offline queue for location submissions; reuse the existing idempotency-key + inline-retry convention already established in useWorkflowAdvance.ts, consistent with how other capture flows defer offline handling to future EPIC4 work
- (decision) Store step-completion location data by extending the existing advance_workflow_step RPC's activity_logs insert with a metadata JSONB payload (latitude, longitude, accuracy, capturedAt) instead of creating a new step_completions table — reuses the existing per-step audit row
- (decision) Add requires_location to the workflow step JSONB schema (per-step, backend future-ready, mirrors requires_photo/requires_signature) AND add a job-level boolean column capture_location_on_steps (default true) as a master switch that gates whether any step-level location requirement is enforced for that job — reconciles "per-step capable backend" with "single job-level toggle" for the MVP frontend, and mirrors the historical require_completion_photo/signature job-level pattern that existed before
- (decision) Location requirement validation (required? provided? accuracy acceptable?) happens in NestJS WorkflowService.advanceWorkflowStep before calling the RPC, matching exactly how photo/signature validation already works today — not inside the SQL RPC
- (decision) Reuse the existing hasInvalidCoordinates util (src/common/utils/validate-coordinates.ts) and the +-90/+-180 range validation pattern already used in StructuredAddressDto for validating the new location fields
- (decision) Consent modal for location permission is shown only once — only when permission status is undetermined (never requested); skip it if already granted; show a Settings-redirect prompt (not the consent modal again) if previously denied
- (assumption) Geofence validation (comparing technician's step-completion GPS against the job's own site coordinates) is deferred out of MVP scope: jobs have no reliable coordinates of their own, only the customer optionally has nullable lat/long, and no distance/haversine utility exists in the backend yet — MVP validates GPS accuracy only, not geofence distance
- (decision) New LocationCapture flow on the frontend follows the exact same divert pattern as Signature capture in useWorkflowAdvance.ts: if targetStep.requiresLocation, navigate to a dedicated location-capture screen (permission -> capture -> attach) before calling advanceWorkflow, rather than capturing inline on the job detail screen
- (decision) Job-level toggle capture_location_on_steps surfaces in NewJobScreen as a simple switch (default ON); no new address/location-picker UI is needed since this is just a boolean flag, separate from the existing customer-address AddressPickerSheet flow
- (question) Should accuracy threshold (e.g. <=100m) reject the step-completion outright, or accept with a flag for later ops review? Field-service research suggests accept-with-warning is friendlier, but not yet decided with the user
- (question) Should location data in activity_logs.metadata also have its own retention/deletion policy (GDPR-style), or does the existing activity_logs retention (if any) already cover this? Not yet confirmed against fenzit-be's current data retention policy

- (decision) Geolocation library changed from react-native-geolocation-service to react-native-nitro-geolocation (via its /compat API), replacing the earlier assumption. Research (2026-09-13) found react-native-geolocation-service is bridge-only and unmaintained (last published ~4 years ago), a poor/risky fit now that fenzo-app runs RN 0.86 with New Architecture enabled (newArchEnabled=true). react-native-nitro-geolocation is built specifically for New Architecture on Nitro Modules — and fenzo-app already depends on react-native-nitro-modules@0.35.10 via react-native-mmkv, the exact version nitro-geolocation's own docs pin against, so this adds no new native runtime.
