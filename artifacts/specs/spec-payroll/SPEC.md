# Payroll — monthly salary processing with attendance-linked LOP

## Why

Fenzit tracks attendance and leaves but cannot turn them into pay: at month end a company admin has no way to generate salary slips, so LOP from excess leaves is applied by hand and statutory slips are produced outside the product (a pain to solve, plus an opportunity — attendance-first payroll is the market's entry wedge). Backdrop: Fenzit is pre-launch, India-first, single-sprint mindset with an explicit user direction to keep payroll simple — good-to-have features only, no enterprise HRMS complexity, built for mid-scale organisations.

## Capabilities

- **CAP-1 — Salary component library**
  - **intent:** Company admin can define a company-level salary component library (e.g. basic, HRA, conveyance, special allowance) in the web admin; exactly one component in the library is designated **basic** (the PF base and the Form V basic/DA line).
  - **success:** A created component is assignable to employees; payslip lines snapshot the component name at the run that produced them; a component cannot be deactivated while any employee structure references it (rejected with the referencing employees listed); renaming is allowed and reflected from the next run; a structure saved without a designated basic component is rejected with a plain-English error.

- **CAP-2 — Employee salary structure (components, formulas, effective dating)**
  - **intent:** Company admin can set each employee's salary as an amount per component, where a component may instead be defined by a formula recomputed from other components (e.g. HRA = 40% of basic); structure changes carry an effective date and never overwrite history.
  - **success:** Employee A's structure (canonical fixture) computes gross ₹28,000 matching the fixture table; changing basic recomputes HRA at the next run without editing HRA; a revision effective from month M makes M's run use the new structure while prior locked months keep their snapshots (fixture variant F); a mid-month-dated revision (e.g. effective 2026-10-15) is first used by the November run — the whole-month rule — and an unlocked October re-run resolves October's structure, never the newest save; a formula cycle (A→B→A) is rejected at save with a plain-English error naming the chain (whole set re-checked on every edit); a formula whose operand has no amount in the employee's structure, a division by a zero-amount operand, or a negative component amount is rejected at save.

- **CAP-12 — Leave types for LOP**
  - **intent:** Admin can configure a leave-type catalog (each type marked paid or unpaid, e.g. casual/sick/earned/unpaid) on the existing leave feature; LOP in a run derives only from leaves of unpaid-marked types plus unapproved absences; paid-typed leaves never produce LOP in v1 (no leave-balance or accrual engine).
  - **success:** The canonical fixture (2 paid-typed + 3 unpaid-typed leaves + 1 unpaid half-day) yields LOP of exactly 3.5 days; a paid-typed half-day produces no LOP (fixture variant I); reclassifying a type applies to runs executed after the change; locked months keep their snapshots.

- **CAP-3 — Monthly payroll run**
  - **intent:** Company admin can run a monthly payroll cycle (async, status polled: queued → running → completed | failed; failed is terminal and retryable by a fresh request) that computes each **active employee-role membership**'s pay from the structure in effect, the month's day-status (LOP applied), and configured deductions; owners/admins and removed members are excluded in v1 — no inclusion configuration; employees with no effective structure, no attendance enrolment, or an employment window that does not intersect the run period are skipped and flagged in the run summary — never a silent ₹0 payslip.
  - **success:** A run of the canonical fixture produces per-employee payslip rows exactly matching the fixture's expected-numbers table; mid-month join/exit auto-prorates per the run-arithmetic invariant (variants C, E, I); re-running the unlocked month replaces it cleanly — one payslip per employee, off-cycle lines preserved; a failed run leaves zero payslips (atomic per tenant-month); concurrent runs for the same month serialize; a zero-employee company completes with a zero-payslip run status; a run is accepted only for months on/after the company's first payroll month (the earliest month any employee's join date falls in — fixture: 2026-09) and only from the month's cut-off day onward (tenant tz, attendance inclusive of the cut-off day) — future months and pre-cut-off attempts are rejected with a plain-English reason.

- **CAP-4 — LOP divisor configuration**
  - **intent:** Company admin can set the LOP divisor convention (calendar days | fixed-30 | fixed-26, default fixed-26); the setting is effective-dated and resolves per month-start resolution (Run arithmetic).
  - **success:** The canonical fixture under each convention produces its own distinct expected row (fixture §Divisor conventions); a change applies from its effective date — an unlocked month re-runs on the divisor effective for that month; locked history keeps snapshots.

- **CAP-5 — Half-day LOP**
  - **intent:** A half-day that produces LOP — an unpaid-typed half-day leave or an owner-corrected `half_day` day-status — counts as 0.5 LOP day.
  - **success:** An owner corrects a present day to half_day via the existing attendance-override path, then the run yields exactly half the single-day LOP deduction (fixture §Owner-corrected half-day: LOP 4.0, earnings 23,692.31); the leave-part path matches the canonical fixture (3.5 total); an owner override replaces that day's leave-derived LOP treatment.

- **CAP-6 — Deduction heads + statutory auto-computation**
  - **intent:** Company admin can define deduction heads as flat monthly amounts or percentages with an admin-picked basis (**basic | gross**), applied per employee; percentage heads compute on the **earned** basis amount for the period (basic: earned basic; gross: post-LOP gross). The system additionally auto-computes PF — employee deduction 12% of the **earned basic** (basic wages payable for the period: prorated for partial months and reduced by LOP), capped at the PF wage-ceiling config; employer share recorded not deducted; company-level PF-covered switch default **off**, but an employee with a populated UAN or PF account number (ever-member) is covered **regardless of the switch**; exclusion applies only to never-members above the ceiling (admin config carrying an EPFO-flux warning); the first-coverage month is recorded when the tenant switches PF-covered on, and employees whose join date precedes it are first-coverage existing employees — and a new-regime TDS estimate for FY 2026-27 under the Income-tax Act, 2025 (slab table, standard deduction ₹75,000, resident-only s.157 rebate with marginal relief, 4% cess — per the fixture's FY 2026-27 config rows): the projection = current monthly structure × months of employment in the FY (never the post-LOP period gross), spread over the **remaining FY months including the run month**, re-estimated and re-spread on any revision or override (a leaver's final run deducts the full remaining estimate); the admin may override any computed amount behind an employer-liability acknowledgment — an override is scoped to one employee and one salary period, survives unlocked re-runs of its period, is immutable after lock, and later periods recompute normally.
  - **success:** The canonical fixture (PF on, PT ₹200) produces PF, TDS, and net exactly as the fixture's expected-numbers table; a percentage head applies to the earned basis (variant B); an override changes only that amount after the acknowledgment; the 50% total-deduction cap (Legal constraint — cap base includes off-cycle earnings; employer shares and recovery lines outside) is checked **after** overrides (variant D: deductions clamped, excess 2,646.15 raised as a recovery line on the next run's payslip — subject to the same cap check, the unabsorbable remainder rolled forward, the outstanding balance shown in the run summary, and deducted on the final run if the employee exits); a statutory value's effective-dated change applies per month-start resolution and locked months keep their old values.

- **CAP-7 — Statutory payslip + self-service**
  - **intent:** The system generates a payslip per employee per run on the **central Form V template (Code on Wages (Central) Rules, 2026, rule 52)** — date of issue; establishment name + address; wage period; employee name, father's/mother's/spouse name, designation, UAN, bank account number; wage-rate break-up (basic / DA / allowances via the component structure); total attendance (paid days / days worked); overtime (₹0.00 in v1); gross wages payable; deductions (PF / ESI / others); net wages paid — plus the product extras: employee code (owner-set), PAN, date of joining, slip number (unique per tenant per salary period), payment date. The Form V ESI line renders the computed admin-head value or ₹0.00 — no ESI computation in v1. This field set is authoritative for tests. Payslip rows store a **full snapshot** of the Form V + product field set, so field presence and value are DB-assertable and the PDF renders from the snapshot. Payslips are employee-visible **only after the month is locked** (admin previews pre-lock); regeneration of an unlocked month issues a new slip number and **destroys and replaces** the superseded row — one live row per employee-period; slip numbers are allocated gap-free but the live set may gap after regeneration (no consecutiveness test over live rows); the prior presigned URL is invalidated; a post-lock PDF retry regenerates the file only, never recomputes amounts; a missing PAN renders blank with an admin-visible warning, never a fabricated value.
  - **success:** The fixture payslip carries every Form V field plus the product extras (asserted from the snapshot row); the employee opens their own payslip history and downloads the PDF and cannot open another employee's; a different company admin sees zero payroll rows for another tenant; re-running the unlocked month changes the slip number and invalidates the old URL.

- **CAP-8 — Payroll calendar**
  - **intent:** Company admin can configure the attendance cut-off day (default 25th, valid 1–28) and pay date (default 1st of next month, **valid 1–7** — the CoW window: payable before expiry of the 7th day, so the 7th itself is legal); all month boundaries resolve in the tenant timezone; attendance/leaves after the cut-off in month M count in month M+1's run as prior-period days (mechanism: Run arithmetic).
  - **success:** Setting the cut-off to the 20th makes the run count only up to the 20th; a leave on the 27th (fixture G) appears in the next month's run with November's tabled amounts; a pay date **after the 7th (from the 8th)** is rejected with the CoW reason; a cut-off of 29/30/31 is rejected with the February reason; the pay date prints on generated payslips.

- **CAP-9 — Payroll lock**
  - **intent:** Company admin can lock a payroll month — permanent in v1, no unlock; a month that has never run cannot be locked (409). The lock freezes the month against re-run, payslip edit, and off-cycle targeting, each rejected with HTTP 409 `PAYROLL_MONTH_LOCKED`; the month-status API returns `locked: true`. Config edits (heads, calendar, structures) are effective-dated rows — a locked month keeps its snapshotted values, so no config edit is ever blocked. The lock freezes month M's pre-cut-off attendance dates; M's post-cut-off days (26th–end) stay editable until M+1's run consumes them as prior-period days.
  - **success:** Each enumerated operation after locking returns 409 with that code; a never-run month returns 409; the month-status API exposes the lock for the web UI to render; the lock confirmation states its permanence, the off-cycle remedy, and lists any outstanding staged off-cycle lines.

- **CAP-10 — Off-cycle payout**
  - **intent:** Company admin can add a one-off line for a specific employee in an unlocked month (current open or earlier unlocked) — an earning (bonus, arrear, correction) or a **negative recovery line** (admin-acknowledged, e.g. an overpay discovered in a locked month); a line is tagged **wage** (arrear/correction — joins the PF base) or **bonus** (default — never joins the PF base); every line joins the wage-period gross, the 50%-cap basis, and the TDS projection; it is staged when that month has not run yet and appears on the month's payslip when it runs; off-cycle for an employee with no effective structure is rejected.
  - **success:** The off-cycle line appears on the chosen month's payslip included in gross and net (fixture G); a bonus does not change PF (fixture G); the cap applies on the basis including the line (fixture G: D + bonus row); no other employee's payslip changes; targeting a locked month is rejected (409); a staged line appears when the month first runs; a re-run keeps exactly one payslip with the line intact; orphaned staged lines are listed in the lock confirmation and run summary.

- **CAP-11 — Payroll audit trail**
  - **intent:** Every payroll-relevant change (structure, deduction heads, calendar, runs, lock, off-cycle) is recorded as who/what/when, viewable by company admin.
  - **success:** `GET` payroll audit events returns one entry per scripted edit, ordered by created_at with a monotonic tiebreaker as provided by the chosen audit idiom, each naming actor, action, and target — table-agnostic.

- **CAP-13 — Employment data for payroll**
  - **intent:** Company admin can capture, per employee in the web admin, exactly this field set — name, father's/mother's/spouse name (mandated by CoW Form V), PAN (validated format), date of birth, date of joining, PF account number, UAN number, designation, bank account number, IFSC code, bank name, employee ID (the tenant employee code, owner-set per `spec-human-readable-ids` CAP-4), department — plus exit date; exit date earlier than join date is rejected at save; the join date is editable and may be cleared — the backfill default runs once at setup, so an active membership without a join date is the real trigger for the run's skip-with-warning path; existing active memberships are backfilled (admin-supplied or created_at-derived default); a removed membership without an exit date falls back to its status-change date.
  - **success:** Fixture variants C/E/I prorate from the join date; a run flags an employee with a missing joining date as skipped-with-warning (never null-prorates); exit date drives proration (variant C2 — seed: an **active** membership with exit_date 2026-10-10); a missing PAN renders blank with a warning (CAP-7); every listed field is editable in the web admin and persisted against the membership/profile; DOB, PF/UAN, and bank details are never exposed to other employees.

## Constraints

**Legal (Code on Wages)**
- Governing law is the **Code on Wages** (in force 21 Nov 2025; central final rules 8 May 2026; state rules a variable overlay); verify the enacted text + target states' rules before legal freeze.
- Wage slips are mandated by CoW s.50(3) and prescribed by **Form V, rule 52 of the Code on Wages (Central) Rules, 2026** (Gazette 8 May 2026; citations in `statutory-verification.md`): issued electronically or physically **on or before payment of wages**; electronic issuance explicitly permitted. The finalised state rules adopt the identical model form — so the product ships the central Form V template plus a per-state "rules notified?" config switch, not per-state field sets (acceptance: CAP-7).
- Monthly wages payable **on or before the 7th** of the succeeding month — CoW s.17(1) reads "before expiry of the 7th day", so the 7th itself is legal and the 8th is a breach; uniformly, no size carve-out (acceptance: CAP-8).
- **Flat 50% total-deduction cap** per wage period, LOP included; cap base = post-LOP pre-deduction gross **including off-cycle earnings**; employer shares and recovery lines outside the base; breach clamps with the unabsorbed excess raised as a recovery line on the next run (acceptance: CAP-6, variant D).
- No statutory literal in code — rates, ceilings, slabs, and the LOP divisor are effective-dated configuration; all dated values (statutory and policy) resolve per month-start resolution (Run arithmetic).

**Run arithmetic — the single pay formula (the invariant)**
- Daily wage = structure amount ÷ divisor, unrounded. **Payable days = calendar days of the employment window ∩ (run month ∪ the run's prior-period days — month-M dates after the cut-off), capped at the divisor**; week-offs and public holidays inside the window are paid days. Earnings = daily wage × (payable − LOP-equivalent days), floored at zero with any shortfall recorded for recovery via off-cycle payout. A full month with no LOP yields exactly the structure amount under every divisor.
- LOP-equivalent days = approved unpaid-typed leaves (half-day 0.5) **plus** day-status `absent` days with no approved leave **plus** owner-corrected `half_day` days with no paid coverage for that half (0.5 each) — counted only inside the payable window; leave outside it never LOPs; **each date belongs to the one run that owns it under the cut-off** (a leave dated after the cut-off belongs to M+1's run — never split across months, never double-counted); `checkout_missing` is paid pending owner correction, flagged in the run summary; days inside the window with no attendance data (enrolment gaps) are paid and flagged; **an owner override replaces that day's leave-derived LOP treatment**.
- TDS estimate rules: projection = current monthly structure × months of employment in the FY (never the post-LOP period gross); spread over the **remaining FY months including the run month**; re-estimate and re-spread on revision; a leaver's final run deducts the full remaining estimate.
- **Month-start resolution:** structures, statutory values, and policy settings (divisor, cut-off, pay date, deduction heads) are effective-dated config rows resolved as of the **run month's first day** (tenant tz) — a mid-month-dated change is first used by the next month's run; an unlocked re-run resolves its own month, never the latest save; locked months keep their snapshots.
- Money is `numeric(18,2)`; intermediates unrounded; half-up rounding applied once per payslip line. Formulas support component references, constants, `+ − × ÷`, and percent-of only; cycles are rejected at save; division by a zero-amount operand and negative component amounts are rejected at save (acceptance: CAP-2).
- Runs are idempotent per month and **atomic per tenant-month** (a failed run leaves zero payslips); concurrent runs for the same month serialize via the existing advisory-lock idiom, re-checking the lock before final commit; the run is async with a polled status (queued → running → completed | failed; failed is terminal and retryable; the advisory lock is released when the worker session ends); run months are bounded per CAP-3; the tenant timezone governs the run window, cut-off, and pay date.

**Data & schema**
- Employment dates (join/exit) and the leave-type catalog are **new schema** on the existing membership/leave structures (no joining/exit data exists today; ~842 existing users backfilled per CAP-13).
- The run consumes the existing day-status engine (`src/common/day-status`, `summariseEmployeeMonth`, including owner corrections) — payroll never recomputes attendance.
- Attendance/leaves after the cut-off belong to the next month's run as prior-period days (payable-window mechanism: Run arithmetic).
- All payroll FKs go through `memberships`; deny-by-default RLS with NestJS service-client access and explicit tenant filters; payslip access is owner-or-own; cross-tenant reads return zero rows (acceptance: CAP-7). No service-role keys in any frontend.
- Slip numbers reuse the house per-tenant sequence-counter idiom (`job_sequences` pattern: counter keyed `(tenant_id, salary_period)`, ON CONFLICT upsert, gap-free), allocated NestJS-first — no new SECURITY DEFINER RPC (AD-3). Superseded payslip rows are destroyed and replaced (CAP-7), so the live set may gap after regeneration.
- Statutory values (PF %, ceiling, slab table) are effective-dated config rows — acceptance in CAP-6. **The PF ceiling config carries its history: ₹15,000 (pre-2026-09-17) and ₹25,000 (from, S.O. 5109(E)) — a run resolves the row effective for its month (a 2026-09 run uses ₹15,000; October uses ₹25,000; fixture §Effective dating).**
- Payslip rows store a **full snapshot** of the Form V + product field set (money rows and every field DB-assertable); the PDF renders from the snapshot.

**Reuse & platform**
- Payslip PDF rides the existing async report pipeline (report request → worker → pdfmake → R2 → presigned URL) — no new PDF machinery; employee visibility only after lock.
- All payroll configuration and administration lives in the **web admin (fenzit-web)**; the **mobile app (fenzit-app) is minimal — employee payslip self-service only** (own payslips + PDF). No payroll admin UI in the mobile app.
- **Zero RPC anywhere in payroll** (user direction 2026-11-17): no new database RPCs at all — every computation, allocation, and settings write is NestJS-first. The slip-number counter is the one place a transactional DB step might tempt an RPC: it uses the `job_sequences` ON CONFLICT idiom called from NestJS, never a SECURITY DEFINER function (AD-3).
- Audit idiom (generic `audit_log` vs domain append-only) is picked in the plan — both precedented; CAP-11's acceptance is table-agnostic.
- Payslip employee-ID renders the tenant employee code, which the **owner sets and can edit** (amended `spec-human-readable-ids` CAP-4) — payroll owns no ID-generation logic.
- **Test anchor:** backend payroll stories extend `test/payroll-journey.e2e-spec.ts` (same real-DB helpers as the attendance journey suite: throwaway tenant, one API call + DB assert per step, FK-safe cleanup), seeded from `canonical-fixture.md` (money rows, asserted day-counts, and the payslip-snapshot field set); the CAP-7 employee-visibility leg runs end to end; legs guard on real credentials; **web-admin acceptance surfaces (lock-confirmation copy, calendar form, employment-data editability) are covered by fenzit-web journey/component tests**, mirroring `spec-human-readable-ids`' FE checks.

## Non-goals

- Statutory filing engines: PF ECR, ESI challans, Form 24Q eTDS, Form 16 generation — admin serves these outside the product.
- Built-in state-wise PT/LWF slab tables; **ESI computation/threshold logic — admins model ESI (e.g. 0.75%) as a per-employee percentage head if applicable, and the Form V ESI line renders that head's value or ₹0.00**; full tax computation (old-regime path, investment declarations, surcharge/annual recompute) — TDS stays a new-regime estimate.
- Leave-balance/accrual engine — LOP is type-based only (CAP-12).
- Loans & advances with EMI, F&F settlement workflow, leave encashment at exit, comp-off, overtime pay lines.
- Bank-transfer advice integration, email/WhatsApp payslip delivery (in-app + PDF only; electronic Form V delivery is compliant), legacy state wage-slip formats (e.g. Minimum Wages Rules Form XI) for draft-state tenants, maker-checker governance, AI features, contractor payments, multi-entity payroll, weekly/fortnightly pay cycles.
- Payroll admin UI in the mobile app (web admin owns all configuration).

## Success signal

A company admin, at month end, configures components and deduction heads once, runs payroll, and every employee's payslip — LOP from their actual leaves, prorated for mid-month joins/exits, statutory PF/TDS computed with admin override — is generated, lockable, and visible to that employee in the mobile app with a PDF download. A second run on the same month produces the same numbers until config changes. The canonical fixture's expected-numbers table holds exactly.

## Assumptions

- Company admin runs payroll; platform super admin has no payroll UI in v1.
- All employee roles in scope; user-facing copy says "Employee".
- Leaver final pay is issued on the normal monthly run for their exit month — the CoW s.17(2) two-working-day F&F timeline is a documented v1 divergence, accepted pre-launch.
- Whole-month rule for revisions: a mid-month-dated structure change takes effect from the next month's run (month-start resolution — no half-month apportionment).

## Open Questions

- **TDS s.192 employer obligation** — the *method* is verified (estimate annual salary income, apply slabs, spread over remaining months — practitioner standard, CalcGuru Jul 2026); still open: the bare s.192/201 statutory wording and whether any small-employer exemption exists, before relying on the estimate + override posture in user-facing compliance copy.
- **EPFO excluded-employee flux** — EPFO administration keeps pushing the exclusion reading for above-ceiling joiners (Feb 2025 circular withdrawn Apr 2025; Jul 2025 draft unnotified) while the judicial line (SC *Pioneer* 2019, Kerala HC *Sivasankaran* 2018/19) supports mandatory enrollment; the product default follows the judicial line with a config flag for the flux. Confirm before legal freeze.
- **EPFO circular primary text** — the mid-month contribution rules (15+ wage-days → full month; <15 days → pro-rata) trace to the HRM-4(2)17/2014/SS-III series (27.01.2017 order — /125 vs /1584 number unconfirmed) and an 08.08.2018 circular; read the primary PDFs (e.g. `eGov_ROHyd2.pdf`) before citing any number in user-facing copy.
- **15-day EPFO joiner convention** — EPFO practice: ≥15 wage-days in a month → contribution on the full month's wage; <15 → pro-rata. v1 computes on exact earned basic (the fixture's basis); adopt the convention or document the divergence before legal freeze.
